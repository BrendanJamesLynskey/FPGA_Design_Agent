# Stage 0: the GT Wizard probe for buffer bypass (brief 96F1, Vivado 2026.1 Basic, no board)

What the Transceiver Wizard (UltraScale FPGAs Transceivers Wizard 1.7, `gtwizard_ultrascale`) does when the design's own configuration (`designs/b96_kr260_10g/ip/amd_ip.tcl`: GTHE4 channel X0Y6, QPLL0, 10.3125 Gb/s, RAW 64-bit user data on a 32-bit internal path, 156.25 MHz reference) is switched to buffer bypass, whether the dynamic QPLL fractional-N ports can be reached, and the GT attributes the bypass build gets, next to today's build. Everything here is generated by the scripts in this folder (an in-memory project, no bitstream, no board); the generated AMD sources are not committed.

## Findings

**1. Options that give TX and RX buffer bypass.** Two properties, nothing else: `CONFIG.TX_BUFFER_MODE 0` and `CONFIG.RX_BUFFER_MODE 0` (default 1 each). The core validates (`probe2.txt`).
- Setting `TX_BUFFER_MODE 0` makes the Wizard change `TX_OUTCLK_SOURCE` from `TXOUTCLKPMA` to `TXPROGDIVCLK` by itself, which is `TXOUTCLKSEL = 3'b101` in the generated wrapper (`wrapper_attribute_diff.txt`): the user clock is derived from the QPLL's own clock, so no steering is needed. `RX_OUTCLK_SOURCE` stays `RXOUTCLKPMA` (the recovered clock). `TX_PROGDIV_CFG` becomes 16.0 (it was 0.0, unused); `C_TX_OUTCLK_FREQUENCY` stays 322.265625 MHz.
- **Wizard quirk:** setting `TX_BUFFER_MODE 0` also moves `FREERUN_FREQUENCY` from 100 to 161.1328125 by itself. The bypass IP script sets it back to 100 MHz last and checks it (`ip/amd_ip_bypass.tcl`).
- **Phase alignment: auto mode, single lane.** The generated sources show `C_TX_BUFFBYPASS_MODE = 0` and `C_RX_BUFFBYPASS_MODE = 0`, which the controllers' source calls "auto mode" (`gen_auto_mode`, `gen_assign_one_chan`). The property `RX_BUFFER_BYPASS_MODE` reads `MULTI`: setting it to `SINGLE` is accepted and then reads back `MULTI`; there is no `TX_BUFFER_BYPASS_MODE` property (setting it is an error). The label is therefore not the controller mode: the generated code is the evidence.
- **The controllers** (`gtwiz_buffbypass_tx`, `gtwiz_buffbypass_rx`, inside the core, `LOCATE_*_BUFFER_BYPASS_CONTROLLER = CORE`) drive `TXSYNCMODE = 1`, `TXSYNCALLIN = TXPHALIGNDONE`, `TXDLYSRESET`, and tie the manual phase-alignment pins (TXPHALIGN, TXPHALIGNEN, TXDLYEN, TXPHDLYRESET and the others) to 0; the RX controller is the same with `RXSYNCMODE = 1`, `RXSYNCALLIN = RXPHALIGNDONE`, `RXDLYSRESET`. State machine (4 states): IDLE, assert DLYSRESET, deassert and wait for the rising edge of SYNCDONE, DONE (done high; error = not PHALIGNDONE). It **starts by itself on the rising edge of the reset-done level** (`gtwiz_reset_{tx,rx}_done_out`) or on `start_user_in`, and clears done and error only when it starts, a few clocks later (so the previous sequence's done is still high for those clocks; `results/b96f1/bypass_seq/` measures it and the design gates on it).
- **Ports the core gains** (`ports_diff_bypass_vs_buffers_on.txt`; all else identical): inputs `gtwiz_buffbypass_tx_reset_in`, `gtwiz_buffbypass_tx_start_user_in`, `gtwiz_buffbypass_rx_reset_in`, `gtwiz_buffbypass_rx_start_user_in`; outputs `gtwiz_buffbypass_tx_done_out`, `gtwiz_buffbypass_tx_error_out`, `gtwiz_buffbypass_rx_done_out`, `gtwiz_buffbypass_rx_error_out`, `txprgdivresetdone_out`. The controllers run on TXUSRCLK2 and RXUSRCLK2. No `txphaligndone` or `rxphaligndone` port is exposed (the controllers consume them inside the core): the board sees only done and error.
- The controllers' reset input needs a driver: the design uses "user clock not active" (`gtwiz_userclk_*_active_out` inverted). That choice is ours and was not checked against AMD's example design: UNCONFIRMED (the controller source shows reset only clears its state).

**2. Dynamic QPLL fractional-N (SDM) ports: no through the Wizard; yes with the QPLL outside the core.**
- Inside the core the Wizard ties `sdm0data_in`, `sdm0toggle_in`, `sdm0reset_in`, `sdm0width_in` (and the QPLL1 copies) to constants in `gth_wiz.v`, and offers only a static numerator, `CONFIG.TX_QPLL_FRACN_NUMERATOR` and `RX_QPLL_FRACN_NUMERATOR` (0 to 16777215, 0 = off), which sets the static `SDM0DATA` attribute. Setting it to 1000 made the Wizard also change `TX_REFCLK_FREQUENCY` and `RX_REFCLK_FREQUENCY` to 64.453101 by itself (it re-derives the reference it expects; reason not investigated): recorded as a hazard, not used.
- With `CONFIG.LOCATE_COMMON EXAMPLE_DESIGN` (the QPLL taken out of the core) the core loses `gtrefclk00_in`, `qpll0outclk_out`, `qpll0outrefclk_out` and gains `qpll0clk_in`, `qpll0refclk_in`, `qpll1clk_in`, `qpll1refclk_in`, `gtwiz_reset_qpll0lock_in`, `gtwiz_reset_qpll0reset_out` (`ports_diff_common_outside_vs_inside.txt`): our own `GTHE4_COMMON` instance then exposes `QPLL0SDMDATA`/`SDM0TOGGLE` and the other dynamic pins. So the later loop-timing build takes the hand-instantiated QPLL path; this stage did not build it (stage 1 does not need it).

Attributes, bypass build against today's build** (`wrapper_attribute_diff.txt`: the generated `GTHE4_CHANNEL` wrapper; `netlist_attrs_rm_gp.txt` and `netlist_attrs_rm_gp_bypass.txt` (and `.full.txt`): `report_property` of the GTHE4_CHANNEL in each implemented build's post_route checkpoint, builds in `../builds/`).

**Implemented netlists agree with the wrapper** for every attribute that is a cell property: of the table above, TXBUF_EN, RXBUF_EN, TX_XCLK_SEL, RX_XCLK_SEL, TX_FIFO_BYP_EN, TX_PROGDIV_CFG, TX_PHICAL_CFG2, CLK_COR_*_LAT and the RXBUF_THRESH_* values are read back from the post_route checkpoints with exactly those values (the diff of the two `netlist_attrs_*.txt` is these and nothing else). The `*_VAL` entries and TXOUTCLKSEL are pin tie-offs in the wrapper, not cell properties, so the netlist shows them as pin connections instead. TXSYNC_MULTILANE, TXSYNC_OVRD, TXSYNC_SKIP_DA and the RX equivalents are 1'b0 in both builds; TXPHDLY_CFG0/1, TXDLY_CFG, RXDLY_CFG, RXPHDLY_CFG are identical in both. UG576 page citations for the meaning of each attribute are in `designs/b96_kr260_10g/docs/loop_timing_feasibility.md` (TX bypass p.135 to 142, 159 to 160; RX p.255 to 260, 270; UG576 v1.7.1 printed pages); this stage did not re-read them.

## Why brief 97's probe left an empty file
`results/b97/gt_bypass_probe.txt` is 0 bytes and its log was suppressed (`-nolog`). The script opened its output with `open $out w`, wrote with unflushed `puts` and closed the file only on the last line, so any Tcl error before that left an empty file and no message; the original error was never recorded and I could not recover it. The mistake not to repeat: no log, no flush, no per-step `catch`. These probes keep the Vivado log, flush after every line and catch each step (the identical `list_property ... -regexp` and `set_property` calls work in 2026.1).

## Reproduce
Needs Vivado 2026.1 and a heavy slot (an IP generate, about 1 minute each, under 3 GB):
```
cd results/b96f1/wizard_probe
for p in probe1 probe2 probe3 probe4; do vivado -mode batch -nojournal -log $p.log -source $p.tcl -tclargs .; done
# probe1: every Wizard property; probe2: the bypass properties, allowed alternatives, the fractional-N numerator side effect
# probe3: generates the design's core with buffers on and bypassed (ip_gen/, not committed); probe4: LOCATE_COMMON EXAMPLE_DESIGN (ip_gen4/, not committed)
# ports_*.txt and ports_diff_*.txt come from the .veo files; wrapper_attribute_diff.txt from the two *_gthe4_channel_wrapper.v files (sed gth_buf/gth_byp to a common name, diff)
vivado -mode batch -nojournal -source netlist_attrs.tcl -tclargs <build>/post_route.dcp netlist_attrs_<name>.txt     # after the two builds of ../builds
```
Files: `probe1.txt` (all properties), `probe2.txt` (bypass properties), `probe3.txt`, `probe4.txt` (what was generated), `ports_*.txt`, `wrapper_attribute_diff.txt`.
