# results/b126: 97C's three latency cuts plus the GT buffer bypass on the 10G link (brief 126); nothing ran on a board

Build `lat_all3_bypass` of `designs/b96_kr260_10g`: the default receive path (no rate matcher) with 97C's three logic cuts (`lat_all3`) **and** both GT elastic buffers bypassed (96F1, 96F1b). `lat_all3` was the fastest board run so far (tick-to-trade `L - E` = 26 clocks, about 161 ns) and `rm_gp_bypass` cut E by 4 clocks; this folder builds the two together, simulates the result, closes timing for the KR260 and writes down what the board should show, before any board time. The board script is written and not run.

## Why this build: the default receive path accepts the bypass
The question was whether a build without the rate matcher (`RATE_MATCH = 0`, 97C's receive path) can run with both GT buffers bypassed, or whether it needs `rm_gp` (the rate matcher) as `rm_gp_bypass` has. It can. What the default path assumes about the two clocks:
- Its PCS, MAC and trading decision run in RXUSRCLK2 (`rx_path_legacy.sv`) and hand the decision to TXUSRCLK2 through an `xpm_cdc_pulse` (the go pulse) and a quasi-static bus of order fields sampled five clocks after the pulse. That structure assumes only that the clocks are asynchronous and about equal in rate; it never relies on a phase relation or on the clocks being the same frequency.
- With the GT buffers on or bypassed, RXUSRCLK2 is the recovered clock in both: the Wizard keeps `RX_OUTCLK_SOURCE = RXOUTCLKPMA` when `RX_BUFFER_MODE` goes to 0 (`results/b96f1/wizard_probe/README.md`). What the bypass changes is TXUSRCLK2's source (`TXPROGDIVCLK`, the QPLL's own clock, instead of `TXOUTCLKPMA`; both the QPLL's 161.1328125 MHz) and what sits between the GT's internal clocks and the user clocks (the two FIFOs). The recovered-clock domain, the transmit domain and the crossing between them are the same.
- The rate matcher (`rm_gp`) exists to carry the receive stream into the transmit clock when a partner's frequency differs. The default path does not need it for that: the decision crosses as an event, not as a stream, and the receive counters live in the receive clock. So the bypass does not remove a requirement the default path was relying on.
- Evidence it works as a design (not a claim about the transceiver): the combined build links in simulation at four receive-clock phases with the bypass controllers' stand-in, sends 8 of 8 orders intact, and recovers from a hung alignment by the 96F1b retry; it meets timing and passes `report_cdc` with 0 critical rows and no waivers. Whether the real GTHE4 aligns and holds is the board test.
- What is **not** shown: behaviour against a partner with a real ppm offset (a loopback has none). Without a rate matcher, a ppm offset only changes how often each phase of the pulse crossing occurs; the pulse crossing's latency is therefore not a constant on a real link. The default path has always had this property.
So the fallback `rm_gp_all3_bypass` (rm_gp, the three cuts and the bypass) was not needed and was not built. It would also be a worse test of "do the two measured gains add": `rm_gp` carries 11 clocks of rate-matcher latency that `lat_all3` was designed to avoid.

## Latency definitions (the owner's rule: say very clearly what is measured)
All figures are clock counts of one free-running 32-bit counter in TXUSRCLK2 (161.1328125 MHz, one clock about 6.206 ns), taken inside the FPGA. **Nothing is measured at the pins**; no instrument looks at the fibre. The counter resolves one clock, so every figure is plus or minus 1 clock (6.2 ns). Medians below are medians over 100 link restarts of the per-link minimum, the way 96E, 96F1b and 97C quote them. Full treatment against STAC-T0 and wire-to-wire definitions: [`docs/latency_definitions.md`](../../docs/latency_definitions.md) (brief 109); the register-level definitions are in `designs/b96_kr260_10g/docs/design.md` sections 5 and 6.

| Quantity | Starts at | Ends at | What is on the path |
|---|---|---|---|
| **E** (echo) | the clock on which a probe frame's preamble word is in the transmit MAC's output register (TX start stamp) | the clock on which the same frame's first word (the destination address) is in the receive MAC's output register (RX start stamp) | transmit MAC, transmit PCS, GT transmit (phase FIFO and serialiser, or their bypass), the SFP+ module (both ways), the fibre (0.17 m: 0.83 ns), GT receive (CDR, deserialiser, elastic buffer or its bypass), receive PCS, receive MAC, and on the default path the pulse crossing that brings the RX start stamp into the transmit clock |
| **L** (loop) | TX start of a feed frame | RX start of the order frame the design sends back, in the same loopback | E once for the feed's trip out and in, **D**, and E once for the order's trip |
| **D** | RX start stamp of the feed | TX start stamp of the order (register TXV24; also **L - 2E**, not L - E, because the loop crosses the link twice) | receive MAC output, trading decision, the receive-to-transmit crossing, order builder, MAC preamble register. **No** GT, PCS or optics |
| **Tick-to-trade, board** | = **L - E**, minus the fibre's 0.83 ns | = E + D less the fibre: one trip through the transmit path, the link and the receive path, plus D | |

What "tick-to-trade (L - E)" means in plain terms: the time from the first bit of a market-data frame arriving at the transceiver's receive pins to the first bit of the order leaving its transmit pins, **plus the optical module's own delay** (unknown, not subtracted: the module sits inside E and therefore inside L - E). Written out, E = a_tx + O + a_rx (a_tx: the transmit stamp to the pin, O: everything between the two transceivers, a_rx: the pin to the receive stamp); L - E = a_rx + D + a_tx + O, whose first three terms are the pin-to-pin path. It is a **FIFO** latency (first bit in to first bit out) in STAC-T0's words, not the **actionable** latency (last bit of the data the decision needs to first bit out), and not the STAC-T0 headline's like-for-like figure. It does not include the 52.8 ns the price takes to arrive after the frame starts. The board's number differs from the simulation's: simulation tick-to-trade (below) counts from the GT word holding the price to the GT word holding the order's start block, with a zero-latency transceiver stand-in, so it leaves out the GT, the optics and the frame time before the price word.

**What the three cuts and the bypass each remove**
- Bypass (96F1b measured): the TX phase FIFO and serialiser path and the RX elastic buffer plus PMA-to-PCS path inside the GT, E by 4.0 clocks, twice in L (the loop crosses the transceiver twice), nothing in D.
- The three cuts (97C measured, `lat_all3` against the default build): the decision's fire event driven directly from the word-7 comparison instead of registered one clock later (`trade64.sv`), the order frame's MAC start taken from the go pulse itself, before the feed frame's FCS verdict is known (`tx_path.sv`; an order that should not go leaves with a poisoned FCS, so it is a bad frame, never a good wrong one), and the output register of the go-pulse crossing removed (`GO_REG = 0`). Together D fell from 10 to 6 clocks (L 50 to 46); E is unchanged.

## Known gaps and limits
- **No board result.** Every latency in the prediction rests on two earlier board runs and an additivity argument (the two changes act in different parts of the path). The one untested interaction is the default path's pulse crossing: its latency depends on the phase between RXUSRCLK2 and TXUSRCLK2, and the bypass changes how that phase is set at each lock; 96F1b tested the bypass with a rate matcher, not this crossing. D, and so L - E, is where a surprise would show.
- The transceiver in the simulations is a stand-in with no buffers: the bypass's saving cannot appear there (the simulated tick-to-trade is the same with and without it). The controllers' alignment time and what a real hang looks like are not simulated.
- The core cocotb bench cannot run the bypass core (Icarus has no `xpm_cdc_async_rst` model and the stand-in has no bypass ports) and its testbench does not pass `GO_REG`; the combined build's safety evidence is the xsim whole-core run (counters read back) plus the diff-based test that the bypass core differs from the base core only where 96F1 and 96F1b documented.
- Power is vectorless. A power measurement was not made.
- One board, one module, fibre loopback, no frequency offset, TX phase-interpolator ppm block powered down by the Wizard in the bypass configuration.
