# results/b140: why the debug build dbg_xvc failed six flow gates, and the flow fixes that clear them

Brief 140. Brief 131's debug build `dbg_xvc` of `designs/b96_kr260_10g` (the eyescan build plus a PS-AXI Debug Bridge and one ILA) failed six synthesis and placement stage gates while its routed timing passed. This folder holds the records of the rebuilt `dbg_xvc` with the fixed flow, of the parent `eyescan` build and the default build on the same flow (to show nothing else moved), and the Vivado evidence for each cause. Causes and fixes in full: `designs/b96_kr260_10g/dbg_xvc/docs/dbg_xvc.md`. No waiver file was written and no gate was loosened for builds without AMD debug IP.

## Records
- `builds/dbg_xvc/`, `builds/eyescan/`, `builds/default/`: for each build, `digest.json` (timing, utilisation, power, gates), `gates.json` (the gate record recomputed from the build's reports; per-crossing and per-pin lists cut to their first entries), `run.json` (wall time, memory, stamp), `stages.txt`, `tool.txt`, and `flow_lines.txt` (the lines the flow's fixes print: `FLOW-DEBUG-CORES-IMPLEMENTED`, `FLOW-DEBUG-RAM-CLOCK-DOMAINS`, `xpm_cdc:` and the stage times).
- `compare/other_builds_before_after.json`: the fields of `gates.json` that matter (gate verdicts, WNS, WHS, placement WHS, LUT, FF, exception counts, CDC structure summary) for `eyescan` and the default build before and after the flow change, and which gates changed in `dbg_xvc`.
- `evidence/place_hold_by_clock_pair.txt`, `evidence/place_worst_hold_path.rpt`, `evidence/routed_hold_same_endpoint.txt`: the placement-stage hold slack by clock pair, the worst placement-stage hold path with its clock tree, and the hold slack after routing, all from checkpoints of `dbg_xvc` (a first full run with `FDA_INSPECT_CKPTS=1`; the final run's gate record gives the same -2.723 ns).
- `scripts/`: the Vivado Tcl that made those records (`place_hold_groups.tcl`, `routed_hold_same_endpoint.tcl`, `ram_clock_domains_check.tcl`), and `collect_records.py` that copies a build's records here.

## Measured
- `dbg_xvc` with the fixed flow passes all 29 gates (16 post-synthesis, 1 post-placement, 10 post-route, bitstream, RTL): WNS 0.323 ns, WHS 0.011 ns, 8216 LUT, 17410 FF, 1.5 BRAM, the same as brief 131's run of the same sources (build stamp f4cdaac2 in both). Exactly six gates changed from fail to pass: `post_synth_no_unconstrained_endpoints`, `post_synth_methodology_no_critical`, `post_synth_cdc_structure_clean`, `post_synth_exceptions_clean`, `post_place_hold`, `exceptions_clean`.
- Wall time 1522.5 s, peak anonymous memory 9663 MiB (2 threads, MemoryMax 12G), against 1745.3 s and 9647 MiB in brief 131 (`compare/other_builds_before_after.json`).
- The `eyescan` build (WNS 0.314 ns, WHS 0.011 ns, 6395 LUT, 14545 FF) and the default build (WNS 0.04 ns, WHS 0.011 ns, 6215 LUT, 14192 FF, placement WHS -0.11 ns) have the same gate verdicts, timing, utilisation, exception counts and CDC summary before and after (`compare/other_builds_before_after.json`: `identical` true for both). In both, `implement_debug_core` did not run and the flow's own XPM exceptions were applied as before (`flow_lines.txt`: `single 0 hs 0 gray 0`).
- Placement-stage hold in `dbg_xvc`: -2.723 ns, all in the Debug Bridge's TCK clocks (174 failing endpoints in the divided-TCK domain, worst -2.576 ns, and 9 launched by the soft-BSCAN TAP clock, worst -2.723 ns); the design's own clocks are at -0.222 ns (`clk_u`), -0.140 ns (`txusr2`), -0.027 ns (`rxusr2`) and -0.038 ns (`clk_pl_0`). The worst path has 3.020 ns of clock skew: 4.994 ns of source clock delay through one BUFGCE, 9.025 ns of destination clock delay through that BUFGCE and a second one in the debug hub (`u_bufg_icon_tck`). After routing, the worst hold launched by the TAP clock is +0.422 ns and the worst inside the TCK domain +0.046 ns.
- Brief 131's counts, now explained: 1000 TIMING-17 Critical warnings and 1008 no-clock register pins at synthesis, 1000 of them behind the empty hub and 8 PS8 outputs with no load (0 and 8 after the fix), 2203 handshake crossings read as unsafe (AMD's CDC-15 waiver), 37 exception rows overridden by the flow's own copies and 12 more rows of AMD's own files that are ignored for benign reasons (11 XPM-scoped, listed as `EXC-IGNORED-XPM-SCOPED`; one in the Debug Bridge's `axi_jtag.xdc`, listed with the debug-IP rows).

## Reproduce
Take a heavy slot (Vivado, peak about 9.7 GiB for `dbg_xvc`, so MemoryMax 12G and no other Vivado job running), then `FDA_VIVADO_THREADS=2 MEM_MAX=12G flow/run_vivado.sh designs/b96_kr260_10g/dbg_xvc base` (and the same for `designs/b96_kr260_10g/eyescan` and `designs/b96_kr260_10g`). Re-evaluate a build directory with `python3 flow/gates.py designs/b96_kr260_10g/dbg_xvc/build/base`, copy the records with `python3 results/b140/collect_records.py dbg_xvc=designs/b96_kr260_10g/dbg_xvc ...`. The hold evidence needs `FDA_INSPECT_CKPTS=1` for the placed checkpoint and `scripts/place_hold_groups.tcl`. The unit tests of the changes are `flow/tests/test_140_debug_ip_gates.py` and `flow/tests/test_xpm_cdc_flow.py`.

## Known gaps and limits
- No board run: the ILA, bridge and Linux XVC server are as untested as in brief 131; only the flow gates changed.
- One run of each build under heavy machine load (load average above 12 for part of the time, which only lengthened the stage times). The three builds are as reproducible as the tool: `eyescan` and `dbg_xvc` gave the same WNS and WHS as brief 131's runs of the same sources, but run-to-run variation was not measured.
- The post-placement hold rule is split by clock name (clocks named for the Debug Bridge's TCK divider, its soft BSCAN TAP and the debug hub). No other design in the repository has the soft-BSCAN bridge, so there is no second design to show the same -2.7 ns pre-route estimate on; the ILA builds with the hard BSCAN show -0.176 ns. AMD documents no pre-route hold figure for this bridge-to-hub structure in the documents available here; the evidence is the clock tree of the worst path and the routed result.
- The Debug Bridge, the hub and the ILA are AMD's: the reset scan and the CDC structure check treat their internals as vendor IP (a crossing from our logic into them is still checked), and `CLOCK_DOMAINS` of the ILA's trace RAM is set to COMMON a step earlier than `opt_design` does it.
- Why Vivado applies AMD's scoped XPM constraint files in `dbg_xvc` and not in the parent builds was not determined (the build holds IP made from a block design, a PS8 and an ILA); the flow detects the situation from the exception list instead of from a cause.
- Both the hub implemented at synthesis and the flow's detection of AMD's XPM rows rely on Vivado 2026.1 behaviour measured here; the flow's version pin records the version of every build.
- Build IDs differ from brief 131's for the same sources (5ef847ff against 4a9ae66a in `dbg_xvc`) because the flow's Tcl is part of what the build ID hashes; the bitstream was not compared.
