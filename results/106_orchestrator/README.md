# results/106_orchestrator: derived constants, stale evidence and plan repeatability (brief 106)

Two small checks added to the check suite, and the three measurements that back them. Everything here is computed from committed records
(`benchmark/v2/runs/b82p2`, `b82p3`, and the build manifests under `results/`); no model was called and no Vivado run was made.

## What was added

| Piece | Where | What it does |
|---|---|---|
| `constants` check (rule `HDL-ORC-01`) | `flow/derived_constants.py`, `flow/checks/__init__.py` | Derives the shell design ID from the spec's quoted four-character string (ASCII, most significant first, `shell/PROTOCOL.md` register 0x00) and compares it with the `DESIGN_ID` binding of the `fpga_shell` instance (a literal, a string, or a name that resolves to a parameter or localparam). Also: a spec identity word that is in no RTL literal (advice), and `create_clock -period` on the board's oscillator port against the board file. Writes `build/derived_constants.json`. |
| `stale` check (rule `HDL-ORC-02`) | `flow/stale_check.py`, `flow/checks/__init__.py`, `agent/core/tools.py` | A build or simulation result is stale when an input hash differs from the record. A build's inputs are its manifest (`flow/manifest.py`); a stamp in `build/lineage.json` adds what the manifest does not hash (spec files, `project.yaml`, the board file) and, for `sim`, the tests and the model. The `build` and `simulate` tools stamp; the `gates` tool marks a result read from changed inputs as stale (`FDA_STALE=enforce` also makes it fail). A README or handover that cites a build ID must cite a current, fresh build. |
| plan-repeatability score | `flow/plan_repeat.py`, `analyse.py` | Scores the stage plan (the collapsed stage order) and a derived parameter across repeats of the same request. The RTL is never compared. |
| tests | `flow/tests/test_106_orchestrator.py`, `agent/tests/test_106_stale_tools.py` | Planted cases for each rule, the 82P3 back-test, the stale cases, the tool hooks. |

## Results (`results.md`, generated by `analyse.py`)

1. **82P3 back-test of the derived-constants gate.** The spec's quoted design ID "UEP1" derives 0x55455031. Four of the six runs bind the
   register-0 identity word 0x55445031 to the shell `DESIGN_ID`; the gate fails exactly those four (`CONST-ID-01`). It passes the one run that
   passed the hidden bench (B r1) and passes A r2, which binds the right value and fails for another reason (0 of 10; "never replies"). So
   the gate catches 4 of the 5 failed runs and flags none of the passing ones. It is one task, and the gate was written knowing the answer
   (see Known gaps in the report). The earlier ledger line that says all five failures used the wrong word is not what the RTL shows: A r2 did not.
2. **Stale check over recorded builds.** All 13 build manifests under `results/` are stale against the files in this checkout, because the flow
   Tcl and the designs have changed since (the build ID covers them, by design). This says history cannot be rebuilt from today's inputs; it does
   not say a published number is wrong. It is the reason a claim must cite a build that is current.
3. **Plan repeatability (82P2 + 82P3, 7 groups, 21 runs).** The stage order is the same in every pair that has a stage record (14 of 14), because the
   stage machine fixes it in code (`agent/graph/stages.py`); the full visit sequence, which includes the model-driven repair loops, is equal in
   6 of 14 pairs. The derived design ID is the same in 17 of 21 pairs, but only 14 of 21 runs bind the value the spec derives: all three
   82P2 UDP-endpoint runs repeated the same wrong word, so repeatability is not correctness. All runs stop at stage 2 (the benchmark's scope), so the
   later stages are not measured here.

## Records

- `results.md` and `results.json`: the three measurements, written by `analyse.py`.
- `analyse.py`: the script; reads only committed records.

## Known gaps and limits

- One task (UDP endpoint) for the back-test, and the rule was written after the failure was known: it shows the case would have been caught, not a rate on new tasks.
- All recorded runs stop at stage 2, so later stages are not in the repeatability numbers; stage order is fixed by code, so its 14/14 is expected.
- The constants gate derives only the design ID, advisory identity words and the board clock period. Register addresses, field widths and prose constants are not derived.
- The stale check covers hashed files, not tool binaries, the KB pin or most environment switches (`HOLES` in `flow/stale_check.py`). Enforcement is off by default (`FDA_STALE=enforce`).

## Reproduce

No access key, Vivado, board or model call is needed.

```
python3 results/106_orchestrator/analyse.py                      # rewrites results.json and results.md from the committed records
python3 -m pytest flow/tests/test_106_orchestrator.py agent/tests/test_106_stale_tools.py -q
python3 -m flow.derived_constants designs/<d>                    # the constants check on one design (exit 1: a blocking finding)
python3 -m flow.stale_check check designs/<d>                    # fresh or stale, and which inputs changed
python3 -m flow.checks designs/<d> --names constants,stale       # the same through the check suite
```

The stale-manifest table (result 2) depends on the checkout: it is re-computed, not frozen, so a later flow change changes it.
