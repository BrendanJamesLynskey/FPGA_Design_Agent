# 125 Lean evidence tier: records

Records of brief 125. The tier itself (the `formal_lean` method of the traceability matrix, the frozen-statement gate, the RTL-link tiers, the `proof` model purpose and the proof
driver) is documented in [docs/traceability_v1.md](../../docs/traceability_v1.md#lean-proofs-formal_lean-brief-125); the Lean project is [formal/lean](../../formal/lean/README.md).

## Records

The table below lists the files; the sections after it give the gray-code run, the cross-check and the build record.

## The gray-code lemma, proved by the model through the driver

`formal/lean/Gray/Spec.lean` states, for every width `n > 0`: consecutive gray codes (the counter steps by one and wraps from 2^n - 1 to 0) differ in exactly one bit
(`gray_step`); the decoder inverts the encoder (`gray2bin_bin2gray`) and the encoder inverts the decoder (`bin2gray_gray2bin`); and a code sampled mid-step, that is the old or the new
code, decodes to the old or the new count (`gray_sample`). The encoder and decoder are the ones of AMD's `xpm_cdc_gray`, which `designs/b96_kr260_10g/rtl/rate_match_gp.sv` instantiates for
both pointers; the Lean text is a manual transcription of the repository's behavioural model of that macro (`flow/cdc_models/xpm_cdc_models.sv`, lines 71-87), not of AMD's source.
**The statements are written by the executor and are left for the owner's approval** (`designs/b96_kr260_10g/verif/lean_approvals.yaml` has no entries). Before the model saw them they were
tested exhaustively in Lean (`#eval`) for widths 1 to 10, all values.

(purpose `proof` of the 108 table: Claude Code, `claude-sonnet-5-5`, effort medium, no tools, 1500 s per call). One run, one model.

**First try against after feedback.** The model's first try did not build: one unsolved goal in the proof of `gray_step`. With the checker's message it fixed that step in the second round. All
four theorems then build with the kernel alone: `#print axioms` lists only `propext`, `Classical.choice` and `Quot.sound` (tier "kernel only"). Total model time 522.2 s (about 8.7 minutes); builds
28.0 s. Plan cost estimates 0.744 and 0.152 (a plan estimate, not a charge). The proof file is 375 lines (the spec was 55 lines), most of it helper lemmas; several steps are written as `first | ... | ...`
alternatives (the model hedged between lemma names it was not sure of); they build, and are a style to tidy, not a gap. `tools/statements.py` confirms that no definition and no statement
changed ("statements identical (helper lemmas allowed)").

## The cross-check of the transcription

`formal/lean/Gray/CrossCheck.lean` (generated by `formal/lean/tools/crosscheck_gray.py`) has 1020 `#guard` lines: for widths 1 to 8 and every value, the Lean encoder and decoder are compared with
the gray value the repository's behavioural model of `xpm_cdc_gray` registers, and the binary value it decodes, in Icarus Verilog 12. A wrong expected value fails `lake build` (tested by editing one).
This tests the Lean text against the repository's model, not AMD's macro. A test (`flow/tests/test_125_lean_tier.py`) regenerates the file and compares it with the committed one when `iverilog` exists.

## The build record

`formal/lean/records/build_record.json`, written by `python -m flow.trace_v1 lean-record`: Lean 4.36.0, build succeeded, the SHA-256 of every Lean file, of each of the ten theorems' statements and
definitions and of the transcribed RTL lines, and each theorem's axioms and tier (7 kernel only, 3 using `bv_decide`: the three checksum theorems 124 already reported). Where Lean is not installed
(CI), the matrix reads this file and says "recorded build (not re-run)".

## Reproduce

Install Lean through elan (the toolchain file selects 4.36.0), then run these commands from the repository root; the model call needs the access key in `.env` and spends plan usage.

```
export PATH=$HOME/.elan/bin:$PATH
python3 formal/lean/tools/crosscheck_gray.py          # regenerate Gray/CrossCheck.lean (needs iverilog)
cd formal/lean && lake build                          # builds Cksum and Gray, runs the 1620 #guard lines
python -m flow.trace_v1 lean-record                   # rewrite the hash-pinned record (needs the toolchain)
python -m flow.trace_v1 write && python -m flow.trace_v1 check
python3 formal/lean/tools/prove.py --module Gray.Spec --theorem gray_step ... --out <dir>   # a new proof run (a model call on the plan; needs the access key)
```

## Known gaps and limits

- One run, one model, one statement set: the first-try and feedback figures are one observation.
- The Gray statements are the executor's and are **not approved**; `lean_approvals.yaml` is empty. Nothing in the matrix counts them as verification.
- The Lean encoder and decoder are a transcription of the repository's model of `xpm_cdc_gray`, tested against that model in simulation; AMD's own macro is not compared, and the synchroniser flops, clocks and metastability are not modelled.
- The proof file has `first | ... | ...` hedges and unused-argument linter warnings; tidying is left for a human.
- The record is a record: CI reads it and does not re-run Lean. A change to any Lean file needs `lean-record` and a commit of the new record, or the items show as stale.
- `rtl_generated` (a Lean model generated from the RTL) is in the schema and is claimed by no item: no generator exists.
