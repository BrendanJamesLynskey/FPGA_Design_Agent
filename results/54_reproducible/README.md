## Results

**Same sources, same settings, different directories: the configuration data is identical.**

| Pair | Bytes that differ | Where | Why |
|---|---|---|---|
| T1 A/B | 4 (file bytes 216-217, 219-220) | `.bit` header field `d` | the time `write_bitstream` ran (`02:28:05` / `02:31:42`: minutes and seconds) |
| c13 A/B | 3 (bytes 220, 222-223) | header field `d` | the same (`05:22:55` / `05:29:04`) |

Everything after the header (from the sync word on) is byte-identical, the configuration CRC recomputed from the
packets matches the file's CRC words in every build, the placement and routing hashes are equal, and the routed timing
summary and utilisation reports differ only in their headers (date, the `-file` path in the command line, and the
header box border, which is as wide as that line). The date field `c` was the same because all builds ran the same day;
it would differ otherwise. Nothing was masked to get this result: the date and time are the only differences.

**Thread count (1, 2 and 4) changed nothing in the result.** T1 at 1, 2 and 4 threads and c13 at 1 and 4 threads gave
the same placement and routing hashes, the same timing and utilisation reports (below the date), and the same frame
data. The bitstreams differ only where the build ID is, because the build ID includes the thread count:

| Pair | Bytes | What |
|---|---|---|
| T1 4 vs 1 thread | 84 | the USR_ACCESS word (4 bytes at 331-334: `DEDB2BF7` / `D46AB04E`); the CRC word after the frame data (4 bytes at 659739-659742), which covers that write (recomputed: matches in both files); header `SW_CRC` and `SW_HDR_SHA256` (bytes 92-99, 115-178); the time |
| T1 4 vs 2 threads | 80 | the same places (a few digest characters happened to coincide) |
| c13 4 vs 1 thread | 81 | the same places (USR_ACCESS at 334-337, CRC at 1631898-1631901, header digests, time) |

`SW_CRC` and `SW_HDR_SHA256` are fields Vivado 2026.1 writes into the header's design-name field (2025.2 bitstreams on
this PC carry only `SW_CRC`). We did not reproduce how they are computed (not the SHA-256 or CRC-32 of the configuration
data or of the header bytes we tried), so they are reported, not explained beyond what was observed: they were equal in
every pair whose configuration data was equal and different in every pair whose data differed. Wall time fell from
508 s (1 thread) to 372 s (4 threads) on c13; peak anonymous memory was 2.3-2.4 GB at both.

So in this flow on Vivado 2026.1 the thread count is safe to vary, as brief 33 found for placement and routing on 2025.2.
The flow still hashes it into the build ID, so two bitstreams built at different thread counts carry different IDs;
whether to drop it from the ID is a follow-up for the planner.

**One comment line changed (T1 M against A).** The manifest's input hash for `dimmer_counter.sv`, the build stamp
(`dfd4624e` to `ac6c157c`), the build ID (`dedb2bf7` to `635312ca`) and the bitstream all changed. The comment changed
the netlist too: `BUILD_STAMP` is a constant in the shell, so synthesis, placement and routing differ (placement and
routing hashes differ; 493 instead of 487 LUT; WNS 4.003 instead of 3.609 ns), and the compressed bitstream is a
different length (582,659 against 661,839 bytes). Gates passed on both.

## The board

`board/`: T1 `t1_A_t2` (build ID `89315dac`) programmed into SRAM on the Nexys A7-100T on 2026-11-12, under
`_handoff/board.lock`:

- JTAG: `REGISTER.USR_ACCESS` read `89315dac`, equal to the manifest's build ID (`program.json`, `build_id_jtag`).
- UART: the shell's `BUILD_STAMP` read `dfd4624e`, equal to the manifest's `settings.build_stamp` (`uart.json`).
- The T1 hardware tests: 8 passed (`hw_tests.txt`).
- Operating conditions at programming time (XADC over JTAG): 25.5 C, VCCINT 1.006 V, VCCAUX 1.794 V, VCCBRAM 1.006 V;
  latched min/max since configuration 24.98-26.09 C, VCCINT 1.0049-1.0071 V, VCCAUX 1.7805-1.7952 V, VCCBRAM
  1.0042-1.0071 V; alarm flags 0000; **inside** the Artix-7 -1 recommended operating conditions (DS181 table 2) and the
  board's 85 C limit. The XADC samples at about 1 MSPS across channels, so it cannot see nanosecond droop.
