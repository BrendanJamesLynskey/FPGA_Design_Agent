# Reproducible builds: measurements (Vivado 2026.1)

Do two builds of the same commit give the same bitstream, does the thread count matter, and does a one-line change
show up? Vivado 2026.1 (Basic licence tier), non-project flow, on a desktop workstation (4 cores, 32 GB); each build
fresh (`FDA_BUILD_CACHE=0`, no cache), memory capped at 6 GB. The method is in
[docs/reproducibility.md](../../docs/reproducibility.md), which also defines the terms used here (manifest, build ID,
build stamp, USR_ACCESS, CRC). Every number below is in [results.md](results.md) and `results.json`, generated by
`compare.py` from the builds' records.

Reproduce: run `repro.sh <jobs file> <raw dir>` (one fresh build per line: label, checkout, design, threads), then
`compare.py <raw dir>`.

## Builds

Three checkouts of the same commit (`41264bf`), in three different directories (one of them three levels deeper, with a
different folder name): A and B clean, M with one changed comment line in `designs/t1_dimmer_counter/rtl/dimmer_counter.sv`.

| Label | Design | Checkout | Threads | Build ID |
|---|---|---|---|---|
| `t1_A_t4`, `t1_B_t4` | T1 (487 LUT) | A, B | 4 | `dedb2bf7`, `dedb2bf7` |
| `t1_A_t1`, `t1_A_t2` | T1 | A | 1, 2 | `d46ab04e`, `89315dac` |
| `t1_M_t4` | T1, one comment line changed | M | 4 | `635312ca` |
| `c13_A_t4`, `c13_B_t4` | c13 Harris VGA, course reference (11,281 LUT, 14 block RAM tiles, 9 DSP) | A, B | 4 | `23d2f095`, `23d2f095` |
| `c13_A_t1` | c13 | A | 1 | `a530c2b3` |

The build IDs are those of commit `41264bf`. Flow files that are inputs of every build (`build.tcl`, `prepare.py`,
`vhdl.py`) have changed since, so T1 at that thread count gets a different ID at the current head; the IDs here, and the
sample bundle's, will not reappear there. c13 was built from a staging copy outside version control, so its manifests
report `dirty: true` (the six staged files are listed under `inputs_untracked`); the comparison does not depend on that.

## Results

**Same sources and settings, different directories: identical configuration data; only the header's time bytes
differ.**

| Pair | Bytes that differ | Where | Why |
|---|---|---|---|
| T1 A/B | 4 (file bytes 216-217, 219-220) | `.bit` header field `d` | the minutes and seconds of the time `write_bitstream` ran |
| c13 A/B | 3 (bytes 220, 222-223) | header field `d` | the same |

Everything from the sync word on (the fixed pattern that starts the configuration data after the file header) is
byte-identical. The configuration CRC recomputed from the packets matches the file's CRC words in every build, the
placement and routing hashes are equal, and the routed timing summary and utilisation reports differ only in their
headers (the date, the `-file` path in the command line, and the header box border, which is as wide as that line). No
field was masked. The date field `c` was equal only because both builds of each pair ran on the same day; it would
differ otherwise.

**Thread count (1, 2 and 4) changes only the words that carry the build ID, nothing else.** T1 at 1, 2 and 4 threads
and c13 at 1 and 4 threads gave the same placement and routing hashes, the same timing and utilisation reports (below
the date), and the same configuration frames. The bitstreams differ only where the build ID is, because the build ID
includes the thread count:

| Pair | Bytes | What |
|---|---|---|
| T1 4 vs 1 thread | 84 | the USR_ACCESS word (4 bytes at 331-334: `DEDB2BF7` / `D46AB04E`); the CRC word after the frame data (4 bytes at 659739-659742), which covers that write (recomputed: matches); the header digests `SW_CRC` and `SW_HDR_SHA256` (bytes 92-99, 115-178); the time |
| T1 4 vs 2 threads | 80 | the same places (a few digest characters happened to coincide) |
| c13 4 vs 1 thread | 81 | the same places (USR_ACCESS at 334-337, CRC at 1631898-1631901, header digests, time) |

`SW_CRC` and `SW_HDR_SHA256` are fields Vivado 2026.1 writes into the header's design-name field. We did not reproduce
how they are computed (they are not the SHA-256 or CRC-32 of the configuration data or of the header bytes we tried), so
they are reported, not explained beyond what was observed: they were equal in every pair whose configuration data was
equal and different in every pair whose data differed. On c13, wall time fell from 508 s (1 thread) to 372 s
(4 threads); peak anonymous memory was 2.3-2.4 GB at both.

So for this flow, on these two designs, the thread count is safe to vary. The flow still hashes it into the build ID,
so two bitstreams built at different thread counts carry different IDs; dropping it from the ID is a possible follow-up.

**One comment line changed (T1 M against A).** The manifest's input hash for `dimmer_counter.sv`, the build stamp
(`dfd4624e` to `ac6c157c`), the build ID (`dedb2bf7` to `635312ca`) and the bitstream all changed. The comment changed
the netlist too: the build stamp is a constant in the test shell, so synthesis, placement and routing differ (placement
and routing hashes differ; 493 instead of 487 LUT; WNS 4.003 instead of 3.609 ns), and the compressed bitstream is a
different length (582,659 against 661,839 bytes). Gates passed on both.

## The board

`board/`: T1 `t1_A_t2` (build ID `89315dac`) programmed into SRAM on a Nexys A7-100T:

- JTAG: `REGISTER.USR_ACCESS` read `89315dac`, equal to the manifest's build ID (`program.json`, `build_id_jtag`).
- UART: the build stamp read `dfd4624e`, equal to the manifest's `settings.build_stamp` (`uart.json`).
- The T1 hardware tests: 8 passed (`hw_tests.txt`).
- Operating conditions from the on-chip sensor (XADC, over JTAG), at programming and again about an hour later with the
  same bitstream loaded: temperature 24.7-26.5 C, supply rails within 1.1 % of nominal, no alarm flags, inside the Artix-7
  -1 recommended operating conditions (DS181 table 2) and the board's 85 C limit. The values, including the minimum and
  maximum the sensor latched in between, are in `program.json` and `conditions_end.txt`. The sensor samples at about
  1 MSPS across channels, so it cannot see nanosecond supply droop.

## Sample release bundle

`sample_bundle/t1_dimmer_counter_base_89315dac/`: `flow/release.py make` on the `t1_A_t2` build (clean checkout). CI
runs `flow/release.py check` on it.

## Files

| File | What |
|---|---|
| `repro.sh` | runs one jobs list (label, checkout, design, threads), one fresh build at a time, copies each build's records |
| `compare.py` | the pairwise comparison; writes `results.md`, `results.json` and `raw/<label>/` with the checkout paths, home directory and host name replaced (`$TREE_A`, `$HOME`, `<host>`) |
| `conditions.tcl` | sensor conditions over JTAG (now, latched min/max, flags) and USR_ACCESS, read-only |
| `raw/<label>/` | each build's `manifest.json`, `run.json`, `gates.json`, `result_hash.json`, `stages.txt`, `tool.txt`, `rc.txt` (no bitstreams, no reports) |
| `board/` | the read-back records (cable serial removed) |
| `board_shell11/` | a separate fresh T1 build with the protocol 1.1 shell, its read-back over JTAG and the UART, and 8 of 8 hardware tests (its own README) |
| `sample_bundle/` | the sample release bundle described above |

## Reproduce

    results/54_reproducible/repro.sh <jobs file> <raw dir>     # one fresh Vivado 2026.1 build per line, run one at a time
    python3 results/54_reproducible/compare.py <raw dir>       # results.md, results.json, raw/<label>/

Each jobs-file line is `<label> <tree> <design dir> <threads>`, where each `<tree>` is a clean checkout of the same commit in a
different directory. A rerun needs Vivado 2026.1, a heavy slot and nothing else building (about 6 GB each). The board records
need a Nexys A7-100T attached and `conditions.tcl`; they cannot be regenerated from the committed files. The build IDs here are
from commit `41264bf` and will not reappear at the current head. The jobs file used is not committed.

## Known gaps and limits

- Two designs (T1 and the c13 course reference) and one commit; one build per label, so only equality or difference of single builds is shown.
- `SW_CRC` and `SW_HDR_SHA256` were not reproduced from the file bytes: they follow the configuration data in every pair, which is all that is known.
- The build ID includes the thread count although varying it was measured harmless; whether to drop it is undecided.
- c13 was built from an untracked staging copy, so its manifests say `dirty: true`.
- The board read-back is one board; the sensor cannot see nanosecond supply droop, and the shell 1.1 record's latched minimum and maximum cover only the time up to programming, not the test window.
- UltraScale+ and Zynq PS-loaded USR_ACCESS behaviour is documented, not measured. The sample bundle has no traceability matrix or review pages.
