### 2.2 The stand-in common block (`standin/gtf_common_standin.v`, test `standin/tb_standin.sv`, log `standin/tb_standin.log`)
`GTF_COMMON_STANDIN` is our own behavioural model, written from public documentation (UG576 chapter 2: Equation 2-3 PLL output frequency = reference x N / M, Tables 2-12 and 2-13, and the port descriptions of the QPLL reference selection, reset, power-down and lock). No AMD source was copied or decompiled; only the primitive's port names are used.
- **What it does:** selects the reference clock by QPLLnREFCLKSEL (001 GTREFCLK0 ... 111 GTGREFCLK), measures its period, and after reset release (and power-down release) plus 256 reference cycles raises QPLLnLOCK; drives QPLLnOUTCLK at reference x N / M (N from the attribute QPLLn_FBDIV as the Wizard sets it, M from QPLLn_REFCLK_DIV; the QPLLnFBDIV port is "reserved, set to 0" in UG576) with 50 % duty; QPLLnOUTREFCLK is the selected reference. Reset or power-down drops lock and stops the clock low. DRP answers with DRPRDY one DRPCLK after DRPEN and reads zero.
- **What it does NOT model:** jitter, real lock time, VCO band choice, fractional-N (SDM), calibration, DRP registers, rate switching, refclk-lost and feedback-lost detection (flags stay 0), the monitor outputs (0), any difference between the two PLLs. Validity: integer N and M only, the settings of AMD's two benchmark designs (N = 64, M = 1, 161.1328125 MHz reference, 10.3125 GHz output).
- **Small test (requirement 2):** `tb_standin.sv` checks lock stays low in reset, lock rises 255.4 reference cycles after release, output edges over 1000 reference cycles equal 64.000 x (QPLL0, N = 64) and 66.000 x (QPLL1, N = 66) the reference, power-down drops lock and the clock, and re-lock works: `PASS` (`standin/tb_standin.log`).
- **Wiring into AMD's design:** only the instantiation line of the example's common wrapper (`rtl/imports/gtfwizard_raw_gtf_common.v`) is changed to instantiate `GTF_COMMON_STANDIN` with the four N/M parameters (`raw_sweep/gtf_common_instance.diff`). The GTF channel is AMD's own unmodified `GTF_CHANNEL` with its encrypted secure model, fed by the stand-in's clocks.
- **Cap check (requirement 2):** the full RAW design now simulates under the Basic tier (no instance-cap error; run in 2.3).

### 2.3 RAW Synchronized benchmark with the stand-in: simulated with a stand-in common block
Set-up: AMD's unchanged RTL and testbench logic (the `ul3524` commit above), project built on a K26 part for IP generation, IP scripts' version gate and `upgrade_ip` as above, debug cores stubbed (`sim_attempt/stubs_dbg.v`), the common block replaced as in 2.2. AMD's own formula is used: `LATENCY = (RCVD - SENT) - 6.5` clocks, times 1.5515 ns (`VNC_LATENCY_CLK_PERIOD_NS` in AMD's testbench).
- **Default run (`raw_run1/`)**: link achieved at 140.8 us, 10 records, every one **1.500 clocks = 2.33 ns**; AMD's testbench PASS (link maintained 50 us).
- **16-run sweep (`raw_sweep/`, `summarise_sweep.py`)**: the reference-clock start offset (0 to 5600 ps in 800 ps steps), the 300 MHz system clock start offset (0 and 1111 ps) and the delay before the system reset (1007 to 1112 reference cycles) were varied through three plusargs added to the testbench copy (`raw_sweep/sim_clk_reset.diff`, `sim_top.diff`; default values give AMD's shipped behaviour). 16 runs, 160 records: **min 1.50, median 1.50, max 1.50 clocks; spread 0.00; = 2.33 ns** in every run.
- **TX/RX user-clock phase scan (`raw_phase_scan/`)**: the txusrclk output phase of AMD's MMCM was changed from its shipped -180 degrees to -135, -90, -45, 0, 45, 90 and 135 degrees by editing the generated clock-wizard source (one run each, 10 records each): **1.50 clocks in all seven**; the counter readings shift by a count between phases (27404 or 27405 for the first record) but the corrected latency does not.
- **Compared with AMD's measured 2.34 ns (RAW):** the simulated 2.33 ns equals 1.5 clocks of 1.5515 ns (the 0.01 ns difference from AMD's 2.34 ns is of the order of the rounding of the clock period; the testbench uses 1.5515 ns for 644.53125 MHz, and AMD's page does not state which period its hardware figure used). So the simulation reproduces AMD's RAW figure to the resolution of the method, **simulated with a stand-in common block**.
- **What this does not show:** AMD says the hardware figure moves with the TX/RX phase after each GTF reset and that the minimum over repeated runs is quoted. The simulation shows no spread at all, over reset timing, reference offsets and a scan of the MMCM phase. The secure GTF model and our stand-in have no random lock/alignment phase, so the zero spread is a property of the model, **not evidence that hardware has none**. The minimum of the simulated distribution equals the median.
- **Cost:** about 2.7 to 3.2 minutes of wall time per run (one thread, 6 GB cap), heavy slot prefix "186:".

### 2.4 MAC Synchronized benchmark with the stand-in: **no result; block lock was never reached**
Same method as 2.3 on `GTFMAC_Latency_10G_Sync` (stand-in dropped into the testbench folder, instantiation change in `mac_attempt/gtf_common_instance.diff`, K26 part, plusargs for the two clock start offsets in `mac_attempt/gtfmac_vnc_tb.diff`, no waveform recording, `macrun.sh`). IP generation and elaboration work and the design fits under the instance cap. The testbench then runs its start-up (PLL lock at 1.6 us, reset-done flags at 7.3 and 9.0 us, near-end loopback configured at 9.6 us, "Waiting for VNC to detect block lock" at 10.08 us) and **stays in the block-lock polling loop for 2.2 ms of simulated time (about 43 minutes of wall time; an earlier attempt with waveform recording ran 21 minutes and was stopped) with no "Block lock found"** (`mac_attempt/mac_r1.out`; I stopped it, stopping only my own systemd scope). RAW linked at 140.8 us with the same stand-in, so the clock source is adequate for RAW. The cause for MAC is **not established**: candidates are (a) something the stand-in lacks that MAC mode needs (it does not model, for instance, the DRP-visible common registers or a lock-time profile), (b) the receive alignment in this model needing a phase the testbench reaches only with AMD's own common-block timing, (c) the testbench's 100,000-attempt polling loop simply being much slower than I could wait. None was tested; a run with a trace of the GTF's own lock and alignment signals would separate them. So **there is no simulated MAC latency, no MAC distribution, and no comparison with AMD's 5.44 ns**; the 5.44 ns remains untested here.

## 3. Measurement methods side by side (task 3)
AMD figures are as published on the repository's pages (a hardware result: MAC 5.44 ns, RAW 2.34 ns, base GTF 10G, near-end loopback, minimum over repeated runs). Ours are from reports 126, 169 and `docs/latency_definitions.md` (KR260, 10GBASE-R via GTH, SFP+ module and 0.17 m fibre; counters inside the FPGA).

| Aspect | AMD GTF benchmark (UL3524) | Ours (KR260, `lat_all3_bypass`, board run A of brief 126) |
|---|---|---|
| Quantity | One-way TX to RX through the transceiver only | E (frame out to same frame in, one link trip); L (feed out to order in); D = L - 2E (decision, receive stamp to transmit stamp); tick-to-trade (board) = L - E - fibre |
| Start event | TimeTx: TX data latched by the GTF on TXUSRCLK (RAW: sync pattern word presented on the TX raw interface; MAC: `TX_AXIS_TCAN_START` accepted) | TX start stamp: preamble word in the MAC output register, in TXUSRCLK2 |
| End event | TimeRx: the RXUSRCLK edge where the GTF launches the data into the fabric (RAW: sync pattern word launched on the RX raw interface; MAC: `RX_AXIS_TSOF`); the benchmark samples it one RXUSRCLK later and backs out one cycle | RX start stamp: receive MAC start strobe (first word, destination address, in the MAC output register) |
| On the path | GTF PMA and PCS to the fabric boundary; in MAC mode also the gearbox (33-cycle loop) and MAC block; near-end internal loopback | E: MAC, our PCS and gearbox (fabric), GT transmit, SFP+ module, fibre, GT receive (CDR, buffers or bypass), PCS, MAC to the stamp. Our GT is in RAW 64-bit mode with the PCS written in fabric (`design.md` 2.2) |
| Excluded | Framing and protocol overhead, PL logic, TX interface setup, RX clock-to-out, package flight (as stated on the AMD page) | Nothing on the link; the optics' own delay is inside the figure and not subtracted |
| Clocks | TXUSRCLK and RXUSRCLK both about 644.53 MHz (1.5515 ns in the testbench), set 180 degrees apart by an MMCM; GTF in near-end loopback | One 161.1328125 MHz clock (6.2058 ns) for the stamp counter; link to a transceiver on the same board, loop-timed through fibre; receive clock recovered |
| Counter | One free-running counter in the RXUSRCLK domain; the TX event crosses into it through a 3-cycle synchroniser; the RX event goes through an identical synchroniser | One free-running 32-bit counter in TXUSRCLK2; the RX decision crosses RXUSRCLK2 to TXUSRCLK2 by a pulse crossing (our `D` includes it) |
| Resolution | One counter clock at 644.53 MHz (1.55 ns) before the adjustment | One clock at 161.13 MHz (6.21 ns) |
| Adjustment | `LATENCY = ABS(RCVD - SENT) - ADJ_FACTOR`; ADJ_FACTOR 6.5 clocks (RAW) or 0.5 (MAC) (half a cycle added back for the 180 degree phase) | None beyond the stated definitions (L - E - 0.83 ns fibre) |
| Statistic | Minimum over repeated runs ("may require running the benchmark multiple times to observe the minimum"); Min/Avg/Max shown in simulation | Median of per-link minima for E and L (100 restarts), plus means (run A: per-link L - E 23.77 clocks, 147.5 ns mean; median-based 24 clocks, 148.1 ns net of fibre) |
| Phase effect | Latency varies with the TX/RX user-clock phase, which can change at every GTF reset; the benchmark fixes the phase to cut the variation. MAC mode also varies with the position in the 33-cycle gearbox loop | Our D came out 8 against a predicted 5-7 (brief 126); brief 169 shows most of the miss is the median method (the same run's register D averaged 7.19) and finds a routing-delay hypothesis on the go-pulse crossing, not measured on the routed design |

Arithmetic on the published numbers (derived, not measured here): at 1.5515 ns per clock, 2.34 ns is about 1.5 clocks and 5.44 ns about 3.5 clocks; the clock is four times faster than ours, so one of our clocks is 6.2058 ns.

**The parallel.** In both, a result that is a small number of clocks moves with a phase relation that is re-drawn at every reset: AMD's TX/RX user-clock phase (and gearbox position), our receive-to-transmit crossing phase (D). Both therefore report a distribution or a minimum over resets, never a single run.

**No headline comparison of 2.34 ns with our 148 ns.** They measure different paths: AMD's is the GTF block alone, between two fabric-side events at the boundary, loopback inside the device, with PL, framing and package excluded; ours is a full link trip including the module, the fibre, the receive CDR, our own PCS and MAC in fabric, and (for tick-to-trade) the order logic. A like-for-like comparison would need (a) our transceiver path measured between the same two fabric-side events (our `a_tx` and `a_rx`, which we cannot separate today: E = a_tx + O + a_rx), for example from an internal near-end loopback build with the stamp points at the transceiver ports, and (b) the clock phases fixed or the distribution over resets reported, and (c) a counter fast enough: a 161 MHz counter cannot resolve a 2.34 ns figure. The same point is made for STAC-T0 in `docs/latency_definitions.md`.

## 4. What we could adopt (task 4; proposals only, ranked)
1. **Report the distribution over resets next to the minimum, and name the phase.** AMD's page says the base figure is a minimum and that it moves with the phase. We already take 100 restarts per run; add the minimum, median and spread of E, D and L - E in every board report, labelled with the reset count. Cost: reporting only (the records exist). Lowest risk, directly serves the open D question.
2. **A phase probe for our own crossing.** AMD fixes the relation with an MMCM and syncs events through an identical synchroniser on both legs. Ours cannot fix the receive phase (recovered clock), but a fabric phase detector (sample RXUSRCLK2 against TXUSRCLK2 at a finer clock or with a delay-line measurement) per lock would let the board's per-lock D be sorted by phase, testing brief 169's hypothesis. Cost: a small build and a board visit; not a new architecture. Ranked second because it needs the board.
3. **Free-running-counter latency monitor in the AMD style as a second instrument.** AMD's block is a single counter capturing both events through matching synchronisers, with FIFOs read over AXI. Ours is the same idea; the difference worth borrowing is the matched synchroniser on the *start* event (so a crossing penalty cancels in the difference) and the one-clock back-out written down. Cost: a few hundred LUTs and a rewrite of one stamp path; benefit uncertain, do only if proposal 2 shows the stamp crossing itself adds jitter.
4. **RAW-like bypass on the GTH.** UG576 has no GTF-style RAW user mode; what it offers for lowest GTH latency is a set of bypasses. Cited from the guide: the TX buffer must be bypassed if latency is critical, and TX phase alignment "uses fewer registers in the TX datapath to achieve lower and deterministic latency" (Chapter 3, TX Buffer, Table 3-17, "TX Buffering versus Phase Alignment"; TX Buffer Bypass, Chapter 3); RX Buffer Bypass (Chapter 4); the 8B/10B encoder and decoder bypass "reduces latency" (Chapter 3 TX 8B/10B Encoder and Chapter 4, 8B/10B decoder attribute and port descriptions); the comma-detect and alignment circuit can be bypassed with RXCOMMADETEN = 0, which "reduces RX datapath latency" (Chapter 4, port description of RXCOMMADETEN; the exact section title was not checked); the TX and RX synchronous and asynchronous gearboxes are optional blocks (Chapters 3 and 4). Not bypassable in what I read: the PMA (serialiser, CDR, equaliser). We already use the Wizard's RAW 64-bit user mode with our PCS in fabric (`design.md` 2.2) and both buffer bypasses (96F1b, 126; AR 68177's 3.4 to 4.4 clock figures are quoted in brief 126). What remains is the internal data width (Table 3-1, TX_DATA_WIDTH and TX_INT_DATAWIDTH, 32-bit and 64-bit internal rows) and any further GT-internal registers, which UG576 does not tabulate; the AR 68177 latency values are the place to read the exact figures. Cost: a Wizard variant and a build; the saving of a narrower internal width is unmeasured, so no estimate is given. I could not confirm in UG576's text what GTF does differently in RAW mode (the GTF is a different transceiver with its own guide, not in `_amd_docs`).
5. **Target the VU2P in out-of-context studies of the order path.** Refused on this PC (section 1). Cost: a licence tier that covers the device (owner decision) or a cloud image that has one; the gain is timing at -3 speed on UltraScale+ fabric, a different fabric from the K26's -2 part, so results would be an upper-end comparison, not our board. Lowest rank until the licence question is decided.
6. **FINN_Latency as the RTL + ML reference.** AMD's page reports 115.748 ns, which the page converts to 37 clocks at 320 MHz (3.125 ns), measured in simulation from the first TVALID in to the next TVALID out for the FINN cybersecurity MLP (60-bit words, a 10-word input), with the design intentionally run at about half the GTF clock. Our brief 113 (report 113) put a 1-clock boosted-tree block (4.3 ns out of context on the K26, 6.206 ns core clock) in the order path with zero added tick-to-trade clocks in simulation, and measured the MLP alternative at 13 clocks in an earlier brief. The comparison is not like for like (different task, data, width and clock; theirs is stimulus to response of the block alone, ours a class available before the message ends) and I would not publish a ratio; what is worth borrowing is the presentation: latency of the block stated as first-valid-in to first-valid-out in simulation, with the clock named. Cost: reporting only. Our own trading-path ML claims should say, next to AMD's 37 clocks, that the block's latency and the path's latency are different things.
