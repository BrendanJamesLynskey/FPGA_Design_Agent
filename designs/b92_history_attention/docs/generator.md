# Datasheet: the stateful arms and their generator (brief 92)

What a user of the generated modules could guess wrong is listed first.

## Things you could guess wrong
- **The arm has memory.** The output for an event depends on the earlier events since the last `rst`. `rst` clears the valid pipeline **and** the
  front end's state (sums, window). The 87 and 91 networks cleared only the valid pipeline; these do not behave that way. After a reset
  the first events see zero state (an empty window, zero sums); the training data never did (it drops the first 50 events of a session),
  so ignore the first N outputs (N = 16 for the window arms, about 64 for the sums with the slowest rate) after a reset.
- **State advances only on `in_v`.** A clock without `in_v` changes no state and produces no event. Latency from `in_v` to `out_v` is
  fixed (`LATENCY`), whatever the spacing of events.
- **`out_cls` is undefined until `out_v`** (the datapath is not reset).
- **Ties go to the lower class index.** In the tiny attention arms a tie between window positions goes to the most recent event.
- **The order-flow term is clipped to -31..31 at the port** (the 87 feature clip, -127..127, is on the *sum* of 16 terms and is unchanged).
- **Port fields are offset to be unsigned:** `ts + 1`, `sv + 8`, `ofi + 31`. A value outside the legal range (`ts + 1 = 3`, `sv + 8 > 16`, `ofi + 31 > 62`) is
  not a legal input; the twin and RTL are only compared on legal values.
- **Shifts are arithmetic and floor** (`>>>` in the RTL, `>>` on numpy int64), so `-1 >> 1 = -1`.

## Ports (every stateful arm)
`clk`; `rst` (synchronous, active high); `in_v`; `in_f[50:0]`; `out_v`; `out_cls[1:0]`.

| Bits | Field | Meaning |
|---|---|---|
| 37:0 | the 87 features | feature 0 in the low bits, widths 8 8 4 3 5 8 2 (bid size, ask size, spread, imbalance bucket, trade-sign sum, OFI sum, last mid direction) |
| 39:38 | `ts + 1` | trade sign of the event: -1, 0, +1 |
| 44:40 | `sv + 8` | signed traded size, -8..8 (0 for a non-trade) |
| 50:45 | `ofi + 31` | the event's own order-flow term, clipped to -31..31 |

`b92_ref_current` (the head alone, no history) has only `in_f[37:0]`, like the 87 and 91 networks.

## Modules (`rtl/gen/`, all generated by `python -m designs.b92_history_attention.hist.cli rtl`)
| Module | Front end | LATENCY (clocks) |
|---|---|---|
| `b92_ref_current` | none (the head on the 7 features) | 1 |
| `b92_a1_decay` | four channels (trade sign, signed size, OFI term, 2 x bucket - 7) x two rates, `s <= s - (s >>> k) + x`, cut to 8-bit columns | 2 |
| `b92_a4_lut` | the same sums, then the 89 LUT network | 2 |
| `b92_a2_win8`, `b92_a2_win16` | the last 8 or 16 token codes in a shift register | 2 |
| `b92_a3_top1`, `b92_a3_relu` | tiny attention (generated and simulated, **not built in Vivado**: it lost at the stage 2 test) | 3 |

Each arm module instantiates its head `<name>_net` (brief 91 `log4`, or the brief 89 LUT network), one clock, fed by registers.
So `LATENCY` = front-end registers + 1. First-output latency after a reset equals `LATENCY`; the window does not delay it
(a zero window is used), but the first N outputs are not meaningful (see above).

## Generator options
`hist/hawkes_sim.HParams` (the self-exciting generator: `mu`, `tau_e`, `n_branch`, `tau_s`, `gamma`, `p_burst`, `burst_len`, `beta_b`,
`d_b`, `kappa`; meanings in the module docstring and design.md section 2); `hist/frontends.RATE_SETS` (decay shifts); `hist/attn`
(`N_WIN = 16`, `D = 4`, `MV = 4`, forms `top1` and `relu`); the head is `designs/b91_lowbit/lowbit/model.Config` (see its datasheet).
