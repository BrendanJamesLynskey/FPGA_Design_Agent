# HDL coding standard: FDA-HDL v1.15

**FDA-HDL v1.15** (2026-11-26; v1.0 of 2026-11-12 was the first release, v1.1 of the same day added the check suite's rules) is the coding standard for the agent's RTL and for anything a person adds. v1.1 (brief 71) splits the reset rule into HDL-RST-01 to HDL-RST-05 after the owner's rule that resets are synchronous, adds the check suite's rules (HDL-CLK-02, HDL-IF-02, HDL-IF-03, HDL-VER-01, HDL-GT-01, HDL-DOC-01), and gives every rule a one-line `fix` and a KB `skill`, which the [check suite](check_suite.md) shows with each finding. v1.2 (brief 73) adds HDL-IF-04 to HDL-IF-06 for the AXI4-Lite interface profiles (the `axi_profile` check). v1.3 (brief 70) adds AMD's DRC REQP-1840 (a register with an asynchronous set or reset driving a block-RAM control pin) to HDL-RST-03 and HDL-RST-06, AMD IP gets the reset it needs (advice from `flow/amd_ip_resets.py`); the reset findings now quote the measured cost ([results/70_resets](../results/70_resets/README.md)). v1.4 (brief 106) adds HDL-ORC-01 (constants the spec or board file defines are derived by code: the `constants` check) and HDL-ORC-02 (evidence is read only while its inputs are unchanged: the `stale` check), see [results/106_orchestrator](../results/106_orchestrator/README.md). v1.5 (brief 105A) makes DRC CFGBVS-1/2 a gate failure for a board whose configuration voltage is confirmed in its board file (HDL-DRC-01; the flow sets the two properties for such a board), adds HDL-XDC-02 (a blanket `set_clock_groups -asynchronous` is flagged for owner review, advisory) and HDL-CDC-02 (`SIM_ASSERT_CHK` is 1 on every `xpm_cdc_*` instance, advisory); see [results/105A_constraint_gates](../results/105A_constraint_gates/README.md). v1.6 (brief 129) adds HDL-IO-01 (a register marked `IOB TRUE`, or in an interface declared `iob: true`, is in the I/O block, or the finding names the cell and Vivado's reason: gate `iob_packed`; an unmarked register beside a synchronous interface's pin is advice); see [results/129_iob_packing](../results/129_iob_packing/README.md). v1.7 (brief 205, owner decision 38) turns the ban on initial values into a setting: HDL-SYN-06 follows `rtl.initial_values` (`allow`, the default; `warn`; `deny`, the earlier behaviour), because AMD (UG949) and Altera both recommend defined power-up values; ROM initialisation passes in every mode and the reset rules are unchanged (an initial value is a power-up state, not a reset), see [design_standards.md](design_standards.md#initial-values-rtlinitial_values). v1.12 (brief 206) adds HDL-INIT-01 (advisory): on AMD parts an initial value of 1 keeps a register out of a DSP48 or block-RAM register (they power up 0, or hold one value per port), and UltraRAM is refused for initial contents; the `init_values` check finds both, see [results/206_power_up](../results/206_power_up/README.md). v1.14 (brief 231, owner 2026-11-26) refines HDL-SYN-06: a register has one start state (an initial value where it has no reset, the reset value where it has, never both with different values), control state (an FSM, a valid flag) keeps its reset, and a design whose every reset reconfigures the FPGA sets `rtl.reset_model: reprogram`, when the initial values are the reset values (`STD-INIT-02`, see [design_standards.md](design_standards.md#initial-values-and-resets-rtlreset_model)); it also adds HDL-STY-01 (a source file is named after its module, Verilator DECLFILENAME) and turns Verilator's PROCASSINIT off, since STD-INIT-01 and STD-INIT-02 replace it. v1.15 (brief 241) adds HDL-DMA-01 (advisory): a design that moves Processing System memory through a non-coherent (HP) port declares its software cache contract in spec.yaml; the `dma_coherency` check reads the declaration and the port names.

Each rule has a short rationale and maps to tool checks:

- Verilator `--lint-only -Wall` warning codes;
- Vivado `report_methodology`, `report_drc` and `report_cdc` rule IDs, read from the build's `gates.json`, at severity
  Warning and above (Info and Advisory do not count);
- the design-standards checker's rules ([design_standards.md](design_standards.md), `flow/standards_check.py`);
- the check suite's own codes ([check_suite.md](check_suite.md), `flow/checks`): the reset netlist scan, the structural
  CDC check, the exception and I/O checks, the MMCM range check, FSM coverage, AMD IP notes, the link plan and the DOC
  gate. `flow/lint_ruleset.py` reads the reset codes from a check-suite result (`--checks build/checks/base/synth.json`);
  rules whose checks are only other suite checks are reported by the suite, not by `lint_ruleset.py`.

The machine-readable copy is `flow/hdl_rules.yaml`. A finding no rule names lands in the catch-all rule of its tool
(`HDL-LINT-00`, `HDL-VIV-00`, `HDL-STD-00`), so nothing is dropped.

```
python3 flow/lint_ruleset.py designs/t1_dimmer_counter --gates designs/t1_dimmer_counter/build/base/gates.json \
    --standards designs/t1_dimmer_counter/build/standards.json --json build/lint/t1.json
```

Each rule ends in one of four states:

| State | Meaning |
|---|---|
| `pass` | its checks ran and found nothing |
| `waived` | every finding is covered by a waiver with owner, reason and date |
| `fail` | at least one finding is not waived |
| `not_run` | none of its tools or reports was available |

The design passes only when no rule fails and every rule was evaluated: a run with a rule `not_run` reports
INCOMPLETE and exits non-zero.

## Rules

| Rule | Title | Rationale | Verilator | Vivado | Standards | Check suite |
|---|---|---|---|---|---|---|
| `HDL-SYN-01` | No latches | A latch is level-sensitive storage; static timing analysis handles it with special cases, and in a synchronous design it almost always comes from an incomplete combinational assignment, where simulation can look correct. | `LATCH`, `NOLATCH` | - | `STD-LATCH-01` | - |
| `HDL-SYN-02` | No combinational loops | A loop through logic has no defined value; simulation may settle where silicon oscillates. | `UNOPTFLAT`, `ALWCOMBORDER` | `LUTLP-*` | `STD-LOOP-01` | - |
| `HDL-SYN-03` | Complete, non-overlapping case statements | An incomplete case infers a latch or a priority the author did not mean; an overlapping or X case item simulates differently from what synthesis builds. | `CASEINCOMPLETE`, `CASEOVERLAP`, `CASEX`, `CASEWITHX` | - | - | - |
| `HDL-SYN-04` | Blocking assignments in combinational logic, non-blocking in clocked logic | Mixing them gives race conditions between simulators and a mismatch between simulation and the netlist. | `BLKSEQ`, `COMBDLY`, `BLKANDNBLK`, `ASSIGNDLY`, `INITIALDLY` | - | - | - |
| `HDL-SYN-05` | One driver per signal | Two drivers is a short in hardware and an X or a last-writer-wins in simulation. | `MULTIDRIVEN`, `PROCASSWIRE`, `CONTASSREG` | `MDRV-*` | - | - |
| `HDL-SYN-06` | Initial values follow the setting rtl.initial_values (default allow) and agree with the reset; ROM initialisation always passes | AMD (UG949) and Altera recommend defined power-up values, so initial values on registers and memories are allowed by default (setting rtl.initial_values - allow, warn or deny). They are a power-up state, not a reset, and the reset rules do not change. An initial block that does more than give power-up values (delays, $display, if or case sequences) is flagged in synthesisable RTL, and deny restores the earlier ban. A register never has both a reset and a different initial value (two start states); control state (an FSM, a valid flag) keeps its reset, unless the design's reset is a reconfiguration (setting rtl.reset_model = reprogram, owner 2026-11-26), when the initial values are the reset values. Verilator's PROCASSINIT is switched off for this reason, since it fires on every register with an initial value, which this rule refines. | - | - | `STD-INIT-01`, `STD-INIT-02` | - |
| `HDL-INIT-01` | An initial value of 1 does not sit on a register that belongs in a DSP or RAM block (advisory) | On AMD parts an initial value is free on fabric and IOB flip-flops, but the DSP48 pipeline registers and UltraRAM power up 0 and a block-RAM port holds one INIT value, so synthesis leaves an INIT = 1 register next to such a block in the fabric, with no warning for the DSP (brief 206, Vivado 2026.1, xc7a35t and xck26 - an 18 x 18 multiply with all four register stages at INIT 1 kept 108 flip-flops out of the DSP48), and refuses UltraRAM for initial contents (Synth 8-12183). Advisory, since the design is still correct, only bigger and slower than it looks. | - | - | - | init_values: `INIT-HB-01`, `INIT-URAM-01` |
| `HDL-DMA-01` | PS memory moved through a non-coherent port has a declared software cache contract (advisory) | The Zynq high-performance (HP) ports do not snoop the processors' caches, so a DMA buffer the PL reads can be stale in DDR and one the PL writes can be hidden behind stale cache lines unless software cleans and invalidates it around each transfer (UG585 and UG1085, PS-PL interfaces). A design that does this says so in its spec, so a reviewer and the driver author know the contract; a design on a coherent port (ACP, HPC) says that instead. Advisory, because the check reads names and declarations, not the driver. | - | - | - | dma_coherency: `DMA-COH-01`, `DMA-COH-02` |
| `HDL-STY-01` | A source file is named after the module it holds | Verilator's DECLFILENAME fires when a file's name differs from its first module (measured over the run records of briefs up to 231, every sampled case was a naming mismatch, none a functional defect, since the flow lists its sources and never searches for a module by file name). The name still matters to the next engineer and to tools that do search by file name, so the file and the module agree. | `DECLFILENAME` | - | - | - |
| `HDL-WID-01` | Widths match | A silent extension or truncation is the commonest arithmetic bug; the reader of the code cannot see it. | `WIDTH`, `WIDTHEXPAND`, `WIDTHTRUNC`, `WIDTHXZEXPAND`, `WIDTHCONCAT`, `SELRANGE`, `ASCRANGE`, `LITENDIAN`, `CMPCONST`, `UNSIGNED` | - | - | - |
| `HDL-SIG-01` | Every signal is driven and used, every port connected | An undriven signal is a constant the author did not choose; an unused one is often a missed connection. | `UNDRIVEN`, `UNUSED`, `UNUSEDSIGNAL`, `UNUSEDPARAM`, `UNUSEDGENVAR`, `PINMISSING`, `PINCONNECTEMPTY`, `PINNOCONNECT`, `IMPLICIT` | - | - | - |
| `HDL-CLK-01` | Synchronous design on declared clocks; no derived or gated clocks | A clock made in logic has skew the tools cannot close; a clock enable on the declared clock does the same job safely. Declared domains let the tools and the reviewer see every crossing. | `GENCLK` | `CLKC-*`, `PLHOLDVIO-*` | `STD-CLK-01`, `STD-CLK-02`, `STD-CLK-03` | - |
| `HDL-CLK-02` | MMCM and PLL settings inside the data sheet's VCO and PFD ranges | Neither report_drc nor report_methodology rejects a hand-instantiated MMCME2 or PLLE2 outside its VCO or PFD range (measured, brief 18); the clock then does not lock or drifts on the board. | - | - | - | clocking: `CMT-RANGE-01` |
| `HDL-CLK-04` | A clock mux is a clock buffer (BUFGMUX_CTRL or BUFGCTRL switched on S), and its modes are constrained as exclusive without hiding real paths | A LUT clock mux glitches when the select changes and puts fabric routing on the clock (TIMING-14); every clock entering a mux is timed against the others until grouped, and grouping the source clocks while their own registers exchange data with the mux fanout hid a -6.63 ns failure and every report_cdc row (measured, brief 208). | - | - | - | clock_mux: `CLKMUX-LUT`, `CLKMUX-NO-GROUPS`, `CLKMUX-SRC-GROUPED`, `CLKMUX-CASE`, `CLKMUX-CE-SELECT`, `CLKMUX-STOP`, `CLKMUX-CASCADE`, `CLKMUX-UNTRACED` |
| `HDL-RST-01` | Synchronous resets; an asynchronous reset only in a reset synchroniser or from a declared external asynchronous input | AMD recommends synchronous resets (UG949); an asynchronous reset is released at an arbitrary time relative to the clock and stops registers packing into DSP and block RAM. The owner's rule (2026-11-13) allows it only in reset and CDC synchronisers and where an external device's reset is asynchronous. | `SYNCASYNCNET` | `ROAS-*` | `STD-RST-01` | resets: `RST-ASYNC-01` |
| `HDL-RST-02` | One polarity per reset | A reset used active high in one place and active low in another becomes two nets and two control sets, which costs placement freedom and invites a mismatched release. | - | - | - | resets: `RST-POL-01`, `RST-POL-02` |
| `HDL-RST-03` | No asynchronous reset or set on a register that belongs in a DSP or block RAM, and none driving a block-RAM control pin | The DSP48 and block-RAM registers have synchronous resets only, so an asynchronous reset keeps the register in the fabric, costing flip-flops and the primitive's fast internal path. A block-RAM control pin (reset, enable) driven by a register with an asynchronous set or reset can corrupt the memory contents, and the default timing analysis does not time it (AMD DRC REQP-1840; seen when a reset synchroniser's output fed a RAM's reset pin). | - | `DPIR-*`, `DPOR-*`, `RMIR-*`, `RMOR-*`, `RROR-*`, `REQP-1840` | - | resets: `RST-DSPRAM-01` |
| `HDL-RST-04` | A reset enters each clock domain through a synchroniser | A reset made in one clock domain and released in another without a synchroniser can release different registers on different cycles, or violate recovery and removal timing. | - | `CDC-7`, `CDC-8` | - | resets: `RST-CDC-01` |
| `HDL-RST-05` | No logic drives an asynchronous reset | A glitch on combinational logic driving an asynchronous reset resets the register; AMD's methodology check LUTAR-1 flags it. | `CDCRSTLOGIC` | `LUTAR-*` | - | resets: `RST-LUT-01` |
| `HDL-RST-06` | AMD IP gets the reset it needs | Each AMD IP has its own reset port, polarity and minimum pulse (measured, brief 70); the Processor System Reset ignores a pulse shorter than its filter, the AXI interconnects need every interface reset together and do not resynchronise it, and the DMA needs 16 clocks. Advice, not a failure. | - | - | - | resets: `RST-IP-01` |
| `HDL-CDC-01` | Every clock-domain crossing through a named, declared primitive | An unsynchronised crossing fails rarely and randomly; only structure, not simulation, shows it. | - | `CDC-*` | `STD-CDC-01`, `STD-CDC-02` | cdc_structure: `U*` |
| `HDL-XDC-01` | Complete timing and I/O constraints | An unconstrained or wrongly constrained path is unchecked by timing analysis, so its slack means nothing. | - | `TIMING-*`, `XDCH-*`, `XDCC-*`, `XDCB-*`, `XDCV-*` | - | exceptions: `EXC-*`; io: `IO-*` |
| `HDL-METH-01` | Methodology findings on the synthesised and routed design fixed or waived | The vendor methodology checks are the tool's own list of constructs it handles badly. | - | `SYNTH-*`, `DPIP-*`, `DPOP-*`, `HPDR-*`, `RTRES-*`, `RBOR-*`, `ULMTCS-*` | `STD-METH-01` | - |
| `HDL-DRC-01` | No design-rule violation | A DRC error blocks the bitstream or describes an electrical problem on the board. CFGBVS-1/2 (the configuration bank voltage) block as a gate failure only for a board whose voltage is confirmed in its board file; there the flow sets CFGBVS and CONFIG_VOLTAGE itself (brief 105A). | - | `NSTD-*`, `UCIO-*`, `PDRC-*`, `RTSTAT-*`, `BIVC-*`, `IOSTDTYPE-*`, `REQP-*`, `CFGBVS-*` | - | - |
| `HDL-IO-01` | Registers meant for the I/O block are in it | A first input or last output register only goes into the I/O block when nothing but the pad sits between it and the pin; otherwise Vivado leaves it in the fabric with a critical warning that the DRC and timing gates never see, and the interface timing depends on placement (UG903, UG904). A register marked `IOB TRUE` (or in an interface declared `iob: true`) that is not packed fails; an unmarked register beside a synchronous interface's pin is advice. | - | - | - | io: `IOB-*` |
| `HDL-XDC-02` | No blanket asynchronous clock group | `set_clock_groups -asynchronous` removes timing from every path between its groups, including crossings nobody declared (UG903); a group over every clock, or over a pair that has paths between it, is flagged for the owner. Advisory, never blocking. | - | - | - | constraint_scope: `XDC-ASYNC-PATHS`, `XDC-ASYNC-ALL` |
| `HDL-CDC-02` | XPM CDC instances keep their simulation checks on | AMD's xpm_cdc macros default `SIM_ASSERT_CHK` to 0, which silences their own warnings for misuse in simulation (a source changing faster than the destination can sample); the house default is 1. Simulation only; advisory. | - | - | - | xpm_sim: `XPM-SIM-01` |
| `HDL-CDC-03` | Each crossing's timing intent is constrained and met | An asynchronous crossing needs a bounded latency and, if multi-bit, a bounded skew across its bits; a clock group or a user clock uncertainty bounds neither (brief 207 measured it). A bus-skew violation after routing fails (UG906); the rest is advisory. | - | - | - | cdc_margin: `CDCM-SKEW-VIOL`, `CDCM-SKEW-MISSING`, `CDCM-DPO-LOOSE`, `CDCM-MTBF-MISSING`, `CDCM-MTBF-LOW`, `CDCM-UNC-HIGH` |
| `HDL-FAST-01` | No data-dependent wide shift or index on a fast path | A shift by a signal, or an index by a signal, of a wide vector is a barrel shifter or wide multiplexer; it costs about log2 of its range in LUT levels. Often the data can stay in place while a small position register moves. Only modules declared fast-path; advisory. | - | - | - | fastpath: `FAST-SHIFT-01`, `FAST-INDEX-01` |
| `HDL-IF-01` | Standard interfaces with AMBA names | Standard interfaces make blocks reusable and checkable by protocol checkers. | - | - | `STD-AXI-01`, `STD-AXI-02`, `STD-ARCH-00` | - |
| `HDL-WAIVE-01` | Every waiver has a reason, an owner and a date | A waiver is a decision; without who and why it cannot be reviewed or revisited. | - | - | `STD-WAIVE-01` | - |
| `HDL-IF-02` | AMD AXI4-Lite IP next to our register blocks is used with its measured conventions in mind | AMD's AXI4-Lite peripherals answer holes with OKAY, ignore byte strobes, alias registers and may pop on read (measured, brief 69); software written for our blocks' conventions misbehaves on them. Advice, not a failure. | - | - | - | axi: `AXI-AMD-IP` |
| `HDL-IF-03` | Every accepted AXI request gets exactly one response within a bounded wait | A slave that drops a response hangs the master for ever (the AXI DMA register port returned one B for two writes, brief 69); no other rule of the checker sees a response that never comes. | - | - | - | axi_checker: `RESP_LOST` |
| `HDL-IF-04` | A generated AXI4-Lite register block has the interface profile its design declares and behaves as it says | A profile (house, amd_compatible, strict) fixes what a driver writer could guess wrong (holes, strobes, unaligned and reserved accesses, the error capture). A block that claims one and behaves as another, or a map that names a profile its design did not choose, gives software wrong expectations that no protocol checker sees. | - | - | - | axi_profile: `AXI-PROFILE-SPEC`, `AXI-PROFILE-MISMATCH`, `AXI-PROFILE-DRIFT`, `AXI-PROFILE-OVERRIDE`, `AXI-PROFILE-STALE`, `AXI-PROFILE-NOSRC` |
| `HDL-IF-05` | A design that mixes interface profiles says so | One design with a strict block and a house block gives the driver two sets of rules; the datasheets state each, but the design should state the mix. A block generated before profiles existed states no profile at all. | - | - | - | axi_profile: `AXI-PROFILE-MIX` |
| `HDL-IF-06` | AMD IP in a design with a strict AXI4-Lite profile is acknowledged | AMD's AXI4-Lite peripherals answer holes with OKAY and read 0, ignore byte strobes and accept unaligned addresses (measured, brief 69); a driver written for strict blocks expects SLVERR and must allow for that. Advice, not a failure. | - | - | - | axi_profile: `AXI-PROFILE-AMD-STRICT` |
| `HDL-VER-01` | Every FSM state and listed transition is covered in simulation | A state or transition never reached in simulation is behaviour no test has checked; the coverage comes from the trace, not from the simulator's own coverage (none of the free simulators has FSM coverage). | - | - | - | fsm: `FSM-STATE`, `FSM-TRANS`, `FSM-UNLISTED` |
| `HDL-GT-01` | A transceiver link the part, speed grade and board can build | A line rate outside the speed grade's window, a reference the board does not provide or more lanes than it has cannot be built; the plan says so before any RTL is written. | - | - | - | gt: `GT-PLAN` |
| `HDL-DOC-01` | The design's handover documents what was built, verified and measured | The next engineer needs every number traced to a record and every gap stated (owner, 2026-11-13; the DOC gate of brief 68). | - | - | - | doc: `DOC-PROBLEM` |
| `HDL-ORC-01` | A constant the spec or the board file defines is derived by code, never retyped | A model that retypes a design ID, an identity word or a clock period can pick the wrong one of two near-named constants (82P3: four of six runs bound 0x55445031 where the quoted design ID "UEP1" is 0x55455031). | - | - | - | constants: `CONST-ID-01`, `CONST-ID-02`, `CONST-LIT-01`, `CONST-CLK-01` |
| `HDL-ORC-02` | Evidence is read only while the inputs it was made from are unchanged | A build, a simulation result or a report is a claim about the inputs at the time it ran; after an input changes, a pass read from it is not a pass. | - | - | - | stale: `STALE-EVID-01`, `STALE-CLAIM-01` |
| `HDL-DSP-01` | A DSP slice has the registers its clock period needs (advisory) | Measured on Vivado 2026.1 (brief 185), a slice without its multiplier register, or without its output register, cannot meet the period a fully registered slice meets; Vivado's own DRC flags only unregistered inputs and outputs, not how fast the slice then runs. | - | - | - | dsp_regs: `DSPREG-01`, `DSPREG-02`, `DSPREG-03`, `DSPREG-04` |
| `HDL-TIM-01` | Logic depth fits the clock period | A path with too many logic levels for its clock cannot be fixed by placement (UG949 p.75, p.200, p.234). The distribution of logic levels against each clock's requirement is advisory; a setup path that still fails with its net delay taken out is a gate, because no placement can close it. | - | - | - | logic_levels: `RPT-LL-*` |
| `HDL-CLK-03` | Simple, parallel clock trees with small skew and uncertainty | Cascaded global buffers do not match insertion delay, local clocks routed in fabric have unpredictable skew, and clock uncertainty or skew above the guide's review thresholds usually means the clock topology is wrong (UG949 p.111, p.139, p.232, p.248). Advisory. | - | - | - | clock_tree: `RPT-CLK-*` |
| `HDL-FO-01` | High-fanout nets are replicated by the right means | A net with thousands of loads, or hundreds of loads on a fast clock, limits the clock frequency (UG949 p.75). The fix is a balanced tree and placement-based replication, not MAX_FANOUT on a global net. Advisory. | - | - | - | fanout: `RPT-FO-01` |
| `HDL-LOG-01` | The synthesis log is reviewed, and not truncated | Messages that say logic was removed or tied off show where the netlist differs from the intent, and the tool prints a message only 100 times by default, so a long log hides the rest (UG949 p.198). Advisory. | - | - | - | synth_log: `RPT-LOG-*` |
| `HDL-CONG-01` | Congestion and utilisation stay in the range the placer handles | A congestion window of level 4 or more, a short-interconnect share over 5 %, or high average utilisation makes placement and routing hard (UG949 p.240, p.244, p.273; UG1292 p.6). Advisory. | - | - | - | congestion: `RPT-CONG-*` |
| `HDL-IP-01` | IP is up to date and unlocked at build time | A locked or out-of-date IP is built from a customisation the tool no longer supports; AMD recommends the latest IP version (UG949 p.49). | - | - | - | ip_status: `RPT-IP-01` |
| `HDL-CS-01` | Control sets stay within the device guideline | Registers share a slice only with the same clock, set/reset and enable, so many unique control sets waste slices and spread placement (UG949 p.49, p.265). Under 7.5 % of the device's capacity is acceptable, 7.5 to 15 % reduction is recommended (advisory), above 15 % it is required (gate). | - | - | - | control_sets: `RPT-CS-*` |

| `HDL-VIV-00` | Vivado methodology, DRC and CDC clean (any finding no other rule maps) | A vendor rule ID no other rule names is still fixed or waived with a reason, not ignored. | - | `*` | - | - |

## Waivers and changes

Waivers live in `designs/<d>/lint/waivers.yaml`:

```yaml
waivers:
  - rule: HDL-XDC-01
    match: "vivado:XDCH-2@*"          # glob over the finding key (square brackets match literally) or re:<regex>
    reason: <why this finding is accepted>
    owner: <who decided>
    date: 2026-11-11
```

Finding keys are `verilator:CODE file:line`, `vivado:RULE-ID@stage` and `standards:STD-ID file:line`. A waiver without
a reason, owner or date fails `HDL-WAIVE-01`; an unused waiver is listed so it can be removed. A change to a rule bumps
the version here and in `flow/hdl_rules.yaml`. The rule table above is generated from `flow/hdl_rules.yaml`; each rule's `fix` and `skill` are there.
