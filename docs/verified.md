# "Verified": what the label means and how it is earned (brief 144)

Every design, arithmetic function and IP-library entry ships a **verification record**: `VERIFIED.md` (for people) and `verified.json` (for tools) beside its README.
The record is generated by `python -m flow.verified <directory>` from the traceability collector ([traceability_v1.md](traceability_v1.md), `flow/trace_v1.py`) and the
evidence files it reads. Nothing in it is typed. The label at the top of the record, and on the README, the website, the agent's hand-over and library retrieval, is
computed, and it means exactly what this page says. Owner decision 26 (2026-11-21) makes this the product's defining property: "I want to emphasise the 'verified'
nature of the agent's products."

## The label

| Label | When |
|---|---|
| `verified` | every one of the six criteria below is met |
| `verified except: <list>` | at least one requirement is verified, none fails, and at least one criterion is not met; the list names each unmet criterion with its count |
| `not verified: <reason>` | a requirement fails, or no requirement has passing evidence |
| `not assessed: no requirements recorded` | the directory has no `verif/testplan.yaml` (an IP-library entry or a design that predates the testplan); its own declared status is quoted in the record, apart from the label, and is not checked |

## The six criteria

1. **Every requirement has passing evidence.** Each requirement is in state `verified` in the matrix (a performance requirement needs a measured value inside its bound).
   A requirement that is `not run`, `stale`, `bounded only`, `no measurement` or `proved, statement not approved` does not meet this.
2. **Every requirement is agreed**, by a human, or by delegation and labelled so (brief 143a, owner decisions 23 and 25). The record shows who agreed it and when, and counts
   delegated agreements apart from human ones. A requirement still in `draft` does not meet this, and a testplan that merely says `agreed` without an agreement record
   is not counted.
3. **Every requirement meets its required method mix** for its kind (brief 143a): for example a safety requirement needs simulation plus a formal proof or the board, and a
   functional requirement needs an independent bench or a proof, because the implementing agent's own tests never count alone.
4. **The bench passes the mutation floor** (brief 143b): the mutation score, killed over killed plus real survivors after equivalent mutants are filtered, is at or above the floor.
5. **The formal results pass the rigour checks** (brief 143c): every assertion has a reachable cover (not vacuous), the assumptions leave the design able to reach its main
   states, and every bounded result carries a written justification of its depth. A design with no SymbiYosys item has nothing to check here.
6. **The evidence is fresh**: no item is stale by its pins (a file it is about changed after the evidence was recorded), and (brief 143d) a fresh re-run of the cheap evidence
   agrees with the committed record.

**Not yet measured.** Criteria 3 to 6 depend on briefs 143a to 143d. Until the collector supplies a field a criterion needs, the record shows it as "not yet measured" and it
counts as **not met**: a label never claims what was not measured. So at the time of writing no design can be `verified`; each says `verified except` and names what is missing,
and the list shrinks as the 143 briefs merge. The generator reads these fields from the collector output when they appear: a requirement's `agreement`
(`{kind: human|agent_delegated, by, date}`) and `method_mix` (`{met: bool}`), an item's `written_by` and `mutation`, and the design's `mutation` (`{score, floor, met}`),
`formal_rigour` (`{met, detail}`) and `fresh_run` (`{differs: [item ids]}`). If a 143 brief names a field differently, change the reader in `flow/verified.py` (`agreement()`,
`item_view()`, `criteria()`); the tests in `flow/tests/test_144_verified.py` pin the behaviour.

## What "verified" never means

- **Interoperability** with a device the design talks to, unless a board measurement against that device is listed. A design checked against its own model accepts its own
  symmetric mistakes. Requirements that depend on an outside element and are not closed by hardware are listed in the record's limits.
- **Timing beyond the stated corner.** A post-route timing result is for the part, speed grade, clock and tool version in its evidence file.
- **Anything beyond the widths and depths checked.** A simulation covers the vectors it ran; a bounded formal result covers its depth; a per-width proof covers the widths it names.
  Only a Lean proof marked all widths covers every width, and only for its model (the record says when the model is a transcription of the RTL, not the RTL).
- **That the requirement is the right one.** The text is a human's check, or the planner's where the record says delegated.
- **A board result**, unless a board measurement item is listed.
- **Anything about files outside the manifest**, or about the files after they change: the record pins the SHA-256 of every file it covers, and the CI check fails when any
  differs from the generator's output.

## What is in a record

The label; the criteria and their results; per requirement its text, kind, agreement (who, when), state and every evidence item (method, status, who wrote the bench,
proof depth where it applies, fresh or stale, the record it reads and that record's hash); the limits; the **hash manifest** (every covered file with its SHA-256) and the git
commit the record was generated at; and the commands that reproduce the simulation and formal evidence. A record never lists a board, programming, bitstream-build or deploy
command: the generator drops any command that names one.

The git commit is informational. A record cannot name the commit that adds it, so the CI check compares everything except the commit; the manifest hashes are what pin the
record to the files.

## Where it shows

- Each design README and IP-library README leads with the label and links the record (the line is rendered by `flow/handover.py` and `flow/net/ipdoc.py` from `verified.json`).
- The agent's hand-over (`AGENT.md`) carries the label and the record path.
- The website has a page, "Verified by construction", and the Traceability page opens each design with a verification panel.
- CI (`flow/tests/test_144_verified.py`) fails if a record is missing or differs from the generator's output, or if a README does not carry the label.

## Commands

```
python -m flow.verified designs/b119_tcp_fast     # write VERIFIED.md and verified.json
python -m flow.verified --all                     # every design, arith function and ip_lib entry
python -m flow.verified --check                   # exit 1 if a committed record is out of date
python -m flow.handover write designs/<d>         # re-render the README and AGENT.md with the label
python -m flow.net.ipdoc                          # re-render the ip_lib READMEs
```

After changing evidence, regenerate in this order: evidence and pins, `python -m flow.trace_v1 write`, `python -m flow.verified --all`, the handover renderings, the site.
A testplan may carry an optional `reproduce:` list (`- {what: ..., cmd: ...}`); without one the record uses the design's hand-over commands that are simulation or formal.
