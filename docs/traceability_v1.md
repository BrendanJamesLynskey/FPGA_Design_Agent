# Specification to evidence: testplan schema v1 (brief 116)

The human specifies and checks that verification is thorough enough. The agent holds the knowledge to implement and to verify. The user can see any of
the implementation or the evidence and does not have to. This page is the schema and the rules by which `flow/trace_v1.py` turns a plan and its evidence
into a matrix. It sits above brief 53's per-artefact tags (`flow/traceability.py`, [traceability.md](traceability.md)): that one traces tagged tests and
properties inside a design; this one traces requirements to typed evidence records, and is what a reviewer reads.

## Files

| File | What |
|---|---|
| `designs/<d>/verif/testplan.yaml` | the requirements, the verification items, `discover:` globs for the bench's tests. Schema `fpga-design-agent/testplan/v1`; a v0 file is upgraded in memory (every requirement functional) |
| `designs/<d>/verif/evidence_pins.yaml` | generated by `python -m flow.trace_v1 pin <design>`: the evidence file's hash and the hash of every file the evidence is about, as of the commit that last changed the evidence |
| `designs/<d>/verif/lean_approvals.yaml` | acceptances of Lean theorem statements, of two kinds (briefs 125 and 135): `human` approvals and `agent_delegated` acceptances by the planner on the owner's delegation. **Never written by a tool or through the testplan**; no entry means "statement not approved" |
| `designs/<d>/verif/agreements.yaml` | which requirements are agreed, by a human or by the planner on the owner's delegation (brief 143a; see "Agreement, the method mix, reviews and waivers"). **Never written by a tool or through the testplan** |
| `designs/<d>/verif/reviews.yaml` | the review records a `review` item points to: who, when, what was read, the findings, human or agent-delegated (brief 143a). Never written by a tool |
| `designs/<d>/verif/waivers.yaml` | waivers: reason, scope, expiry, approver kind (brief 143a). Never written by a tool |
| `flow/method_mix_policy.yaml` | the method mix a requirement of each kind needs before it is `verified` (brief 143a) |
| `formal/lean/records/build_record.json` | the hash-pinned record of the last `lake build`, written by `python -m flow.trace_v1 lean-record` (needs the toolchain) |
| `designs/<d>/verif/matrix.md`, `matrix.html` | generated by `python -m flow.trace_v1 write`: the matrix, gaps and every requirement in full |
| `docs/traceability_matrix.md`, `.html` | the project roll-up |

## A requirement

`id`, `kind` (functional, performance, interface, safety), `title`, `text`, `source` (a document and anchor, or v0's `spec:` list), `spec_status` (always `draft`
in the testplan: agreement is recorded in `verif/agreements.yaml`, and `spec_status: agreed` in a testplan fails the gate), optional `external` (what outside the design the requirement depends on), and for a performance requirement
`performance: {quantity, unit, op, bound, condition}` with `op` one of `le ge lt gt eq`.

## A verification item

`id`, `requirements: [...]`, `method`, `title`, `evidence: {file, reader, ...}`, optional `pass_when`, `checks`, `bounded`, `planned`, `written_by`
(`implementing_agent`, `independent_bench` or `human`; see below), and for `board_measurement` an `instrument`.

| Method | Evidence it reads |
|---|---|
| `sim_test` | a JUnit XML of the recorded run (`reader: junit`, `tests: [stem::name, stem::*]`) |
| `uvm_test` | as `sim_test`; a hook until brief 112 merges |
| `assertion` | an SVA run record; a hook until brief 115 merges |
| `formal` | a proof or equivalence record; `bounded: {depth: N}` makes a passing BMC `bounded` |
| `formal_lean` | a Lean 4 theorem proved for **all widths**, checked by Lean's kernel (brief 125; see "Lean proofs" below). Reads the build record, not an evidence file |
| `coverage_bin` | a coverage record |
| `timing` | a post-route report field (`digest.json`) |
| `sim_measurement` | a simulation result file: a value judged against the requirement's bound, or `pass_when` conditions |
| `board_measurement` | a pre-registered board result file, with `instrument`: `eye_scan`, `jtag_registers`, `sysmon`, `ila_capture`, `latency_loop`, `optical_ddm` or `external_equipment` |
| `review` | a named check; it passes only through a record in `verif/reviews.yaml` (the reviewer fields of the item are not read; brief 143a) |

Readers: `json` (`field: a.b.c`), `text` (`regex` with one group), `junit`, `gates` (v0 upgrade), `exists`. A file name may be a glob; the last match in
sorted order is read (run directories are time stamps).

## Agreement, the method mix, reviews and waivers (brief 143a, owner decision 25)

The agent that implements a design also writes its testplan, so four things a reader relies on are kept in files the agent never writes and no tool in the flow writes
(code: `flow/trace_records.py`; tests `flow/tests/test_143a_agreement.py`).

**Agreement.** A requirement is a **draft** until `verif/agreements.yaml` says otherwise. An entry is the owner's, `agreed_kind: human` (`agreed_by`, `date`), or the planner's on the owner's
delegation, `agreed_kind: agent_delegated` (`accepted_by`, `delegated_by: owner decision 25`, `date`); the two are never mixed (a human entry has no `accepted_by`/`delegated_by`, a delegated one
no `agreed_by`). Each entry pins `text_sha256`, the hash of the requirement's identity, kind, title, text, performance bound and external element (whitespace normalised; the `source` anchor
is not part of it). A requirement whose text or bound changes after it was agreed is a **draft again** and the matrix says so (gap `agreement_dropped`); it is reported, not a gate
failure. `python -m flow.trace_v1 agreement-hash DESIGN [REQ]` prints the hash and the current state and writes nothing. The matrix has an Agreement column (draft / agreed (human) /
agreed (delegated, not human)) and the summary counts the three apart: "N of M requirements agreed by a human, K agreed on the owner's delegation (not human), D draft". The testplan cannot claim
agreement: `spec_status: agreed` in it fails the gate. A malformed file (unknown requirement, bad hash, unknown `agreed_kind`, a field of the other kind) fails the gate.

**The method mix.** `flow/method_mix_policy.yaml` lists, per requirement kind, alternatives (each a list of method groups); a requirement is `verified` only when its **passing** items satisfy one
alternative. Otherwise, if anything passes, it is **`partially verified`** and the cell, the gap list and the full text name the groups the closest alternative still lacks (a performance
requirement keeps its state `no_measurement`, which is the same rule as before). Current policy: *safety*: simulation plus a formal proof, or simulation plus a board measurement; *performance*: a
measured value inside the bound (timing, simulation measurement or board measurement); *functional*: a simulation check from a bench the implementing agent did not write, or a formal proof, or a
board measurement; *interface*: the same three. A checkout with no policy file, or a kind the policy does not list, uses the earlier rule (one passing item verifies). The policy replaces
"any one item passes"; a stale, bounded, failing or not-run item never counts towards the mix. A formal Lean item satisfies the formal group on the same terms as before (its statement must be accepted).

**Who wrote the test.** An item with a test as evidence (`sim_test`, `uvm_test`, `assertion`, `coverage_bin`, `sim_measurement`) may say `written_by: implementing_agent | independent_bench | human`. Every
cell names it ("own test", "independent bench", "human-written", or "author not recorded"). **An item that does not say is counted as the implementing agent's own**, because the house rule is that the agent's own
tests never count alone: the group `independent_simulation` is not satisfied by them. Mark an item `independent_bench` or `human` only where that is true (a spec-only bench written without
the RTL or the agent's tests, or a test a person wrote); the gate rejects any other value, and rejects `independent_bench`/`human` on a measurement, timing or formal item (those are not "written"). A requirement
whose every passing item is an own test is marked "rests only on the implementing agent's own tests" in the matrix, the gap list and the summary count.

**Reviews.** A `review` item passes only if `verif/reviews.yaml` has a record with the same `item`: `reviewer`, `reviewer_kind: human | agent_delegated` (a delegated review needs `delegated_by`),
`date`, `read` (the files the reviewer read, each optionally `{file, sha256}`; a read file whose pinned hash differs makes the item `stale`), and `findings` (`none` if none). Without a record the
item is `not_run` ("no review record"), whatever the testplan says about a reviewer. The cell names the kind ("human review", "agent delegated review"); the summary counts human and delegated reviews apart.

**Waivers.** `verif/waivers.yaml` entries have `id`, `requirement`, `waives` (the scope: method groups from the policy), `reason`, `expires` (a date), `approver_kind` and the matching `approved_by` or
`accepted_by` + `delegated_by`, `date`. A waiver in effect whose `waives` covers every group a `partially verified` (or `no_measurement`) requirement lacks makes its state `waived`, shown as "verified under a
waiver" with the waiver id and expiry, counted separately in the summary, and listed in the gaps (`waiver_in_effect`). It never rescues a requirement with nothing passing. **An expired waiver
waives nothing** (gap `waiver_expired`; the date is today's, or `TRACE_TODAY` in tests, so a matrix with a waiver changes when it expires). **A safety requirement is waived only by a human**: a delegated
waiver of a safety requirement fails the gate and is not applied. A malformed waiver (no reason, no expiry, unknown group or requirement) fails the gate.

## Lean proofs (`formal_lean`, brief 125)

Lean 4 is used narrowly: for datapath algorithms and arithmetic identities where per-width SymbiYosys proofs do not cover the claim ("proved for all widths"), and as a
spec-checking role (a theorem statement is a precise requirement that a human reads). SymbiYosys stays the tool for control, handshakes, FIFOs and clock crossings. Background and
the survey are in [lean_assessment.md](lean_assessment.md); the Lean project is [formal/lean](../formal/lean/README.md). Code: `flow/lean_tier.py`; tests `flow/tests/test_125_lean_tier.py`.

An item names the theorem and how the Lean model meets the RTL:

```yaml
- id: V-LEAN-GRAY-STEP
  requirements: [B96-F-LEAN-GRAY-STEP]
  method: formal_lean
  title: One bit changes per count, wrap included, every width
  lean: {module: Gray.Spec, theorem: Gray.gray_step}            # project defaults to formal/lean
  rtl_link:
    kind: transcription_tested                                  # rtl_generated | transcription_tested | transcription_untested | model_only
    source: [{file: designs/x/rtl/a.sv, lines: "78-82"}]        # the transcribed lines; `commit:` reads them from that commit instead of the tree
    transcribed_in: formal/lean/Gray/Spec.lean (bin2gray, ...)
    crosscheck: {file: formal/lean/Gray/CrossCheck.lean, reference: "what it is compared with"}
```

**Four things the matrix always says about a Lean proof**, in the cell and in the requirement's full text:

1. **Is the statement approved, and by whom?** A human approves a statement, by an entry in `verif/lean_approvals.yaml` (item, theorem, the statement's hash, the hash of the
   module's definitions, approver, `approver_kind: human`, date). `python -m flow.trace_v1 lean-statement <design> <item>` prints what to read and the hashes; it writes nothing, and
   nothing in this repository writes the approvals file. Without an entry the item is **statement not approved**: the proof built, but it is not counted as verification (the
   requirement's state is "proved, statement not approved" and the gap list names it). An `approved_by` field in the testplan itself is a gate failure.
   **Delegated acceptance (brief 135).** The owner may delegate open decisions to the planner agent (owner decision 23). The planner's acceptance of a statement is a second kind of entry,
   `approver_kind: agent_delegated`, with `accepted_by` (for example "planner (Session A)"), `delegated_by` (for example "owner decision 23"), `date` and the same two hashes; it never
   uses `approved_by`, and a `human` entry never uses `accepted_by`. It is not a human approval and is never shown as one: the item reads "proved; statement accepted by the planner on the
   owner's delegation (not a human approval)" against "proved; statement approved by a human". **Decision on counting:** a delegated acceptance does count as verification for the
   requirement (state `verified`, with a note that it rests on a delegated acceptance), because the owner chose to delegate and the proof is real; but the summary line counts it apart,
   "N verified, of which M rest on delegated acceptances", where M is the verified requirements whose every passing item is a Lean proof with a delegated acceptance. A requirement that
   also has a passing simulation, formal or board item is not in M. The owner can ask for a human approval at any time by replacing the entry with a `human` one. An agent cannot set
   either kind through the testplan, and any other `approver_kind` approves nothing and fails the gate.
2. **Axiom tier**, read from `#print axioms`: *kernel only* (propext, Classical.choice, Quot.sound), *kernel plus a compiled decision procedure* (a `bv_decide` SAT certificate checked by
   compiled code, so the Lean compiler is in the trusted base), or *unsound* (`sorryAx` or any other axiom: the item fails).
3. **How the Lean model meets the RTL.** *Proof of a model, no RTL link* (pure arithmetic); *proof of the transcription, transcription not tested*; *proof of the transcription,
   transcription tested* (a person wrote the Lean from named RTL lines, and a cross-check compares it with an independent reference; the proof says nothing about the RTL beyond that
   reading and test); *proof about the RTL* (`rtl_generated`: a tool made the Lean model from the RTL; no such tool exists yet, and no item claims it). A requirement verified only by
   transcription-level proofs says "the Lean proof is of a transcription of the RTL, not of the RTL itself".
4. **Where the build status came from.** With the Lean toolchain installed and `--lean live` (or `auto`), `lake build` runs in a scratch copy and the status is computed from it
   (`lake build (live)`). Without it, the status is read from the committed build record and shown as **recorded build (not re-run)**. `write` and `check` always use the record, so
   the committed matrices and CI do not depend on the machine; `show` uses `auto`. CI has no Lean toolchain and stays green.

**Staleness** (reported, not failed): the record pins the SHA-256 of every Lean file in the project (and the lakefile and toolchain), of each theorem's statement and definitions, and of the
transcribed RTL lines. If any of them differs from the record, the item is `stale`. Rebuild with `python -m flow.trace_v1 lean-record` and commit the record.

**The frozen-statement gate** (fails CI, for both kinds of acceptance): for an accepted item, the theorem's statement (comments removed, whitespace normalised) and the module's definitions must hash to the approved
values. A changed statement or definition is a failure, not a warning: the statement is the specification. Comments and whitespace do not count as a change. The gate also fails an
approval for an unknown item, an `approver_kind` that is neither `human` nor `agent_delegated`, an entry that mixes the two kinds' fields, an item whose theorem is missing, a `transcription_tested` link without an existing cross-check file and a named reference,
and a transcription source whose lines cannot be read.

**Limits.** The proof is about the Lean model. Timing, control, clocks and metastability are not modelled unless an item says so. The record shows that a build succeeded at those file
hashes; it is not a re-run. The approver's check is the human's: this repository cannot tell who typed the entry, so the rule is procedural, and the gate only checks the entry's form and
that the hashes still match.

## Status rules (computed, never typed)

Per item: `fail` if a condition does not hold or a measured value is outside the bound; `not_run` if the evidence file or field is missing (a `planned:` hook
says why); `stale` if it passes but a file in `checks` differs from its pinned hash, the evidence file differs from its pin, or there is no pin; `bounded` if it
passes and `bounded:` is set; `unapproved` for a `formal_lean` item that builds while its statement is not accepted (neither a human approval nor a delegated acceptance); otherwise `pass`.

Per requirement: `fail` if any item fails. Where `flow/method_mix_policy.yaml` has an entry for the kind, `verified` also needs the method mix (above), else `partially verified` or `waived`. A **performance** requirement is `verified` only when a measuring item (`timing`, `sim_measurement`,
`board_measurement`, judged against the bound) passes; the basis is recorded as board, post-route timing or simulation only; a passing test alone gives
`no_measurement`. Without a policy entry a requirement is `verified` with one passing item; otherwise `bounded` with only bounded formal, `stale`, `unapproved` (only Lean items whose statement is not approved), or `not_run`.

A requirement with `external` has a hardware closure, `done` when a `board_measurement` item passes and `open` otherwise. If it passes in simulation alone, the
matrix says "passes without hardware; hardware verification open".

## Gaps and the gate

Reported: requirements with no passing evidence, stale evidence, performance verified in simulation only, external requirements not closed by hardware.
**Fail CI** (`python -m flow.trace_v1 check`, and the tests in `flow/tests/test_116_traceability.py`, which also compare the committed matrices with what the code
writes today): a requirement no item traces to, an orphan check (an item tracing to no or an unknown requirement, or a bench test no item names), an approved Lean statement that changed, a malformed `formal_lean` item or approvals file, a malformed agreements, reviews or waivers file, `spec_status: agreed` in a testplan, a waiver of a safety requirement that is not a human's, an unknown `written_by`, an unknown
method or kind, a `board_measurement` without a valid instrument, a performance requirement without quantity, unit, op, bound and condition, a `checks` file that does
not exist. Staleness is reported, not failed.

## Limits

Staleness is a lower bound: the pin records the checked files as of the evidence's commit, so evidence generated from an older tree and committed later looks fresh.
A requirement is only as good as its text; the matrix shows that checks exist and pass, not that the requirement is the right one, which is the human's check.
