# Specification to evidence: testplan schema v1 (brief 116)

The human specifies and checks that verification is thorough enough. The agent holds the knowledge to implement and to verify. The user can see any of
the implementation or the evidence and does not have to. This page is the schema and the rules by which `flow/trace_v1.py` turns a plan and its evidence
into a matrix. It sits above brief 53's per-artefact tags (`flow/traceability.py`, [traceability.md](traceability.md)): that one traces tagged tests and
properties inside a design; this one traces requirements to typed evidence records, and is what a reviewer reads.

## Files

| File | What |
|---|---|
| `designs/<d>/verif/testplan.yaml` | the requirements, the verification items, `discover:` globs for the bench's tests. Schema `fpga-design-agent/testplan/v1`; a v0 file is upgraded in memory (every requirement functional) |
| `designs/<d>/verif/evidence_pins.yaml` | generated by `python -m flow.trace_v1 pin <design>`: the evidence file's hash and the hash of every file the evidence is about, as of the commit that last changed the evidence |
| `designs/<d>/verif/matrix.md`, `matrix.html` | generated by `python -m flow.trace_v1 write`: the matrix, gaps and every requirement in full |
| `docs/traceability_matrix.md`, `.html` | the project roll-up |

## A requirement

`id`, `kind` (functional, performance, interface, safety), `title`, `text`, `source` (a document and anchor, or v0's `spec:` list), `spec_status` (`draft` or
`agreed`; only a human sets `agreed`), optional `external` (what outside the design the requirement depends on), and for a performance requirement
`performance: {quantity, unit, op, bound, condition}` with `op` one of `le ge lt gt eq`.

## A verification item

`id`, `requirements: [...]`, `method`, `title`, `evidence: {file, reader, ...}`, optional `pass_when`, `checks`, `bounded`, `planned`, and for
`board_measurement` an `instrument`.

| Method | Evidence it reads |
|---|---|
| `sim_test` | a JUnit XML of the recorded run (`reader: junit`, `tests: [stem::name, stem::*]`) |
| `uvm_test` | as `sim_test`; a hook until brief 112 merges |
| `assertion` | an SVA run record; a hook until brief 115 merges |
| `formal` | a proof or equivalence record; `bounded: {depth: N}` makes a passing BMC `bounded` |
| `coverage_bin` | a coverage record |
| `timing` | a post-route report field (`digest.json`) |
| `sim_measurement` | a simulation result file: a value judged against the requirement's bound, or `pass_when` conditions |
| `board_measurement` | a pre-registered board result file, with `instrument`: `eye_scan`, `jtag_registers`, `sysmon`, `ila_capture`, `latency_loop`, `optical_ddm` or `external_equipment` |
| `review` | a named check with `reviewer`, `reviewer_kind` (human or agent) and `date` |

Readers: `json` (`field: a.b.c`), `text` (`regex` with one group), `junit`, `gates` (v0 upgrade), `review`, `exists`. A file name may be a glob; the last match in
sorted order is read (run directories are time stamps).

## Status rules (computed, never typed)

Per item: `fail` if a condition does not hold or a measured value is outside the bound; `not_run` if the evidence file or field is missing (a `planned:` hook
says why); `stale` if it passes but a file in `checks` differs from its pinned hash, the evidence file differs from its pin, or there is no pin; `bounded` if it
passes and `bounded:` is set; otherwise `pass`.

Per requirement: `fail` if any item fails. A **performance** requirement is `verified` only when a measuring item (`timing`, `sim_measurement`,
`board_measurement`, judged against the bound) passes; the basis is recorded as board, post-route timing or simulation only; a passing test alone gives
`no_measurement`. Other kinds are `verified` with one passing item, `bounded` with only bounded formal, `stale`, or `not_run`.

A requirement with `external` has a hardware closure, `done` when a `board_measurement` item passes and `open` otherwise. If it passes in simulation alone, the
matrix says "passes without hardware; hardware verification open".

## Gaps and the gate

Reported: requirements with no passing evidence, stale evidence, performance verified in simulation only, external requirements not closed by hardware.
**Fail CI** (`python -m flow.trace_v1 check`, and the tests in `flow/tests/test_116_traceability.py`, which also compare the committed matrices with what the code
writes today): a requirement no item traces to, an orphan check (an item tracing to no or an unknown requirement, or a bench test no item names), an unknown
method or kind, a `board_measurement` without a valid instrument, a performance requirement without quantity, unit, op, bound and condition, a `checks` file that does
not exist. Staleness is reported, not failed.

## Limits

Staleness is a lower bound: the pin records the checked files as of the evidence's commit, so evidence generated from an older tree and committed later looks fresh.
A requirement is only as good as its text; the matrix shows that checks exist and pass, not that the requirement is the right one, which is the human's check.
