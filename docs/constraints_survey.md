# Constraints survey: every constraint and design property the AMD flow offers, and when the agent should use each

Brief 105, 2026-11-19. Question from the owner (2026-11-18): "survey of all possible constraints, and make a plan for when and where to include them." This file is the survey (one table per group) and the ranked plan. The measurements behind the claims are in [results/105_constraints_survey/](../results/105_constraints_survey/README.md); the executor's report is `reports/105_constraints_survey_report.md` in the planner's hand-off folder.

Families covered: 7-series (Artix-7 on the Nexys A7, the Zynq-7000 PL on the ZedBoard), UltraScale+ (the K26 PL on the KR260) and Versal (named in AMD's guides; none of our boards). Where a row says "same" the three guides agree; where families differ the row says how. The per-family detail lives in the knowledge bank's `family_matrix` (areas `cdc`, `constraints`, `clocking`, `io`, `power`).

## 1. Sources and how to read the tables

Every row cites the AMD guide and chapter, in our own words. Chapter map of the guides used (local copies: UG903, UG949, UG901, UG912, UG906, UG908, UG907 v2025.2; UG835 v2025.2; UG974 v2026.1):

| Guide | Chapters used |
|---|---|
| UG903 Using Constraints | 2 Constraints Methodology; 3 Defining Clocks (primary, virtual, generated, clock groups, latency/jitter/uncertainty); 4 Constraining I/O Delay; 5 Timing Exceptions (multicycle, false path, min/max delay, case analysis, disabling timing arcs); 6 CDC Constraints (bus skew); 7 XDC Precedence; 8 Physical Constraints (netlist, I/O, placement, routing, configuration) |
| UG949 UltraFast Methodology | 2 Board and Device Planning (power, clock resources, I/O planning, SSI, configuration); 3 Design Creation with RTL (coding, clocking guidelines, Clock Domain Crossing); 4 Design Constraints (timing, power and thermal, physical); 5 Design Implementation; 6 Design Closure (timing, power, DRC, configuration and debug) |
| UG901 Synthesis | 3 Synthesis Attributes (supported attributes, attributes in XDC, propagation rules) |
| UG912 Properties | 3 Key Property Descriptions (each property has "Architecture Support" and "Applicable Objects") |
| UG906 Design Analysis | 4 Timing Analysis; 5 Reports; 6 Synthesis Analysis and Closure Techniques; 7 Implementation Analysis and Closure Techniques |
| UG908 Programming and Debugging | 3 Generating the Bitstream or Device Image (BITSTREAM.* settings, OVERTEMPSHUTDOWN) |
| UG907 Power Analysis | 2 Estimating Power (switching activity); 6 Tips and Techniques for Power Reduction |
| UG835 Tcl Commands | command reference (`report_synchronizer_mtbf`, `report_bus_skew`, `set_data_check`, `group_path`, `set_max_time_borrow`, `create_waiver`) |
| UG974 / UG953 Libraries | XPM_CDC parameters |

The columns:

- **Does / Families**: what it does and where it exists. "7s" 7-series, "US+" UltraScale and UltraScale+, "Vs" Versal. Family support is from UG912's "Architecture Support" line for property rows, otherwise from the guide's text; "not checked" means the local text does not say.
- **Missing / Misused**: the hazard if the agent leaves it out, and if it uses it wrongly.
- **Belongs**: `XDC` (design.xdc), `RTL` (attribute in the source), `ip.yaml` (the IP library's parameters), `board` (board file and master XDC, never from the model), `run` (flow script such as `flow/build.tcl`).
- **When**: how the agent decides.
  - `ALWAYS`: every design, by rule.
  - `DERIVE`: by rule from a fact the design already declares (for example, every crossing in `architecture.yaml` gets its synchroniser constraints); code writes it, the model never types the value.
  - `MEASURED`: only after a report names the net or path that needs it.
  - `BOARD`: comes from the board's files; the model names a resource only.
  - `OWNER`: never without the owner's yes.
- **Today**: what our flow does now. `set` = we write it; `check` = a gate or rule looks at it; `neither`. File and line are at main `a3755f32`.
- **Gate**: how a gate could check it (a lint rule, a Vivado report, a `report_methodology` rule ID, a DRC).

C1 and S12 can meet on an input register: an input port's first synchroniser stage takes ASYNC_REG, not IOB, unless the interface table says `iob: true` (UG912: IOB wins over ASYNC_REG).

Rule-ID severities (Critical Warning, Warning, Advisory) are those of the Vivado 2026.1 catalogue in `results/71_check_suite/rule_catalogue_2026_1.tsv`. Our post-route gates count only Critical Warnings and Errors from `report_methodology` and `report_drc` (`flow/gates.py` `_n_sev` at line 369 and the gate dict at lines 669-671), so a rule that is only a Warning in the catalogue blocks nothing unless a separate check in `flow/` reads it.

## 2. The b89 check (answer first)

`designs/b89_lutnet_gen/rtl/treelut/treelut_arm.sv` is not a clock-domain crossing. It has one clock port `clk`; every sequential block in it and in the TreeLUT module it wraps (`TreeLUT.v`, `myreg.v`) is `@(posedge clk)` or a `.clk(clk)` port connection, and its only reset `rst` is synchronous and in the same domain. The post-route timing summary of its out-of-context build lists one clock (`results/b89/ooc/a7/reports/treelut_arm/timing_summary.rpt`, clock summary: `clk`, 7.750 ns). A crossing needs two clocks.

Why it was flagged: the flag came from a name search for "sync"/"cdc" outside the gate. No code in `flow/` or `agent/` selects modules by name for the crossing check: `flow/cdc_structure.py` reads the netlist's register-to-register paths between clocks (`flow/cdc_paths.tcl`) and writes nothing for a one-clock design. So the gate did not miss it, and there is nothing to fix in RTL or in a name search. `designs/b89_lutnet_gen/tests/test_b89_rtl.py` now pins the fact: the file has one clock and no `negedge`, so a future edit that adds a second clock fails the test and the crossing gate takes over.

## 6. Measurements

Four small experiments on out-of-context designs, Vivado 2026.1, one thread, one run per variant (one seed). Numbers are in [results/105_constraints_survey/results.md](../results/105_constraints_survey/results.md), generated from the raw reports; the designs are in `flow/tests/fixtures/constraints_survey/`. Out-of-context runs have no I/O delay model, so these compare variants of one design; they do not show that a design closes.

**M1: ASYNC_REG present against absent** (24 independent two-flop synchronisers, 10 ns to 3 ns clocks).
- 7-series (xc7a100t): with the attribute all 24 chains sit in one slice. Without it 11 of 24 do; the mean distance between the two stages is 1.25 slices, the largest 5, and the mean stage-to-stage delay is 0.874 ns against 0.809 ns (largest 1.247 against 1.195). No SRL was inferred for a two-stage chain either way. TIMING-10 and CDC-5 appear only without the attribute; with it CDC-6 appears.
- UltraScale+ (xck26): all 24 chains packed into one slice in both variants, so no placement difference was seen (delay 0.442 against 0.427 ns mean). With the attribute `report_synchronizer_mtbf` lists 24 chains, overall 2.8e+25 years; without it the command prints Power 33-219 (no identified synchronizers) and writes no report.
- Reading: the placement harm of a missing attribute is real but modest and family-dependent here; the harm that is certain is that the MTBF report and the tool's own synchroniser recognition both go blind. Both rules are Warnings, so a gate that counts only Critical rows passes the plain variant (rank 4 in section 5, and the `cdc_structure.py` U2 rule, which does catch it).

**M2: `MAX_FANOUT` and `DONT_TOUCH`** (one register driving 3000 flops, 2.7 ns clock, xc7a100t).
- No attribute: Vivado already replicated the driver 17 times (largest fanout 232); the path from it has 0.914 ns slack and 1.497 ns delay.
- `MAX_FANOUT=100`: 30 copies, largest fanout 100, slack 0.956 ns, delay 1.455 ns: a gain of 0.04 ns on a path that already met timing.
- `DONT_TOUCH` (alone or with `MAX_FANOUT=100`): one copy, fanout 3000, delay 2.078 ns, slack 0.333 ns. `DONT_TOUCH` overrides `MAX_FANOUT` completely and costs 0.58 ns on this path.
- Design WNS is -0.299 ns in all four variants, from an output-port path unrelated to the driver (no output delay model out of context). So this run does not show `MAX_FANOUT` rescuing a failing path; it shows that the attribute is not needed where the tool already replicates, and that `DONT_TOUCH` removes that replication. A failing-path case would need a tighter clock or a longer path and was not run.

**M3: `set_bus_skew` on a 16-bit Gray pointer** (10 ns to 6 ns clocks).
- No exception (a): WNS 0.672 ns, datapath delay spread 0.323 ns; `report_bus_skew` prints "No bus skew constraints".
- `set_max_delay -datapath_only 10` (b): the report still says "No bus skew constraints"; slack is positive, so a gate that only reads slack passes with no skew bound at all (rank 1).
- Plus `set_bus_skew 6` (c): requirement 6.000, actual 0.906, slack 5.094 ns.
- Plus `set_bus_skew 0.25` (d): the same placement (spread 0.205 ns), requirement 0.250, actual 0.906, slack -0.656 ns: the report fails when the bound is tighter than the routed skew, so `post_route_bus_skew_ok` has a real negative case.

**M4: the KR260 10G design's routed checkpoint** (brief 96E `rm_gp`, opened read only).
- `report_synchronizer_mtbf` finds 1345 synchronisers, overall 6.48e+51 years; 2844 ASYNC_REG flops, 61 XPM CDC cells.
- `report_cdc`: CDC-3 1194 Info, CDC-9 4 Info, CDC-6 6 Warning (multi-bit with ASYNC_REG), CDC-15 2107 Warning (clock-enable-controlled structure, the hand-built handshake data paths carrying `Max Delay Datapath Only`). No row says a chain lacks ASYNC_REG. The two Warning groups pass today's Critical-only gate; they are the population rank 1 and rank 3 would examine.
