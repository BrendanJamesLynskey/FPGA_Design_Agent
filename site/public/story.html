How it was built

How the agent was built, evaluated and improved

How the FPGA Design Agent was designed, measured and corrected. The agent turns a plain-English request into a design checked by hidden tests, code-run gates and a board. This page shows how that was built and tested, one experiment at a time, including the ones that found nothing.

Best result: a deterministic CDC gate flagged 10 of 10 faulty designs where the tool's own report flagged 5, with 0 false alarms on 12 correct designs. Not proven: how often the agent solves a task it has never seen. The first held-out evaluation was stopped with no score, and the baseline evaluation has not been run.

11 experiments are written up below, each in the same form. Where a run was single or the sample small, the card says so and claims no rate.

Terms used on this page

Terms used below: CVDP is a public set of RTL-writing problems. CDC is a signal crossing between two clocks. A mutant is a design with one deliberate fault, used to test whether the tests notice. An escape is a run whose own checks passed while the hidden tests failed. Slack is how much timing margin a path has; negative means it fails. V0 to V3 are the four verification stages. H1, H2 and H9 are three harness changes (context management, hang protection, report digests). Slack and WNS both mean timing margin. An oracle answers the agent's clarifying questions from the hidden spec. ILA is an on-chip logic analyser. MCP is the protocol the agent's tools speak. Stage 2 is the RTL and tests stage. The Clarifier, Modeller, Verifier and Designer are the agent's four roles. The models are named as the provider lists them.

What the measurements say about building agents

  • The agent's own checks are not a pass. 6 of 21 development runs passed their own checks and failed the hidden tests, each from a spec read differently. dev.json
  • Where the standard tool is silent, a deterministic gate can see the fault. The tool's own CDC report alone flagged 5 of 10 faulty designs; the gate flagged 10, with 0 false alarms on 12 correct designs. mutant_table.md
  • A test bench that looks complete can miss reset-state faults. The first full mutation run killed 90.48 percent of 21 mutants; the survivors were both reset-state faults. mutation_t1.json
  • A cheaper model is not evidence of equal quality. Paired over 86 problems, one cheaper model was 12.4 points worse (interval -21.7 to -3.5) and the other showed no detectable difference. paired_eval86.md
  • A tool the roles do not use cannot be measured. With the router on, end-to-end hidden passes were 0 and with it off 0; the roles hardly called the new tools. e2e.md
  • Few blocks show only large effects, and a rule needs one reading. H1 lowered cost by 32.8 percent (interval -53.3 to -4.3) and tokens by 65.6 percent (interval to +0.9), so the adopt rule gave two answers. analysis.md
  • One run per case is an illustration, not a rate. 1 of 3 seeded timing misses closed, and none of 6 attempts to write RTL with the design-time plan passed its hidden bench. README.md
  • Pin every tool that is not under test. 9 of the 57 eval-1 slots ended as not run after an automatic CLI update. eval1_preregistration.md
  • A speed-up counts only with an identical result. The build cache cut an agent run's build sequence by 76 and 80 percent on two designs with identical placement and routing hashes. README.md

The full list, with what each claim does not show, is in docs/agent_lessons.md.

Negative31 Oct

Does a cheaper open-weight model match the base model?

Hypothesis
Can one of the cheaper open-weight models (z-ai/glm-5.3-flash or deepseek/deepseek-v4.1-flash-1017) replace the base model openai/gpt-6-luna for writing RTL at lower cost?
Result
Paired against the base (61.6 percent pass rate), glm-5.3-flash differed by -4.1 points (interval -13.4 to 5.8), which is no detectable difference. deepseek-v4.1-flash-1017 was worse, by 12.4 points (interval -21.7 to -3.5), with a pooled pass rate of 49.2 percent.
Uncertainty
97.5 percent paired bootstrap over problems. Cost was reported incompletely for the candidates, so its comparison is a lower bound only.
Decision
The base model stays. The screen's rule picked it.
What it taught
A cheaper model's price advantage is not evidence of equal quality. Pair the comparison on the same problems and read the interval, not the two means.
Setup and evidence

Setup. The 86 CVDP evaluation problems, the same LangGraph agent harness for every arm, the base model run once and each candidate two or three times. Pre-registered before any scored run: the problems, the settings and the rule for picking. Pass rate is the hidden benches' verdict; no language model scores anything.

glm-5.3-flash pooled pass rate: 57.6 percent over its runs; the interval includes zero, so this is a null, not a tie.

Evidence: #4 #6 PREREG.md paired_eval86.md

Inconclusive1 Nov

Which open-weight model to fine-tune

Hypothesis
Which of two open-weight code models is the better base for a later fine-tune?
Result
The spend guard ended 65, 52 and 42 of the 86 problems in the three runs. Under the pre-registered rule all runs are void, so no model is recommended.
Uncertainty
None. No paired comparison was made, because every run was void.
Decision
No base was chosen. The result is recorded as inconclusive.

Win1 Nov

Do the agent's own tests detect broken designs?

Hypothesis
Does a test bench that passes on the correct design also fail on a design with a deliberate fault?
Result
The first full run killed 90.48 percent of the mutants (2 survived, both reset-state faults no test looked at). The bound checkers killed none that the bench missed (90.48 percent). After a test for reset state was added, 100 percent.
Uncertainty
One design, one seed, hand-written mutants. A score, not an estimate with an interval.
Decision
The first-run figure is the unbiased one. The harness now runs mutation testing itself, and V3 floors that the agent's plan cannot lower are fixed in a file.
What it taught
A bench can look complete and miss reset-state faults. Measure it with mutants, and report the score from before the bench was fixed.
Setup and evidence

Setup. 21 hand-written mutants (operator, constant, condition and reset faults) of T1, run against the bench alone and against the bench with the bound assertion checkers. First full run, then a re-run after one new test.

A live run later set its own mutation threshold low in its test plan and passed V3 on few evaluated mutants. The floors are 70 percent mutation score and 75 percent toggle coverage, with at least 10 mutants evaluated.

Does the agent's own check catch a misread spec?

Hypothesis
When the agent's own tests and gates pass, do the hidden tests also pass?
Result
13 of 21 runs passed every hidden test. 6 were escapes: the agent's own checks passed and the hidden tests failed, every one from reading the spec differently from the tests.

Development tasks, changed between runs: no interval is meaningful, and none is claimed as a pass rate for new tasks.

Stopped, no score9 Nov

The first held-out evaluation (eval-1): stopped, no score

Hypothesis
What fraction of 19 held-out tasks does the agent solve, with 3 runs each?
Result
Stopped before analysis. 14 of the 57 run slots had been launched and 2 runs were scored; 9 ended as not run because Claude Code updated itself between two launches and the agent refuses an untested CLI version. No result is reported.
Uncertainty
None. No score exists.
Decision
The project owner stopped it, because it could not finish in time and the benchmark was too small for the goals. This was a scope decision, not a reaction to results. The tag stays as a record. Later evaluations pin the CLI binary with a version check, and a new tag and pre-registration come with a baseline evaluation on the larger benchmark.
What it taught
Pin every tool that is not under test, including the one that runs the agent. Some held-out tasks had their pass counts seen, so they moved to development, and no fix was derived from them.
Setup and evidence

Setup. Pre-registered before any scored run: 19 tasks, 3 runs each, scored by hidden tests, a task-level bootstrap, with a planned half-width of 17.5 points. The agent, knowledge bank and benchmark were frozen at the tag eval-1.

Win10 Nov

Does a deterministic CDC gate beat the tool's own report?

Hypothesis
Does a gate that checks the structure of the asynchronous paths and simulates with injected synchroniser delay catch clock-crossing faults that the tool's own CDC report does not?
Result
The tool's CDC report alone flagged 5 of the 10 faulty designs. The new gate flagged 10 of 10, with 0 false alarms on the 12 correct designs. The table was identical on the re-measurement on Vivado 2026.1.
Uncertainty
Fixtures are small hand-written designs, not a sample of real designs, so this is a detection table, not a rate. The simulation injection is cycle-level with no timing window. Faults found in the soak rig (M9 and M11) were not re-run on Vivado 2026.1 and are withdrawn.
Decision
The gate was merged into the flow and replaces reliance on the tool's report alone.
What it taught
Where the standard tool is silent, a small deterministic check can be decisive. Seed the fault yourself and show which check sees it.
Setup and evidence

Setup. 12 correct and 10 deliberately faulty small designs (fixtures), synthesised on Vivado 2026.1, xc7a100tcsg324-1. Columns: the tool's CDC report alone, a structure check, a cycle-level simulation with injected delay (three seeds) and the new gate.

Null11 Nov

Does routing the right skill to a role help?

Hypothesis
Would a router that picks skills for each role, and a hybrid keyword and vector index, help the agent find the right knowledge?
Result
Retrieval recall at six skills was 0.394 for the plain index, 0.306 for the hybrid index and 0.1 for the router's classifier. End to end, hidden-test passes were 0 with the router off and 0 on; stage 2 gates passed in 1 and 0 runs.
Uncertainty
Three runs per arm cannot show a difference in pass rate, and none is claimed.
Decision
The router stays behind a flag and is not adopted.
What it taught
In the traces the roles hardly used the new tools and kept calling the old one, so the intervention was never exercised. Check that a tool is used before measuring what it does. The by-product was a bug where a multi-skill load silently dropped the middle of each skill, fixed on one case.
Setup and evidence

Setup. Retrieval on 12 labelled development tasks against a catalogue of 157 skills, then an end-to-end comparison with the router off and on, 3 runs per arm, the low-cost model gpt-6-luna, stopping after stage 2. Pre-registered; later arms marked post hoc.

Win11 Nov

Do timing exceptions hide failures, and can a gate see them?

Hypothesis
Can a timing exception (a false path or multicycle path) hide a real failure, and does a gate flag the harmful ones without flagging the correct ones?
Result
The gate's verdict matched the expected verdict on 14 of 14 drills, of which 10 were expected to be flagged. A further row of the 15 is an alternative design with no exception and no expected verdict.
Uncertainty
Fixtures, one run each. The drills show the gate's logic; they say nothing about how often real designs have such exceptions.
Decision
The exceptions gate is part of the build flow. A later fix stopped it failing every build with a debug core, whose own ignored exceptions it had counted as the design's.
What it taught
A gate that fails every build is as broken as one that passes every build. Test it on a clean design and on a faulty one.
Setup and evidence

Setup. 15 drill designs on Vivado 2026.1, each with an exception that is either correct or harmful (too broad, a typo that matches nothing, a false path over a binary bus), re-timed without the exception and after routing.

Mixed11 Nov

Do more threads or a build cache make Vivado runs faster?

Hypothesis
Does the thread count change results or time, and can a cache and resumed builds cut an agent run's build time without changing the result?
Result
Placement and routing hashes and slack were identical at every thread count. The mid-size design c13 took 546 s at one thread and 413 s at four; the small design c10 showed no measurable gain. The cache cut one agent run's build sequence by 76 percent on c10 and 80 percent on c13, with identical hashes and slack.
Uncertainty
Two runs per thread count, other jobs shared the PC that night, so wall times carry that load. The no-cache time is modelled from the measured fresh-build stages.
Decision
The build cache is part of the flow. Threads stay at one under the memory cap, since results are identical and the gain was small.
What it taught
Check the result is identical before you celebrate a speed-up. Several figures from the earlier release were withdrawn because they could not be repeated under the new memory cap.
Setup and evidence

Setup. Fresh builds of three designs on Vivado 2026.1, one at a time under a 6 GB memory cap, at one, two and four threads, and one agent run's build sequence replayed with and without the cache.

Evidence: #118 README.md results.md

Mixed12 Nov

Does changing the harness around the model change cost and success?

Hypothesis
Do context management (H1), hang protection (H2) or typed report digests (H9) cut tokens, cost or wall time without losing hidden-test passes?
Result
H1 lowered cost by 32.8 percent (interval -53.3 to -4.3) but tokens by 65.6 percent with an interval that includes zero (to +0.9), so it met the rule on one reading and not the other. Its wall time fell 18.1 percent but the interval includes zero once the blocks with a run stopped by the time limit are left out. H2 lowered cost by 1.5 percent (interval -31.4 to 12.6): no difference detectable. H9 lowered cost by 16.1 percent, below the bar. 5 of 12 blocks passed the hidden tests in the baseline and 5 in H1; two of the 4 tasks were passed by no arm.
Uncertainty
Percentile bootstrap over the 12 blocks, paired against the baseline. With this few blocks only a very large effect is visible.
Decision
No arm was adopted by the pre-registered rule. The project owner then made H1 the default for development runs after seeing the data, which is recorded as a decision made after the data. Re-measure on more tasks before quoting a saving.
What it taught
The adopt rule said "tokens per run (and cost)" without saying how to read "and". Write the rule so it cannot be read two ways. H2 solved a problem that was too rare in the round to compare.
Setup and evidence

Setup. 4 tasks, 3 repeats, four arms (the baseline A0 and H1, H2, H9), 48 valid runs of 51, the low-cost model gpt-6-luna, stopping after stage 2 (no Vivado). Each task and repeat is a block with all four arms in rotated order. Pre-registered adopt rule: a primary metric at least 30 percent better with an interval that excludes zero, and no loss of tests passed.

Mixed12 Nov

Can the agent repair a timing miss by itself?

Hypothesis
Can a loop that edits the RTL, re-checks it on an independent bench and rebuilds close a timing miss, and does a design-time plan help?
Result
c13_hough_lines closed in one iteration, from -0.225 to 0.61 ns of worst slack without the plan. Of 3 seeded misses, 1 closed; c14_int8_dot_requant stopped at the 5-iteration limit at -5.27 ns (from -24.601) and c11_nco_mixer at -1.569 ns (from -4.401). When the RTL was written with the plan, none of 6 attempts passed the hidden bench, so no first build with the plan exists.
Uncertainty
None: one run per case, so these are illustrations, not rates. Two builds of the same unchanged RTL differed by about 0.05 ns of slack.
Decision
The loop stays as a repair tool with its limits stated. The plan's comparison on other designs is not run.
What it taught
An early with-plan run accepted a design whose core had been removed by synthesis; Icarus allowed two blocks driving the same registers and Vivado tied them to ground. That run is not counted, and it is why a synthesis guard exists. A passing simulation is not a passing build.
Setup and evidence

Setup. Vivado 2026.1, xc7a100tcsg324-1, whole-board builds. The RTL writer was gpt-6-luna. One run per case: c13_hough_lines with and without the plan, and 3 seeded misses made by raising a task's clock. The hidden bench is always the acceptance check.

The method, in plain words

Hidden tests decide

A task's tests are written from its spec and never shown to the agent. Passing means the hidden tests pass, the code-run gates pass and, for hardware tasks, the board agrees. The agent's own testbench never counts, and no language model ever produces a score.

Repeats and pairs

The agent is stochastic, so every task runs several times (3 in the first evaluation) and two versions of the agent are compared on the same tasks, with an interval, not two means. With 19 tasks a pass rate was planned to be known to about plus or minus 17.5 points, which shows a large difference and not a small one.

Development and held-out

Development tasks are for finding and fixing faults. Held-out tasks decide, are touched rarely, and a fix is never derived from them. Where one was seen, as in eval-1, it moves to development.

Nothing leaks

Knowledge comes from documentation, never from the benchmark. A leak guard fails the site build if text from private tasks appears, and during scored runs the agent searches only a frozen library.

Pre-register, then pin

Before a scored run the arms, tasks, repeats, comparisons and stopping rules are written down and committed. The CLI, model and tool versions are pinned and recorded with every run.

Change one thing

A measurement changes one thing at a time. When several changes ship together, nothing is attributed to any of them. A correctness bug in the measuring instrument is the exception, and is fixed on one case.

Retire, do not delete

An evaluation is retired when it is saturated, no longer measures what is wanted, is contaminated, is not comparable after a change to the tools, or is too noisy. It becomes a regression suite. eval-1 was retired by a scope decision before it produced a score.

The improvement loop

Every fault found in a run or a review becomes a recorded finding: the cause class, the fix, and the pull request. Reading single runs generates hypotheses; the experiments above decide. A fault in the measuring instrument is fixed on one case, with no statistics.

Timeline of the design

The order the agent was built in. Each step says what changed, why, and what the evidence showed.

  1. 30 Oct

    A flow that a board can check

    Changed. The Vivado flow, its gates, an ILA debug core and a test shell on the Nexys A7 board, then automated bring-up that programs the board by its JTAG serial number and runs tests against a model.

    Why. A design only counts when hardware shows it behaving as specified. Everything later is judged against that bar.

    What the evidence showed. The first design, T1 (a dimmer and counter), went from source to bitstream to a board test with no hand steps.

    Evidence: #1 #2 #9 f0b methodology.md

  2. 31 Oct

    Which model writes the RTL

    Changed. A pre-registered screen of cheap open-weight models against the base model on 86 problems.

    Why. Cost decides how many runs the project can afford, so the model choice was measured rather than assumed.

    What the evidence showed. Neither cheaper model beat the base, and one was worse by a margin its interval excludes from zero (card below). See the experiment card.

    Evidence: #4 #6 #10 f1b

  3. 1 Nov

    Verification stages V0 to V3

    Changed. A verification backbone of four stages, from requirements tracing to coverage and mutation testing, on a simulator-portable stack.

    Why. The agent's own testbench never counts as a pass. A model's test shares its misreading of the spec, so checks must come from code and from tests the agent does not see.

    What the evidence showed. Mutation testing of T1's tests found two survivors that no test looked at, both reset-state faults (card below). See the experiment card.

    Evidence: #11 04f verification.md

  4. 2 Nov

    A graph of stages and roles, two ways to run a role

    Changed. A harness-neutral agent core with an MCP tool server, a stage machine in plain code, role agents (Clarifier, Modeller, Verifier, Designer) on Deep Agents, and a second arm that drives the same roles through Claude Code.

    Why. Keeping the stage order in code, not in a prompt, makes each stage gate-able. Two harnesses let the same task be run on different models without changing the graph.

    What the evidence showed. The first runs failed at stage 2 for harness reasons (spec items lost silently, stale test files, a model API mismatch). The fixes came out of one diagnosis.

    Evidence: #12 #13 #14 #15 agent_core.md agent.md

  5. 3 Nov

    Per-role models and the test writer

    Changed. Each role picks its own model and effort. The test-writer role's failures were diagnosed from run records and fixed in code.

    Why. One role spent the whole stage budget so the Verifier never got a turn, and a repair visit deleted the Verifier's own files.

    What the evidence showed. The fixes are plain code (a turn reserve, files kept across repair), not prompt wording.

    Evidence: #18 #21 role_models.md test_writer.md

  6. 4 Nov

    A frozen benchmark with hidden tests

    Changed. Benchmark tasks with a spec, hidden tests the agent never sees, reference RTL and mutants, split into development and held-out, then reviewed and re-frozen; a course tier of larger projects added.

    Why. Success has to be decided by something the agent cannot influence. Development tasks are for fixing the agent; held-out tasks are for deciding.

    What the evidence showed. Review found blockers and fixed them before any scored run. Every later change to frozen content has a dated amendment.

    Evidence: #19 #32 #33 #42 AMENDMENTS.md FROZEN.md

  7. 5 Nov

    Gates the agent cannot lower

    Changed. The harness runs coverage and mutation testing itself, gate messages name what is missing, and V3 thresholds have floors the agent's plan cannot lower.

    Why. A live run set its own mutation threshold low in its own test plan and passed V3 with few mutants evaluated.

    What the evidence showed. The floors are now fixed numbers in a file the agent never writes (mutation score floor 70 percent, at least 10 mutants evaluated).

    Evidence: #27 #31 #34 #40 #41 verif_floors.yaml 05l

    Changed. Runs of course tasks on the Claude Code arm, each followed by a fix to the agent for the fault it exposed.

    Why. Reading single failed runs generates hypotheses cheaply. A fix that corrects a measuring-instrument fault needs no statistics.

    What the evidence showed. 6 of 21 development runs were escapes: the agent's own checks passed and the hidden tests failed (card below). See the experiment card.

  12. 12 Nov

    Vivado 2026.1 for everything published

    Changed. The flow moved to Vivado 2026.1 and every published number was re-measured on it or withdrawn.

    Why. A number measured on an older release does not describe the tool the reader will use.

    What the evidence showed. Some results were identical on the new release; some could not be repeated and were withdrawn. Vivado 2026.1 needs its free licence installed to start at all, which the earlier release did not.

    Evidence: #126 #128 #134 33_vivado_speed_2026_1 vivado_2026_1_remeasure

  13. 12 Nov

    A closure loop and a design-time timing plan

    Changed. When a design passes simulation but misses timing, a loop edits the RTL, re-checks it on an independent bench, rebuilds and repeats; a plan chooses DSP and block RAM use before the first build.

    Why. Timing repairs are routine work that the agent should do itself.

    What the evidence showed. One case closed in a single iteration both with and without the plan, one seeded case also closed, and two seeded cases stopped at the iteration limit (card below). See the experiment card.

    Evidence: #140 62a_closure closure_loop.md

  14. 13 Nov

    The agent documents its own work

    Changed. A documentation standard and checker, a handover file that code fills from the run's records, and a DOC step in which the Designer writes the prose.

    Why. Anything the agent produces is held to the standard of a human engineer's hand-over, so the next engineer can pick it up.

    What the evidence showed. An independent re-review of three agent-written handovers found claims the records did not support, and the DOC step's prompt and checks were tightened.

    Evidence: #154 #157 #159 documentation_standard.md 68_agent_docs

  15. 14 Nov

    One check tool with a registry

    Changed. A single check tool and registry, with reset rules; the first version of the reset check read source text with regular expressions.

    Why. Gates should be code with tests. A text scanner is not a sound HDL front end.

    What the evidence showed. Three adversarial reviews each defeated the regular-expression scan, so it was replaced by elaboration with Yosys and slang or GHDL, failing closed.

    Evidence: #163 #164 doccheck.py

Limits

The findings listed are the ones with a recorded fix, not a complete count of the agent's faults. Most experiments ran one model on a small task set, and each card says so. Results measured on an earlier Vivado release and not repeated on Vivado 2026.1 are not shown. The list of merged pull requests is a snapshot from the day the page was built.
