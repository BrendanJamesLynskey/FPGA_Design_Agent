Verification

How the designs are verified

Every design the agent makes is checked by several techniques that fail in different ways, and none is trusted alone.

Best evidence, each from deliberately seeded faults written by the project's own author: a wrong-pin fault that passes simulation and every check inside the FPGA was found only by measuring the board's audio output; and a gate for crossings between clocks flagged 10 of 10 such faulty designs where the vendor tool's own report flagged 5, with 0 false alarms on 12 correct designs. The gate was built after these faults were known, so this is not a held-out result.

Nulls and gaps, stated first: the agent's own tests let 6 of 21 development runs through that the hidden tests then failed; the independent spec-only test writer caught one of five known escapes; mutation testing found 2 survivors the bench missed on its first run; and the formal proofs are bounded, so they say nothing beyond the depth they were run to.

How to read this page

Terms: a seeded fault is a deliberate defect put into a design to see whether a check notices it. T1 is the hand-written reference design. V0 to V3 are the four verification stages, and a gate is a check run by code that stops a stage if it fails. The Modeller, Verifier and Designer are the agent's roles for the reference model, the tests and the RTL. A scoreboard compares a design's outputs with a model. Toggle coverage counts signal bits that changed. Each technique below has the same three parts: what it is and what it can and cannot find, where the agent and the flow use it, and the measured evidence. Engineering detail is in the drawers. Every number is read from a committed result file, which shows where it came from, not that the method is sound.

The techniques, one by one

Directed and self-checking simulation

What it is
A test drives a design's inputs and compares its outputs with a reference model, so the test says pass or fail by itself. The tests are written in Python with cocotb and run on Icarus and Verilator for SystemVerilog, and VHDL runs through GHDL. The reference model is written by a separate role, the Modeller, which never sees the RTL.
Catches
Wrong behaviour on the cases the tests drive: wrong values, wrong timing against the model, missing features.
Cannot find
Anything no test drives, and any misreading of the spec that the test author shares with the designer, because the model, tests and RTL can all agree on the wrong reading.
Where it runs
Stage 2 writes the model first, then the tests, then the RTL; the V2 gate requires every planned test to pass on every seed. The Verifier role writes the tests, the Designer repairs the RTL, and code runs the gates.
Evidence
On the T1 reference design 15 tests pass on seeds 1, 2 and 3 under Verilator 5.048 and under Icarus 12, with 23 assertions bound and none failing. VHDL (GHDL 4.1.0) is a gap: a model's first translations passed 0 of 5 board tasks, all failing on one naming mistake, and the end-to-end agent writing VHDL has passed 0 of 4 runs.
Engineering detail and records

The simulator matrix decided the stack. Covergroups are unsupported in every free simulator but one, so the bench is Python and runs everywhere.

The V1 gate fails unless the bench uses the blind model. The check is bench_uses_blind_model.

GHDL's back end has no code coverage for VHDL, so VHDL designs have no coverage figures.

Hidden tests decide the result, not the agent's own tests

What it is
On benchmark tasks, a design counts as passing only if tests written by a separate author, against an independent model of the full spec, pass. The agent never sees them. Its own testbench never counts, because a model's tests share its misreading of the spec.
Catches
A design that satisfies the agent's reading of the spec but not the real one.
Cannot find
It cannot tell the agent why it failed, and it can only judge tasks that have hidden tests.
Where it runs
Used only when scoring benchmark runs, outside the agent's loop. In the loop the agent can add an optional extra test writer, the spec-test role, which writes its own bench from the spec alone and never sees the RTL.
Evidence
On 11 development tasks, 13 of 21 runs passed every hidden test, and 6 runs were escapes: the agent's own checks passed and the hidden tests failed. 5 more runs had a gate fail, were repaired and then passed, and 3 were stopped by the agent's own gates although the hidden tests would have passed. The spec-test role, replayed on saved designs, caught one of five known escapes and failed 0 of 4 correct designs.
Engineering detail and records

Held-out tasks are kept in a private repository, and a leak guard fails the site build if a 80-byte window of that material appears in it.

Every escape so far has one cause, a spec-interpretation difference. The development tasks are the ones used to find and fix faults, so these rates are not a held-out score.

The spec-test role is off by default. Its replay used saved final designs and no RTL repair.

Constrained-random stimulus, functional coverage and code coverage

What it is
Random stimulus within legal limits finds cases a person would not write. Coverage measures what was exercised: functional bins (planned events), line, branch and toggle coverage of the RTL, and cover properties that must be reached. The verification stages V1 to V3 say what each requires: V1 traces every spec item to a check, V2 needs the tests and the constrained-random test to pass with the assertions bound, V3 needs coverage at the floors on several seeds.
Catches
Untested code and untested events, and, by the unreached cover properties, assertions that can never trigger.
Cannot find
It cannot show that what was exercised was also checked. A bin is a count of events the bench caused, not evidence it compared them with anything.
Where it runs
V3 sits inside stage 2. The floors are in a fixed file the agent cannot write; a plan may raise a threshold, never lower it. Only a waiver with a reason excuses a named bin or cover property.
Evidence
T1 reaches V3: 69 of 69 functional bins, line coverage 100 %, branch 100 %, toggle 87.24 % (759 of 870 points). The 111 unhit toggle points are structural: bits no register drives and blank display digits.
Engineering detail and records

The floors are functional bins 100 %, cover properties 100 %, line 90 %, toggle 75 %, mutation 70 %, and at least 3 seeds.

The thresholds were set after seeing the first run, so they are defaults for later benches, not a calibrated standard.

Mutation testing

What it is
Seed one small fault into a copy of the design, run the tests, and see whether they fail. A fault the tests miss shows a gap in the tests. It is used on the agent's own tests, on the IP benches and on the hidden tests of the benchmark.
Catches
Tests that run the code but do not check what it does, such as reset states no test looked at.
Cannot find
It cannot count a fault that changes nothing visible as caught. Such an equivalent mutant shows as a survivor, so a score below the top is not always a weak bench.
Where it runs
Stage 2's V3 gate, through the mutate step the harness runs itself. A mutant counts as caught only when its run fails. A mutant whose copy does not compile is excluded, never counted as caught, and a score counts only when at least 10 mutants were evaluated.
Evidence
T1: 21 mutants, 90.48 % killed on the first full run by the bench alone; the bound checkers killed none the bench missed. The 2 survivors were reset-state faults, so a test was added and the final score is 100 %. The generic tool agrees: 21 of 21 killed. Faults seeded into the IP benches: 56 of 56 in the network blocks, 10 of 10 in the MAC, 5 of 5 in the CRC instruction and 19 of 19 in the instrument library were caught.
Engineering detail and records

One design, one seed and hand-written mutants for the first figure. The IP-bench faults were written by the same agent that wrote the benches, so a full catch rate there shows the benches are not blind to the faults their author thought of.

Mutation is a heavy local job and is not in CI; CI gates read the committed result.

Assertions and protocol checkers

What it is
An assertion is a rule written beside the design that must always hold, for example "a response never arrives before its data". A protocol checker is a set of such rules for a bus. The AXI4-Lite and AXI4-Stream checker here is a block that runs in simulation and in the FPGA, and was compared with AMD's own checker. A separate monitor flags a response that never comes.
Catches
Protocol violations at the cycle they occur, including those a data comparison would never see, such as a held request dropped.
Cannot find
It cannot see data errors. A wrong byte on a legal transfer passes every protocol rule; that is the scoreboard's job. A rule that never fires may be broken, which is why every rule is also shown firing on its seeded violation.
Where it runs
Bound into the bench at V2 (the check is assertions_bound_zero_failures). The same checker is built into the board design and reports rule counts over the serial shell. The missing-response rule exists because AMD's checker has no such rule and did not flag a lost response on AMD's own DMA core.
Evidence
On the board, 17 of 17 planned runs passed. Of 8 seeded bugs, the rules built here flagged 6, the data checks 3, and AMD's checker 5 (it watches only the AXI4-Lite bus, and the byte-strobe bug breaks no protocol rule). Every data bug was caught by the scoreboard or the stream receiver instead (matrix above).
Engineering detail and records

The checker's own proofs and its mutants are in the formal section below.

The missing-response monitor is bound into the register-block bench; a response that never comes fails the test.

Formal verification with SymbiYosys

What it is
A solver searches every input sequence, not a sample, for one that breaks a property. Bounded proofs cover up to N clock cycles; cover tasks show the property can be reached; and k-induction proves a property for all cycles when the block's state is constrained enough. The checker is proved, then attacked: each copy of it with one deliberate fault must fail some proof.
Catches
Corner cases no one thought to simulate, such as a rare back-to-back sequence, and a checker that is silent because it is broken.
Cannot find
A bounded proof says nothing about cycles beyond the depth of a bounded proof, or about a datapath too large for the solver. Time constants are shrunk for the proof, so the proof is of the structure at that parameter, not of the board value. The solver reads a subset of SystemVerilog.
Where it runs
A formal method per requirement is planned at clarify and discharged at V2 only when both its bounded and cover tasks pass. When SymbiYosys is not installed the flow never claims a proof: the method must be re-planned, with a reason.
Evidence
AXI4-Lite rules: 21 of 21 proofs pass at depth 20 and 37 of 37 checker mutants are killed (12 of them semantic). Stream rules: 11 of 11 proofs and 16 of 16 mutants. A k-induction proof of the trading interlocks at depth 30 and of the MDIO frame logic hold for all cycles. PDR proved 3 of 3 further blocks for all cycles. A fault restored in the ICMP echo block fails its proof at step 60.
Engineering detail and records

14 of 14 network-block jobs pass; the table below lists each with its method.

The checker mutants are attacked at depth 12, lower than the 20 of the proofs on the unmodified checker.

The tools differ by record: Yosys 0.33 for the checker proofs and Yosys 0.70 for the network blocks.

Clock-domain-crossing verification

What it is
A signal that crosses between two unrelated clocks can be sampled mid-change. Three checks look for unsafe crossings: AMD's report_cdc, a structural check of the synthesised netlist, and a simulation that randomly delays each synchroniser by one cycle to expose designs that only work when the crossing is lucky. Reset synchronisers get the same treatment.
Catches
A bus crossed bit by bit, two synchronisers whose outputs are combined, a pulse into a level synchroniser, a reset used across clocks.
Cannot find
It cannot model real metastability or route skew; the simulation adds a whole cycle and has no timing window. A design with no crossing passes at once.
Where it runs
The structural check is a synthesis gate (post_synth_cdc_structure_clean); the injected simulation runs the design's own tests plain and with injection in the V3 stage (cdc_injection_clean).
Evidence
Of 10 faulty designs, report_cdc alone flagged 5, the structural check 9, the injected simulation 3, and the gate, which runs the structural check and the injected simulation, flagged 10, with 0 false alarms on 12 correct designs. The table is from Vivado 2026.1.
Engineering detail and records

Synthesis-only reports; no place and route, no board.

The soak rig's report_cdc results were not re-run on Vivado 2026.1 and are withdrawn from this site.

Static checks

What it is
Rules checked without running the design: lint (the FDA-HDL coding standard), AMD's methodology and DRC reports, and a single agent tool, check, that runs all of them and returns a short digest instead of the raw reports. The reset check decides from the elaborated design, and a netlist scan after synthesis catches resets that elaboration cannot see.
Catches
Asynchronous resets, mixed reset polarities, resets crossing clocks, logic driving a reset, and other rules a simulator never executes.
Cannot find
A synchronous reset folded into the data logic leaves no row in the scan. A passing check does not mean the design is correct, only that it follows the rules.
Where it runs
The sign-off gate post_synth_resets_clean and the Designer's check tool share one registry, so a finding means the same thing in the loop and at sign-off.
Evidence
The reset check's netlist part was attacked with 26 small designs built with Vivado 2026.1. The reset source check went through three review rounds that broke its earlier text scanner, which is now replaced by elaboration; both wrong passes the attacks found were fixed.
Engineering detail and records

A module exempt by its name alone let a user module called reset_sync pass; both of those wrong passes were fixed and are covered by regression cases.

Findings that are not rule failures are listed in the results README.

Hardware-in-the-loop and board verification

What it is
The design is built, programmed on a Nexys A7 board and tested against the same model the simulation used. Seeded hardware faults check that the checks fail when they should, and the board's temperature and rails are recorded as evidence that the run was inside its operating conditions.
Catches
Faults only a real board shows: a wrong pin, a clock that behaves differently, a bus at speed.
Cannot find
It cannot reach internal state beyond what the shell and the on-chip logic analyser can read, or measure what no instrument was connected for.
Where it runs
Stage 9 (V-HW). The run always stops for a person before anything touches the board. Runs are planned before the board is used, and each passes when its verdict is the one the plan expects.
Evidence
The AXI plan passed 17 of 17 runs on Vivado 2026.1, inside the recommended operating conditions at every sample. The same programs in simulation gave the same transaction digest and cycle count on 13 of the 13 runs against our own logic; the other 4 use a vendor block-RAM core on the board and are compared by transactions and verdicts only. The pin fault (below) passed 7 of 7 self-checks and failed only at the jack.
Engineering detail and records

Runs on the vendor's block RAM core are compared by transactions and verdicts only; the simulation uses a memory model there.

Instruments that were not connected (a logic analyser, a scope, a spectrum analyser) were not measured; their drivers are tested on synthetic data only.

Requirements traceability

What it is
Every requirement in the spec names how it will be shown to hold, and a table links each one to the test or proof that shows it, the result, and the coverage. Gates name any requirement, test or coverage hole left without evidence.
Catches
A requirement nobody tested, a test that checks nothing in the spec, and evidence that went stale after a requirement changed.
Cannot find
It cannot show a design meets requirements nobody wrote. It is a record of what was verified; it is not a claim of compliance with any standard.
Where it runs
Recorded, not a stage-exit gate: a run can finish with failing traceability gates and the review page shows them. The clarify gate rejects vague or compound requirements.
Evidence
T1: 11 requirements with 14 proof methods, 56 of 57 tests and properties citing a requirement. 3 deliberately broken T1 runs were each caught by exactly one traceability gate, while every simulation still passed.
Engineering detail and records

The three broken runs deleted a requirement's only test, added an untagged test, and added an RTL branch no test reaches.

The agent-side pieces are covered by unit tests only; no new agent run used them yet.

Adversarial review of the checkers themselves

What it is
A check that passes everything is worse than none, so each checker is attacked: reviewers and the author try to build a design it should flag and does not. A wrong pass is fixed, and the attack becomes a regression case.
Catches
A checker that is exempted by a name, misses a primitive, or folds a fault away.
Cannot find
It cannot find a fault in the attackers' own blind spots. Rounds of review on the reset check found faults each time, so another is not ruled out.
Where it runs
Part of building each check; the findings are in the improvement loop of the how-it-was-built page, which lists 19 faults with a recorded fix.
Evidence
The 26 attack designs of the static-checks card are one such attack; the how-it-was-built page lists every finding and its fix.
Engineering detail and records

Findings in the measuring instrument itself are fixed on one case, with no statistics.

Formal proofs: what bounded means

A bounded proof checks every input sequence up to N clock cycles and says nothing about cycle N plus one. An unbounded proof covers every cycle. k-induction shows that if the property holds for k cycles in a row it holds on the next one, but it needs the block's internal state to be constrained enough to make that step true. PDR (property-directed reachability) searches for that constraint itself.

A null: k-induction of the MAC FSMs returned unknown and those tasks were removed, so the MAC state machines are proved only to a bounded depth.

Proofs for every cycle

Unbounded attempts on the AXI4-Lite checker, the stream checker and a generated register block, run with Yosys 0.70 and recorded whatever they returned. k-induction returned unknown on 3 of 3: it could not show the step case without a hand-written invariant, and the cause was not investigated further. PDR proved 3 of 3, so for these blocks the properties hold for every cycle, not only to a depth. The property for the checkers is that they never fire on legal traffic; for the register block it is the slave's side of the bus rules. The assumptions are the ones the bounded proofs use, and those proofs have cover tasks that reach the interesting events, so the assumptions are not contradictory.

A real counterexample

A real formal failure. The checker was given one deliberate fault: it counts a write response as early only when no address has been seen, ignoring the write data. The proof "whenever the rule is broken, the checker must flag it" then fails at step 3 of the search to depth 12. Drag the slider to replay the trace the solver found.

The checker flags at step 1, when the response comes with the address, and is silent from step 2 on, although the write response is still waiting and no write data was ever sent. The solver found it without being told where to look; a directed test would need someone to think of the case.

Equivalence checking

Equivalence checking asks a different question: are two versions of a design the same? eqy compared the generated register block before and after the interface-profile change, and two profiles that are meant to differ. A pair that is meant to be equal must prove equal, and a pair that is meant to differ must be reported different.

Limits

Everything here is measured on small blocks and a few designs: the hand-written T1 reference, the AXI checker and the network blocks. A technique that caught every seeded fault shows the faults were findable by it, not that no other fault exists; faults written by the same author as the checks share their blind spots, which is why the hidden tests and the board are kept separate. Formal results are bounded unless stated. Results not repeated on Vivado 2026.1 are not shown. The map of techniques to checks is the author's reading of the flow's code; the checks it names exist and the test suite verifies that.

How each check was found and corrected is on the how-it-was-built page; the documents are docs/verification.md and docs/traceability.md.
