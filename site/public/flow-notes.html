1. AMD's CDC macro constraints are missing in the batch flow

Built and verifiedone probe design, two macros

Problem

The xpm_cdc macros are AMD's ready-made clock-crossing circuits (UG974). Each one relies on timing exceptions that AMD ships as scoped constraint files, not inside the RTL. If those exceptions are not applied, the tools time the crossing as an ordinary synchronous path between two unrelated clocks, and a correct design fails timing.

Standard Vivado

The agent builds in non-project mode (read_verilog then synth_design). There the scoped files were not applied. On a probe design with one xpm_cdc_single and one xpm_cdc_gray between a 10 ns and a 7 ns clock (Vivado 2025.2, xc7a100tcsg324-1), report_cdc showed Exception "None" on both crossings and the clk_a to clk_b setup slack was -1.364 ns on 5 failing endpoints. The CDC gate did not notice: report_cdc says nothing about an exception that is absent. The only sign was the negative slack, which the agent could only have cleared by writing its own exceptions or a blanket asynchronous clock group, the very thing that hides real crossing bugs (card 3).

This flow

flow/xpm_cdc.tcl runs right after synth_design and applies the same rules by cell name: a false path to the first stage of each xpm_cdc_single and reset synchroniser; set_max_delay -datapath_only plus set_bus_skew for each xpm_cdc_gray; set_max_delay -datapath_only on the data of each xpm_cdc_handshake. A design with no XPM macros gets no exception. The rules were first proven in the CDC soak rig build.

Evidence

Setup slack on the clk_a to clk_b path of the probe design. Hatched bar: a violation.

The same probe was run once before the fix and once after, through the flow's own build script. The probe is one design with two macros; it shows the gap and the fix, not a rate. xpm_cdc_pulse and xpm_cdc_async_rst get no exception yet, and xpm_cdc_array_single has not been checked.

2. report_cdc cannot see every unsafe crossing

Built and verifiedon fixtures; no agent run yet; no board result yet

Problem

A crossing can be wrong while every synchroniser looks valid to the tool: a multi-bit binary counter crossed bit by bit, a one-cycle pulse into a level synchroniser, two flags synchronised separately and then compared. report_cdc checks the structure it recognises and the constraints it can see; it does not run the design.

Standard Vivado

On 12 of the mutants of the CDC soak rig (deliberately broken crossings, one fault each), report_cdc alone flagged 5. It passes M3, M5, M6a, M7, M9 and M11 as structurally valid synchronisers, and gives M1 only a warning. Before this work the agent's CDC gate was report_cdc Critical rows plus a text check that only looked inside one module.

This flow

Two further checks sit in the V3 gate. Structure: after synthesis the flow lists every flip-flop pin reached from another clock and classifies the crossing (synchroniser chain, XPM macro, constrained Gray or handshake, reset bridge, or unsafe), joining it with the exception report_cdc found. Simulation with injection: the design's own tests run again with every first synchroniser stage, and every XPM macro, replaced by a version that sometimes holds its old value for one extra destination cycle. A design that passes plain and fails injected fails the gate.

Evidence

On the fixtures, report_cdc alone flagged 5 of the 10 ported mutants. The new gate flagged 10 of 10 and passed all 12 correct variants. M9 and M11 (a FIFO or handshake reset on one side only) are not covered: the rig catches them by injecting on the release of an asynchronous reset, which the cycle-level model does not have.

Why a simulation with an extra cycle finds the tear

A bus crossed bit by bit is safe only if at most one bit changes at a time. A binary counter changes several bits at once, and each bit's first flop may resolve a cycle late. Step through a 4-bit counter crossing into a two-flop synchroniser, with and without the extra cycle, as a binary counter and as a Gray counter. Hatched cells are first-stage flops holding their old value for one extra cycle.

The frames come from site/flow_model.py, a small model of the same rule as the gate's injection. The source value changes every 4 destination cycles. A sampled value is torn when it equals neither the current nor the previous source value.

Not done

No agent run has used the new gate yet. The CDC rig's board results are not part of this page. The gate checks that a hand-built Gray bus carries its exception; it does not check the coding, so only simulation can catch a binary bus with a correct exception.

3. Over-broad timing exceptions hide real failures

Designed, not built as tasks

Problem

A model that cannot meet timing can make the failure disappear by writing a blanket set_false_path, a multicycle path or an asynchronous clock group over the failing path. The timing summary then reads clean.

Standard Vivado

Vivado applies any exception it is given and reports the remaining paths. Its methodology checks (TIMING-46 and TIMING-47 among them) flag some of these cases, but a passing slack figure alone does not tell a real pass from a hidden failure.

This flow

The planned constraint-grading tasks seed a real violation into the design: a true synchronous path that fails, a failing path between related clocks, an unsynchronised crossing. The task passes only if that violation stays visible after the agent's constraints are applied. A blanket false path, a clock group or a waiver on the seeded path fails the task, and a repaired twin of the design must meet timing with the same constraints.

Evidence

Schematic of the check: the same failing path, with and without a false path over it. No measured values.

The design is written down; the tasks are not built or run, so there are no results.

4. Gates that go further than Vivado's own pass or fail

Builtcovered by unit tests; no live run of the changed gates

Problem

A run can finish with a bitstream while a report is missing or the quality of the result is poor, and a test framework can report a skipped test without calling it a failure.

This flow
  • Quality-of-results gate. After routing, the score from report_qor_assessment must be at least 4 of 5.
  • A missing report fails its gate. A quality review found that a report which did not exist made its gate skip, and a skipped gate counted as a pass. When the build wrote its run record, a missing report now fails the gate.
  • A skipped test is not a pass. The review found that a cocotb test marked as skipped counted as passing the planned-test check, and that tests marked expected-to-fail turned a real failure into a pass. Both now fail, and a scan of the bench source flags the markers.
Sources
flow/gates.py; flow/verif_gates.py; tests under flow/tests.

5. Pblocks made after synthesis are soft

Measuredon the CDC rig

Problem

A pblock is a placement region. The CDC rig builds its regions in Tcl after synthesis to put each crossing at a known distance. Regions made at that point came out soft (IS_SOFT = 1), so the placer treats them as a hint.

Standard Vivado

About half of the destination cells were placed outside their region until IS_SOFT was set to FALSE.

This flow

The rig sets IS_SOFT FALSE on every pblock it creates. The agent's own flow creates no pblocks, and pblocks in its constraint file are read before synthesis, where they default to hard. Any future step that makes pblocks in Tcl after synthesis must set it too.

Sources
hil/cdc_soak/tcl (the build scripts).

6. The MIG wizard validates pins; scripted generation does not

Measuredtwo seeded faults; rule checker built

Problem

The DDR memory controller wizard (MIG) validates the chosen pinout against the memory's byte-group and bank rules on its pin-selection page, before it will generate the core. The agent works without the GUI: it writes the MIG project file and generates the core from a script.

Standard Vivado

In the wizard, a bad pinout is caught at that validation step. Generating the same core from a script (create_ip, the project file, then generate_target) skips it: the pins were not validated. A pinout with a byte-group fault generated with no message and the bad pins were written to the constraints file. A pinout with a duplicated pin also generated with no message, and the line for one data pin was silently dropped.

This flow

The knowledge bank's mig_pin_rules.py checks the memory pin rules itself. It flagged both seeded faults and passed the good configuration.

Not done

Whether implementing the MIG example design rejects a bad byte group has not been run.

Sources
Pin-check results in the private knowledge repository (tools/pin_xdc_check); the pin-planning grading design.

7. report_ssn is not available for every part

Measuredavailability only; no substitute built

Problem

Simultaneous switching noise (SSN) limits how many fast outputs can share a bank. Vivado's report_ssn estimates the margin for a pinout.

Standard Vivado

The report works on the Artix-7 100T part and on the Zynq-7000 part checked, and it flagged a deliberately overloaded bank. On the Kria K26 part it is not available.

This flow

The pin checks use report_ssn where the part supports it. The design-rule check and the spread metrics do not depend on it and stay on every part. No substitute for the SSN margin on the K26 part has been built.

Sources
Pin-check results in the private knowledge repository (tools/pin_xdc_check).

8. AMD IP models need xsim, which cocotb cannot drive

Planned

Problem

AMD's DSP cores (FIR, FFT, DDS and others) ship their simulation models in encrypted form. Only AMD's own simulator, xsim, and licensed commercial simulators can run them. Icarus, Verilator and GHDL cannot, and cocotb has no xsim back end, so the agent's usual test method does not reach a design that uses these cores.

This flow

Planned, not built: a file-based harness. Python writes the stimulus as text files and a seeded schedule of back-pressure; a generic SystemVerilog testbench reads them in xsim and writes every output beat to a response file; Python compares the response word for word with AMD's bit-accurate C model of the core where one ships. A synthesis run at the target clock checks timing and resources.

Status

Specified in the expertise survey. No code and no measurements yet.
