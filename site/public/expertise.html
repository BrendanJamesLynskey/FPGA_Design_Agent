Areas of expertise

FPGA design draws on many specialisms, from clock crossings to memory controllers. This page takes them one at a time and says, for each, what the agent knows, what its flow checks on every run, what has been measured and what is not yet shown.

Each area is a drawer. It opens with a few plain sentences, then the measurements with a link to the file each comes from, then the gaps. The lists behind it (the skills the agent can load, the checks in the flow, and where AMD's advice differs between device families) sit in a Details section inside the drawer, closed until you want them.

Constraints and timing closureWriting clocks, I/O delays and exceptions that are right, and reading timing reports to close the paths that fail.21 skills, 7 flow checks Checked by the flow

Constraints tell Vivado what the clocks are, when signals arrive at the pins and which paths need no timing; timing closure is the work of making every remaining path fast enough. The agent writes the constraints from its skills, and a gate after routing fails any run that misses setup, hold or pulse-width timing or leaves a path unconstrained. A separate checker looks for risky lines, such as a false path with no stated reason.

Measured. On 10 small designs with one timing-exception mistake each, Vivado itself said something about the exception in 5; the flow's checks flagged 10. They passed 4 of 4 correct designs. source On 13 small designs with one I/O-delay or virtual-clock mistake each, Vivado itself said something in 2; the flow's gates flagged 13. source On a two-clock probe design, setup slack on the crossing was -1.364 ns without AMD's macro exceptions and 8.891 ns with them (Vivado 2026.1). source

In agent runs. Of the development runs whose saved designs were rebuilt on Vivado 2026.1, 6 reached routing; setup slack was positive in 6. source In 3 agent runs of the slow-controller drill (one clock, a one-in-eight enable, an eight-clock multicycle), the constraint grader passed 2; the other run put a register that a write sets on any clock into the eight-clock group, which only the grader's simulation check caught. source In 3 agent runs of the ADC-capture drill (input delays from a data sheet, the oscillator's jitter, a margin for implementation only), the delays were right in 3, free of made-up delays in 3 and carried the jitter in 3; the implementation-only margin was right in 0. source

Not yet shown. I/O delay constraints, virtual clocks and clock uncertainty are written from the skills; no committed run scores them against a data sheet. The flow's multicycle check looks at each register's clock-enable logic, not at whether the register really changes only on the enable; the drill grader adds that check in simulation, the flow does not yet. Only one exception drill is built (the slow controller); the two-cycle datapath, the quasi-static register and the seeded wrong false path are not. Exceptions and I/O delays are now shown in agent runs, but one exception run wrote a wrong multicycle that the flow passed, and no I/O run kept its implementation margin out of sign-off the way asked; virtual clocks have no agent runs yet.

Clock-domain and reset-domain crossingSynchronisers, multi-bit crossings, asynchronous FIFOs, reset bridges and the checks that find a crossing report_cdc passes but that is still wrong.14 skills, 4 flow checks Checked by the flow

Signals that pass between unrelated clocks need synchronisers, and a mistake there can pass every simulation and still fail on the bench. The agent knows the standard circuits for single bits, buses, FIFOs and resets, and its flow checks each crossing three ways: Vivado's crossing report, a structural check of every flip-flop fed from another clock, and a simulation that makes synchronisers resolve late.

Measured. On 10 ported broken crossings, report_cdc alone flagged 5; the flow's gate flagged 10. It passed 12 of 12 correct variants. source On the 12 mutants of the soak rig, its simulation with injection flagged 9. source

Not yet shown. No agent run has used the stronger crossing gate yet. A reset cleared on one side only, in an asynchronous FIFO or a handshake, gets past the gate; only the rig's simulation catches it. The gate's simulation works cycle by cycle, so it finds lost pulses and bits crossed separately but not route skew, glitches or true metastability.
