The agent

This page shows the agent itself: a controller written in code that walks a design through fixed stages, and a small team of language-model agents that do the writing inside each stage. The diagrams are drawn from the agent's own code and its run records, and a recorded run plays through them at the end.

Architecture · Controller loop · Role agents · Stages and gates · A recorded run · Harness and its experiments

What it cannot do yet. It has no held-out score: the development runs are a record of the work, not a measure of how it does on new tasks. No design the agent built has yet passed every test on the board: the one programmed so far passed 3 of 3 serial-link tests and failed its internal signal captures. It designs one module at a time; the project layer for multi-module designs is not yet driven by the controller. The one agent-built design on the board reached it at verification level V1 (the seed and mutation gates, V2 and V3, were not run in that run), and a diagnostic copy showed its RTL hard-wires the shell's build stamp, which its own hardware test never checked. The Deep Agents harness has been run on the small T1 design and, in the harness experiments, on four small tasks up to simulation, with one model; how it compares with Claude Code on the benchmark has not been measured.

What "agent" means here

An agent is a language model that works in a loop: it reads, calls a tool, reads the result and decides what to do next. Left to itself, such a loop drifts, and a model that writes both a design and its tests can make the same mistake in both. So the agent here is two things. A controller, written in Python with LangGraph, decides which stage comes next and whether a stage has passed, from the tools' results alone. Inside each stage, one or more role agents, each a model with a narrow job and a narrow view of the files, do the work.

The architecture

A request comes in as plain English. The interview turns it into a signed-off spec. From then on the controller runs the stages; the role agents write files and call tools; the tools drive Vivado and the simulators; code turns the reports into gate results; and those results, not the models, decide what happens next. Beside the stack sit the private knowledge bank, which the agent reads through two tools, and the project layer for multi-module designs, which today has its own commands and is not yet called by the controller.

The controller loop

The controller is a LangGraph state graph with four steps that repeat once per stage visit. Work runs the stage's role agents. Gate runs the flow's own checks. Review takes a snapshot of the design, so any stage can be rewound, and, when review is on, lets a person approve, edit or rewind; it always pauses before anything touches the board. Advance picks the next stage in code: the next one if the gates passed, or the stage that owns the failure if they did not. A run ends when every stage has passed, or when a stage has used its visits and the run gives up.

The loop exists because language models are good at writing and poor at judging their own work. Putting the judgement in code means a model cannot talk its way past a failed check, and the same stages, limits and gates apply whichever model is doing the writing.

The role agents

There are four roles. The Clarifier turns the request into a spec. The Modeller writes a short Python model of the design from the spec alone. The Verifier writes the tests and the test plan from the spec and the model. The Designer writes the architecture, SystemVerilog, constraints and probes, and does every repair; Vivado implementation is run by the deterministic flow, not by this role. The Modeller and the Verifier never see the RTL, so a misreading of the spec in the RTL is not copied into the tests that judge it. Even so, the agent's own tests never decide a result: hidden tests, written in advance and checked by mutation testing, do.

Two harnesses, the same roles

A harness is the program that runs a model's tool loop. The agent has two, chosen per role. By default each role is a Deep Agents agent (LangChain's create_deep_agent, deepagents 0.7.32), calling models through OpenRouter; the default model is openai/gpt-6-luna. The alternative runs each role turn as one headless Claude Code call on Anthropic models, with every built-in tool switched off and only the agent's MCP server attached. Either way the role gets the same prompt, the same tools and the same jail, and the same gates judge it.

The Deep Agents library can give an agent a to-do list and sub-agents of its own. Here it does neither: the inspection of the role agent as the code builds it, above, finds no to-do tool, and the general-purpose sub-agent is switched off. The planning lives in the controller instead, and the "sub-agents" of this design are the role agents themselves, which the controller calls one after another.

The stages and their gates

Each stage ends in gates. Stage 2 holds the verification stages V0 to V3, from a test plan to closed coverage and a mutation score; stages 1 to 9 follow AMD's UltraFast methodology. Every stage visit has a turn budget, each stage a number of visits, and each failure a list of earlier stages it may go back to; all three come from agent/graph/stages.py. The whole run is capped at 300 turns.

Workflow variants, planned

Several other shapes of workflow are planned as variants of this graph, each behind a flag, to be compared on the same development tasks with the same budgets. None has been run yet, so nothing is claimed for any of them.

The planned variants (none run yet)
  • Skill router not yet measured

    Adds a step that shortlists skills before each role, which then loads them on demand.

  • Independent spec reviewer not yet measured

    Adds a second agent, on another model, that challenges the signed-off spec before any RTL.

  • Best of N not yet measured

    Adds several RTL candidates in parallel; the agent's own gates pick one (hidden tests never).

  • Plan and decompose not yet measured

    Adds a split into modules with contracts, built in parallel and then integrated.

  • Retrieve, then adapt not yet measured

    Adds a search for the closest verified component, which is adapted instead of writing from nothing.

  • Constraints critic not yet measured

    Adds a narrow agent that reviews timing exceptions against known rules.

Harness engineering

A harness is everything around the model: the tools it is offered, how its context is kept as the work goes on, the prompts, the limits, the rules for when to stop, and the sandbox it works in. The model sees only what the harness passes it, and acts only through what the harness lets it call.

So the harness matters as much as the model. The same model costs more and finishes less in a harness that resends a long transcript every turn, or that lets a hung simulation run for half an hour. The controller and the gates above are one half of this agent's harness. This section is about the other half: what runs inside each role agent, and the experiments to improve it.

What ours is today

An audit on 2026-11-11 built a Deep Agents role agent exactly as the agent builds it and read what it is given. It is close to a bare tool loop. The model gets our role prompt and nothing else, a handful of file tools and the stage's own tools, and no to-do list or sub-agents. The library stacks six middleware around it, but for our models only two change what the model sees. One answers tool calls left without a result. The other summarises older turns, but only once the transcript reaches about 170,000 tokens; before that it only shortens the file contents the model wrote in older turns. Tool results, such as Vivado reports and simulation logs, stay in full, and every turn resends them: there is no context eviction of results and no prompt caching.

The experiments

Each change to the harness sits behind a flag, with the baseline left as it is. The first round ran three of them against the baseline: 48 valid runs in 12 blocks, each block one task and one repeat with all four arms, on four small tasks, one low-cost model (openai/gpt-6-luna) for every role, stopping after RTL and simulation. The rule, fixed before any run, was to adopt an arm only if its primary measure falls by at least 30 % with a 95 % interval that excludes zero, its share of hidden tests passed does not fall (the interval of the change does not lie below zero), and it has at most one more task-repeat that only the baseline passed than the other way round.

On 2026-11-12 the owner made H1 the default for development runs, a decision taken after seeing this data, not a pre-registered outcome; the baseline stays available as --harness-arm A0. The clearest effect is H1, which moves large tool results to a file and summarises old turns earlier: it cut cost by about a third, with an interval that excludes zero, and passed as many hidden tests as the baseline. But the rule asked for a saving in "tokens per run (and cost)" without saying whether cost alone counts, and on tokens the interval includes zero; both readings are reported; tokens and wall time were not separated from the baseline, and a larger task set is needed before quoting a saving. The typed digests of H9 cut cost by less than the bar, and their token saving, about a third, has an interval that includes zero. Hang protection (H2) showed no difference; the baseline hung only once, so this round could not test the protection itself. Two of the four tasks were never passed by any arm, so the pass counts rest on the other two. The other arms have not been run.

Fixes already made

Three findings about the harness have already been fixed, each with its evidence. Protection against hung simulations is the time limit in the table above; a stronger one (H2) was tried in the first round of experiments.

  • Whole skills from load_skill. When a role loaded several skills at once, the tool layer's output limit cut the middle out of them without saying so. load_skill now returns whole skills up to the limit and names the ones it held back, so the role can load each by name. Evidence: the fix tools.py test_36_skill_routing.py
  • The debug core's own timing exceptions. The exceptions gate failed every build with a logic analyser in it, because the analyser core brings timing exceptions that Vivado ignores. The gate now reports those as information and still fails on the design's own. Evidence: the fix exceptions_check.py test_45_ila_exceptions.py
  • A build cache for Vivado. A repeated build of an unchanged design now comes from a cache, and a later stage resumes from the last checkpoint. One agent run's build sequence on the c10 task took 304.6 s instead of a modelled 1266.9 s, with the same result. Evidence: the fix build_cache.py summary.json
