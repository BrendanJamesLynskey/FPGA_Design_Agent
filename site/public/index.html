FPGA Design Agent

An agentic FPGA design environment: from a plain-English request to a bitstream proven on the board

So far on the board: the hand-built reference design passes every test; the one agent-built design programmed passed 3 of 3 serial-link tests and failed its logic-analyser captures. No held-out score yet.

Describe a block in plain English. Language-model agents interview you about what you left out, write the spec, a model of it, the tests and the SystemVerilog, then drive the simulators and Vivado 2026.1 to a bitstream and test it on a Digilent Nexys A7-100T. Every stage ends in a check run by code, not by a model, and a failed check sends the work back to the agent that owns it.

So "proven on the board" is the aim the environment is built for, shown so far for the hand-built reference design. The agent-built design reached the board at verification level V1 only (the seed and mutation gates were not run), its bitstream was built before the move to Vivado 2026.1, and a diagnostic copy showed its RTL hard-wires the shell's build stamp.

Which model did what: the 21 development runs used Claude Sonnet through Claude Code; the replayed run further down, and the one agent-built design on the board, came from the Deep Agents harness with OpenAI openai/gpt-6-luna; and in the development runs and evaluations a smaller Claude model (claude-haiku-5-5) stands in for the user in the interview, answering only from the hidden spec.

What is agentic about it, and what stops it

The agents decide

  • what to ask about a request before anything is written
  • the spec, a model of it, the tests, the RTL and the constraints
  • what to change after a failed check, within that stage's budget
  • which tools to call: simulators, lint, Vivado reports and the knowledge bank

Code stops them

  • a controller in code, not a model, picks the next stage
  • gates read the tools' reports; a model cannot argue past them
  • each agent may read and write only its own files
  • visits per stage and 300 turns per run, then the run ends

Inside the loop the agent's own tests drive it: the stage-2 gates run the tests it wrote. On benchmark tasks a run is then scored only by hidden tests written in advance and checked by mutation testing, never by its own tests.

A person approves

  • anything that touches the board: the run always stops for a person before the board stage
  • each stage's result, when review is switched on; it is off by default and was off in every recorded run, where the spec counts as signed off once no question is left open
  • wiring the instruments, and every merge

What is hard about it

A model that writes a design and its tests can make the same mistake in both, so a passing test proves little. The agent therefore splits the work: one agent writes a model of the spec without seeing the RTL, another writes the tests from the spec and that model, and the result is judged by hidden tests written in advance. Vivado run from a script also does less than a careful engineer would: it drops constraints, misses clock crossings and lets over-broad timing exceptions hide failures. Beyond the flow shows where, and what the environment adds. And the board is where a design meets real pins and real time, so every result the board returns is read by code and can send the work back. What has not been measured yet is how much the controller and its gates add over a single model session given the same tasks; the harness experiments are the first step towards that comparison.

The loop, on the bench

This is the agent loop of plan, act, observe and decide, drawn with the parts of the real set-up. The agents plan and write; the design goes through the simulators, Vivado and the board; and each part returns something a program can read, which enters a gate. A pass moves on to the next stage, a failure goes back to the agent that owns it.

Every leg of this loop is a measurement a program can read, so the whole loop can be automated; that is the aim, not yet the result. Today 12 of 19 legs run with no one at the bench, 2 are being built (the instrument captures and the stage that feeds them back), and 5 need a person: wiring, approvals, merges and buying.

All 19 legs, with the run record or code that shows each

Runs with no person today 12

  • Interview to a signed-off spec In development runs an oracle model answers the questions; for a real request the person who asked answers them. Evidence: run_5.json interview.py
  • Role agents write the model, the tests, the RTL and the constraints Each role writes only the files it owns, through a path jail in code. Evidence: agent_luna_05c2_run7.json roles.py
  • Lint, simulation and formal checks Verilator lint, cocotb tests on Icarus or Verilator, SymbiYosys proofs, coverage and mutation testing. Evidence: run_5.json verif_gates.py
  • Vivado synthesis, place and route, and the bitstream The tools build fixed commands; the model never writes Tcl or shell. Evidence: agent_luna_05c2_run7.json build.tcl
  • Gates that read the reports Code parses timing, design-rule, clock-crossing, methodology and exception reports into pass or fail. Evidence: gates.py exceptions_check.py
  • The repair loop A failed gate sends the work back to the stage and role that own the failure, within a visit budget. Evidence: agent_luna_05c2_run7.json stages.py
  • Programming the board over JTAG into SRAM Selected by the cable's serial number; volatile memory only. Evidence: agent_luna_05c2_run7_bringup.json program.tcl
  • Tests over the board's UART shell Register reads and writes through a small shell built into every design. Evidence: agent_luna_05c2_run7_bringup.json README.md
  • Captures of internal signals with the ILA, in batch Vivado's logic analyser, armed and read by script; the hand-built reference design passes all its captures. Evidence: t1_dimmer_counter_bringup.json bringup.py
  • XADC readout of die temperature and core voltage Read over the UART every epoch of a soak; a temperature limit stops the design. Evidence: read_counters.py
  • The clock-crossing soak rig Hours of checked crossings with no one at the board, counted in hardware and read over the UART; a person says yes before a new bitstream is left to soak. Evidence: README.md RUNBOOK.md
  • Audio measured at the board's jack A USB audio interface records the output and a program reads frequency, level, distortion and noise; a seeded pin fault that passed simulation and every in-chip check was caught only here. Evidence: b30_hil_audio.hil.json b30_hil_audio_pinfault.hil.json hil.py
