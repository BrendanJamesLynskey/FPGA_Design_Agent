FPGA Force

A force multiplier for FPGA teams: a whole team's work, from your spec to a checked bitstream.

You specify and judge. The agent implements. The board closes the loop.

What decides whether an FPGA design is right is what it was asked to do and whether the verification is thorough enough to trust. Those two jobs stay with the person. The agent holds the implementation know-how: it interviews you about what the request leaves out, writes the model, the tests and the SystemVerilog, and drives the simulators, Vivado {{board.vivado}} and the board. You can look at any of it. You do not have to.

So far on the board: the hand-built reference design passes every test; the one agent-built design programmed passed {{board.agent_board.uart_passed}} of {{board.agent_board.uart_tests}} serial-link tests and failed its logic-analyser captures. No held-out score yet.

The premise

Writing the RTL is the part the agent takes over. The part that decides whether a design can be trusted is upstream and downstream of it: stating exactly what the design must do, and judging whether the evidence covers that statement. We think this is the under-weighted insight in FPGA work, and it is the reason this agent exists: to take the implementation off the person's hands so the person's attention goes to the specification and to the evidence.

You specify

  • ports, clocks, rules, limits and what the design is for
  • the agent asks about what you left out; the spec counts as signed off only when no question is open

The agent implements

  • model, tests, RTL, constraints, builds and repairs
  • it carries the tool and device knowledge ({{packs.sections}} sections in its knowledge bank)
  • code, not a model, decides whether a check passed

You judge

  • read the evidence against every requirement
  • decide whether it is thorough enough, and send the work back if not
  • approve anything that touches the board

The implementation stays open to inspection: where it is and how to open it.

Hardware verification is its own layer

Simulation and formal tools check a design against a model of the world. An FPGA can also be checked against the world itself, with instruments attached: the on-chip eye scan, register reads over JTAG, SYSMON temperature and voltage, debug captures, a latency loop with predictions written down first, and the optical module's own readings. This extra layer should always be used. Where an external element is involved, such as an external data source, a network card, an optical link or another device, it may be the only way to verify at all, so the flow makes room for it, including the wait when the hardware has not arrived.

  • The first measured receive eye of the KR260's 10G link, after two faults found on the way: record.
  • A board latency run against pre-registered predictions: record.
  • What a fibre loopback cannot show, and the network-card test that waits for hardware: plan.

What is agentic about it, and what stops it

The agents decide

  • what to ask about a request before anything is written
  • the spec, a model of it, the tests, the RTL and the constraints
  • what to change after a failed check, within that stage's budget
  • which tools to call: simulators, lint, Vivado reports and the knowledge bank

Code stops them

  • a controller in code, not a model, picks the next stage
  • gates read the tools' reports; a model cannot argue past them
  • each agent may read and write only its own files
  • visits per stage and {{agent_graph.run_limits.turns}} turns per run, then the run ends

Inside the loop the agent's own tests drive it: the stage-2 gates run the tests it wrote. On benchmark tasks a run is then scored only by hidden tests written in advance and checked by mutation testing, never by its own tests.

A person approves

  • anything that touches the board: the run always stops for a person before the board stage
  • each stage's result, when review is switched on; it is off by default and was off in every recorded run, where the spec counts as signed off once no question is left open
  • wiring the instruments, and every merge

What is hard about it

A model that writes a design and its tests can make the same mistake in both, so a passing test proves little. The agent therefore splits the work: one agent writes a model of the spec without seeing the RTL, another writes the tests from the spec and that model, and the result is judged by hidden tests written in advance. Vivado run from a script also does less than a careful engineer would: it drops constraints, misses clock crossings and lets over-broad timing exceptions hide failures. Beyond the flow shows where, and what the environment adds. And the board is where a design meets real pins and real time, so every result the board returns is read by code and can send the work back. What has not been measured yet is how much the controller and its gates add over a single model session given the same tasks; the harness experiments are the first step towards that comparison.
