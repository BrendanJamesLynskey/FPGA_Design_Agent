Examples

Four stories from the development work: a clean first run, an interview that decided the outcome, a task that took five runs, and a hand-built design on the board. Each development task here was used to find and fix faults in the agent, so these runs show how it works and fails, not how it will do on new tasks.

2. The same task twice: the interview decides

A sine-wave generator task ran twice with the same agent. The part of its text that mattered:

{{!spec_c10}} {{!c10_runs}}

Run 1 passed every check the agent ran and still scored {{examples.1.runs.0.tests_passed}} of {{examples.1.runs.0.tests_total}} on the hidden tests, because it never settled how a sample is packed into the data register. Run 2 asked, got an answer and passed. That escape is why the agent now asks about register layout whenever a task names registers without giving offsets.

3. Five runs of one task, each exposing the next problem

An int8 dot product with requantisation ran five times. After each failure the agent was fixed, never the task, and the task was run again. This is how development tasks are used, and why their results are not a score.

{{!spec_c14}} {{!c14_table}}

Run 5 passed all {{examples.2.runs.4.tests_total}} hidden tests with every gate of the flow at the time green. Its saved design, rebuilt on Vivado {{board.vivado}}, has setup slack {{examples.2.runs.4.wns_ns}} ns, {{examples.2.runs.4.lut}} LUT, {{examples.2.runs.4.ff}} FF and {{examples.2.runs.4.dsp}} DSP, and fails one gate added after the run: the I/O-constraint check, because its XDC gives slow pins invented input delays. Runs 3 and 4 left RTL that passed the hidden tests but stopped on an internal gate: the agent failed its own bar, and the bar was the problem.
