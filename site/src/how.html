How it works

A design moves through fixed stages, and each stage ends in a gate: a check run by code, not by the model. The model proposes; the tools judge. The agent shows the controller and the role agents that do this; a short glossary closes the page.

A real run, step by step

The stages

The stages follow AMD's UltraFast design methodology (UG949). A failed check sends the run back to the stage that can fix it.

StageNameWhat it produces
0InterviewA signed-off spec: ports, clocks, reset, latency, and each assumption with its reason. The user answers, or in an evaluation an oracle.
1PlanBlock diagram, clocking, every clock crossing, a resource budget.
2RTL and testsSystemVerilog, constraints, and tests checked against a golden model.
3ConstraintsPins and clocks checked against the board's master file.
4SynthesisThe netlist, its reports and their gates.
5ImplementationPlace and route, and the bitstream.
6Timing closureSetup and hold slack at the target clock.
7Power closureA power estimate and its gate.
8Design-rule closureDesign-rule, methodology and clock-crossing reports.
9Board and debugProgram the board, test over its serial link, capture internal signals. A human approves programming every time.

Verification

Inside the RTL stage, verification is staged as the OpenTitan project does it, with free tools in place of a paid simulator: a test plan, every spec statement traced to a test or proof, tests passing on every seed, then closed coverage and a mutation score at its floor. The stage cannot end until all four hold and lint is clean. Some checks go further than Vivado does alone; Beyond the flow tells those stories.

Mutation testing

A bench that passes proves little unless it can fail, so mutation testing plants bugs and requires the tests to catch them. What the model may touch

The model runs as headless Claude Code, one call per turn, with every built-in tool off. It reaches only our MCP server, which gives each role just the tools its stage needs (lint, simulate, mutate, formal, build, gates, document search, skill loading, and files in its own directories). The board is never offered to the model: the harness programs it after a human approves. The same stages run with other models, so harness and model can be compared. Development runs here used {{dev.model.0}}. They ran on an earlier Vivado release; every timing, area and power figure this site shows for them is a rebuild of the run's saved design on Vivado {{board.vivado}}, and a run whose design files were not kept shows none.

Glossary

Agent
A language model working in a loop: it reads, calls a tool, reads the result and decides what to do next.
LangGraph
An open-source library for writing such loops as a graph of steps; here it holds the controller that runs the stages.
Harness
Everything around a model that runs its tool loop: the tools, how its context is kept, the prompts, the limits and stop rules, and the sandbox. Here either Deep Agents (an open-source library built on LangGraph) or Claude Code.
Middleware
Code that the harness runs around every model call or tool call, for example to summarise old turns or to repair a malformed call.
Context eviction
Taking old or bulky material out of what the model is sent each turn, such as a long report saved to a file and replaced by a short preview and its path.
Prompt caching
A provider feature that keeps the unchanged start of a prompt between calls, so a repeated transcript costs less and returns sooner.
MCP
The Model Context Protocol, an open standard by which a model's harness calls tools served by another program.
RTL
Register-transfer level: hardware written as registers and the logic between them, here in SystemVerilog.
Bitstream
The file that configures the FPGA, produced at the end of the Vivado flow.
Clock-domain crossing (CDC)
A signal passing between unrelated clocks. It needs a synchroniser and the right constraints, or it can be sampled mid-change.
Slack
The time a signal has to spare before the clock edge that captures it. Negative slack fails timing.
Out-of-context synthesis
Synthesising one block alone, without pins or the rest of the design, for its size and an early view of its timing.
Mutation testing
Planting small bugs (mutants) in a design to see whether its tests catch them.
Golden model
A short program, written from the spec alone, that says what the design should output.
Hidden tests
Tests written for each task before any agent run and never shown to the agent. A run passes only if all of them pass.
Escape
A run whose own checks all passed while the hidden tests failed.
Held-out set
Tasks set aside before development and never used to improve the agent, so a score on them is fair.
Oracle
A language model that plays the user in an evaluation's interview, answering only from the hidden full spec.
