Beyond the standard flow

The agent drives Vivado from scripts, with no GUI, and in that mode Vivado sometimes does less than a design needs. Each card tells one such story: what goes wrong, why, what the flow does, and what has been measured.

1. AMD's crossing macros lose their timing exceptions

Built and verifiedone probe design, two macros

AMD's ready-made clock-crossing circuits, the XPM macros, rely on timing exceptions shipped in separate constraint files. In the scripted flow those files were not applied, so Vivado timed each crossing as an ordinary path between unrelated clocks and a correct design failed timing. Neither Vivado's crossing report nor the agent's crossing gate noticed, because neither reports an exception that is missing. The only sign was negative slack, and the easy cure, a blanket exception, is the one that hides real bugs (card 3).

The flow now re-applies AMD's rules by cell name straight after synthesis; a design without the macros gets no exception. On a probe design with a {{flow_notes.xpm.clk_a_period_ns}} ns and a {{flow_notes.xpm.clk_b_period_ns}} ns clock (Vivado {{flow_notes.xpm.vivado}}), setup slack on the crossing went from {{flow_notes.xpm.before.wns_ns}} ns, with {{flow_notes.xpm.before.failing_endpoints}} failing endpoints, to {{flow_notes.xpm.after.wns_ns}} ns.

{{!xpm_figure}}

Setup slack on the crossing, one build before the fix and one after. Hatched bar: a violation.

One design with two macros shows the gap and the fix, not a rate. The pulse and asynchronous-reset macros get no exception yet, and the array macro is unchecked.

Details: the rules, the report rows and the sources

flow/xpm_cdc.tcl runs after synth_design: a false path to the first stage of each xpm_cdc_single and reset synchroniser; set_max_delay -datapath_only plus set_bus_skew for each xpm_cdc_gray; set_max_delay -datapath_only on the data of each xpm_cdc_handshake. The rules were first proven in the crossing soak rig. Before the fix (read_verilog, synth_design, {{flow_notes.xpm.part}}) report_cdc showed Exception "None" on both crossings. Not covered: xpm_cdc_pulse, xpm_cdc_async_rst; not checked: xpm_cdc_array_single.

2. Vivado's crossing report passes some unsafe crossings

Built and verifiedon test designs; no agent run or board result yet

A crossing can be wrong while every synchroniser in it looks valid: a binary counter crossed bit by bit, a one-cycle pulse into a synchroniser meant for slow levels, two flags synchronised apart and then compared. Vivado's report_cdc checks structure and constraints; it does not run the design. Of the {{flow_notes.counts.rig_mutants}} broken crossings on the soak rig, a hardware test bed for crossings, it flagged {{flow_notes.counts.rig_report_cdc_flags}}. The agent's crossing gate used to rest on that report.

The gate now adds two checks. After synthesis it classifies every flip-flop fed from another clock, as a synchroniser chain, an AMD macro, a constrained Gray bus or handshake, a reset bridge, or unsafe. Then it reruns the design's own tests with each first synchroniser stage, and each AMD macro, sometimes holding its old value for an extra cycle, as a late-resolving flop would. A design that passes the plain run but fails this one fails the gate.

On {{flow_notes.counts.ported}} broken crossings ported to the test set, the report alone flagged {{flow_notes.counts.report_cdc_flags}} and the new gate {{flow_notes.counts.gate_flags}}, and the gate passed all {{flow_notes.counts.correct_pass}} correct variants. A FIFO or handshake reset on one side only is not covered: the rig catches those by disturbing a reset's release, which the gate's cycle-level model lacks.

{{!mutant_table}}

"Rig simulation" lets the first stage resolve late within 1 ns of the clock edge; it catches M4 only because a delay is modelled on its path. "Gate's own injected simulation" is the gate's cycle-level version, run on the test set. M6b and M6c (M6a with route padding, a hardware skew effect) are not ported.

Why an extra cycle finds the tear

A bus crossed bit by bit is safe only if one bit changes at a time. A binary counter changes several, and if one bit arrives a cycle late the destination sees a value that never existed: a torn value. Step through a 4-bit counter crossing a two-flop synchroniser, binary or Gray-coded, with and without the extra cycle. Hatched cells are first-stage flops holding their old value.

Frames from site/flow_model.py, a small model of the gate's rule. The source changes every {{flow_notes.tear.hold}} destination cycles; a sample is torn when it equals neither the current nor the previous source value.

{{!tear_table}}

A longer run of the same model. A Gray counter changes one bit per step, so a late bit gives only the old value or the new one. The model is cycle-level: it finds lost pulses, separately crossed bits and reconvergence, not route skew, glitches or true metastability.

Not yet shown: no agent run has used the new gate, and the rig's board results are not here. The gate checks that a hand-built Gray bus carries its exception, not that it is Gray-coded, so only simulation catches a binary bus with a correct exception.

Details: what the report misses, and the sources

On the rig, report_cdc passes M3, M5, M6a, M7, M9 and M11 as valid synchronisers and gives M1 only a warning. The old gate was its Critical rows plus a text check inside one module. The new checks sit in the V3 gate; M9 and M11 are the one-sided resets it does not cover.

3. Over-broad timing exceptions hide real failures

Designed, not built

A model that cannot meet timing has an easy way out: declare the failing path a false path, a multicycle path or part of an asynchronous clock group. Vivado applies any exception it is given, and the timing summary reads clean. Its methodology checks catch some cases, but a passing slack figure alone cannot tell a real pass from a hidden failure.

The planned grading tasks each seed a real violation: a slow synchronous path, a failing path between related clocks, or an unsynchronised crossing. A task passes only if the violation stays visible after the agent's constraints are applied, and a repaired twin of the design must meet timing with the same constraints.

{{!exception_figure}}

The check in outline: one failing path, with and without a false path over it. No measured values.

The tasks are written down but not built or run, so there are no results. Among the methodology checks that catch some cases are TIMING-46 and TIMING-47.

4. A missing report or a skipped test looks like a pass

Builtcovered by unit tests; no live run of the changed gates

A quality review of the flow found three ways a weak run could pass. A missing report made its gate skip, and a skipped gate counted as a pass. A cocotb test marked as skipped counted towards the planned tests. A test marked as expected to fail turned a real failure into a pass. All three now fail (a missing report, once the build has written its run record), and a scan of the test source flags the markers. After routing, Vivado's quality-of-results score (report_qor_assessment) must also be at least 4 out of 5.

Sources: flow/gates.py; flow/verif_gates.py; tests under flow/tests.

5. Placement regions made after synthesis are only hints

Measuredon the crossing test rig

A pblock is a region of the chip that some cells must be placed in. The soak rig makes its pblocks by script after synthesis, to put each crossing at a known distance. Pblocks made at that point came out soft, a hint to the placer: about half of the destination cells landed outside their region until the rig set IS_SOFT to FALSE. It now does so for every pblock. The agent's own flow makes none, and pblocks in its constraint file are read before synthesis, where they are hard by default; any future step that makes them later must set the property too.

Source: the build scripts in hil/cdc_soak/tcl.

6. Scripted DDR controller generation skips the pin check

Measuredtwo seeded faults, through placement; rule checker built

AMD's DDR controller wizard, the MIG, checks a pinout against the memory's byte-group and bank rules before it generates the core. Generating the same core from a script, as the agent must, skips that check. A pinout with a byte-group fault generated silently, with the bad pins in the constraints file; one with a pin used twice also generated silently, and one data pin's line was dropped. The knowledge bank's own pin-rule checker flagged both and passed the good pinout.

Could Vivado catch the faults later, when the design is built? The good pinout and both faulty ones were taken through the controller's example design: synthesis, placement and the design-rule checks. The byte-group fault came out identical to the good pinout and was not rejected, because the generator derives the byte lanes from whatever pins it is given, so the design is consistent with the wrong pins. The duplicated pin raised no error either, only warnings naming the missing data pin and one more unplaced port than the good build. So the build is at best a weak second opinion, and the rule checker stays the gate. Routing was not run for the faults.

Sources: section 2 of docs/project_mode_parity.md and results/project_parity/mig_impl (the build of the example design, flow/mig_impl_check.tcl); pin-check results in the private knowledge repository (tools/pin_xdc_check, mig_pin_rules.py) and the pin-planning grading design.

7. The switching-noise report is missing on some parts

Measuredavailability only; no substitute built

Simultaneous switching noise limits how many fast outputs can share an I/O bank, and Vivado's report_ssn estimates the margin. It works on the Artix-7 100T and on the Zynq-7000 part checked, and it flagged a deliberately overloaded bank. On the Kria K26 it is not available. The pin checks use it where they can; the other pin checks run on every part. Nothing yet replaces the noise margin on the K26.

Source: pin-check results in the private knowledge repository (tools/pin_xdc_check).

8. AMD's IP models need a simulator the tests cannot drive

Planned

AMD's DSP cores (FIR, FFT, DDS and others) ship encrypted simulation models that only AMD's xsim and licensed commercial simulators can run. The free simulators the agent uses cannot, and the cocotb test framework has no xsim back end. The plan is a harness that works through files: Python writes the stimulus and a seeded back-pressure pattern, a generic test bench replays it in xsim, and Python compares every output word with AMD's bit-accurate C model where one exists. A synthesis run at the target clock checks timing and resources. The harness is specified in the expertise survey but not built: no code or measurements yet.
