How it is evaluated

Tasks used to improve an agent cannot also measure it. So a set of tasks is put aside, the method is written down and committed before any scored run, and the agent is frozen at a tag. This page explains that method in plain words.

In short: the first evaluation set aside {{eval.tasks}} tasks the agent never saw (five have since moved to development, after it was stopped; the problems page lists them), {{eval.runs_per_task}} runs of each, scored by hidden tests that no language model grades. With {{eval.tasks}} tasks a pass rate is known to about ±{{eval.planned_halfwidth}} percentage points: enough to show a large difference between two versions of the agent, not a small one. Finer comparisons come from pairing two versions task by task.

The first such evaluation froze the agent at the tag (a fixed, named version of the code) eval-1, with its method in the pre-registration. It was stopped before analysis (the note added when it stopped). The next, the baseline, uses the same method on a larger benchmark.

The method

{{eval.tasks}} tasks were drawn by a fixed random seed, before any agent run, from the first benchmark and the course tier, and the agent was never to see them: not their text, tests or reference designs. Their files are frozen with checksums, and a check must find no mismatch before the first run. Everything labelled "development" elsewhere on this site comes from the other tasks.

Each task has hidden tests, written before any agent run against an independent golden model and run on the Icarus simulator. No language model grades anything, and a run passes only if every hidden test passes. The tests are themselves checked: the reference design must pass, and {{eval.mutants_per_task}} deliberately broken versions per task must fail.

Each task runs {{eval.runs_per_task}} times, {{eval.runs}} runs in all, each from a clean checkout, in an order fixed in advance by a seed so that no task runs easiest first. The agent sees only the task text and the board's knowledge pack. Its questions go to an oracle ({{eval.oracle}}) that answers from the hidden spec, with a check that each answer quotes it, and every exchange is logged.

A run that ends for an infrastructure reason is reported as not run, with evidence, and never repeated into the result. Nothing changes during the evaluation: a bug found on the way is written down, fixed afterwards and measured as a second evaluation on the same tasks.

What is reported

Tasks, not runs, are the unit. The headline is pass@1, the mean of each task's pass rate (one attempt per task), with a 95% interval from a bootstrap over tasks ({{eval.resamples}} resamples). A Wilson interval on runs sits beside it, labelled as ignoring that runs of one task are alike. The report also gives the share of escapes, runs whose own checks passed while the hidden tests failed, split by the check that should have caught them.

The width was planned in advance from the {{eval.dev_runs_for_width}} development runs on {{eval.dev_tasks_for_width}} tasks: an expected half-width of about ±{{eval.planned_halfwidth}} points for the 95% interval. It comes from tasks differing in difficulty, so more runs per task barely narrow it. On {{eval.tasks}} tasks a pass rate is known to about that much; sharper comparisons will come later, from pairing results task by task.

Limitations, stated up front

{{eval.tasks}} tasks give wide intervals. There is one board, one model and one harness. A language model stands in for the user in the interview, Icarus is the scoring simulator, and every constant (gate floors, caps, timeouts) was chosen on development tasks.

Held-out task text stays private until the results are published. Nothing on this site comes from a held-out task, and a scan of the published pages against the private held-out material is part of each release.
