# Verification harness for the fp_mul (Floating-point multiplier (IEEE-754-style binary formats))

Generated by `python -m arith.tools.gen_harness` (arith brief 139a); the handwritten parts are `assertions.sv`, `chk_top.sv` and `coverage.yaml`. This folder is a deliverable: rerun it against your own instance after you integrate or change the block. It needs nothing else from the repository.

## What is in it

| File | What |
|---|---|
| `model.py` | the bit-exact model of the specification ([../spec.md](../spec.md)), in Python integers (the floating-point functions also have `fp_ref.py`, the exact-rational reference it calls, and `fpx_ref.sv`, the specification as wide integer RTL that the checker uses) |
| `bench.py`, `fp_mul_cocotb.py`, `harness_common.py` | the cocotb bench: drives one vector per clock (exhaustive at small widths; edge values, runs of ones and random inputs at large ones) and compares every output bit with the model, allowing for your latency |
| `assertions.sv` | a passive SystemVerilog checker with the specification as plain wide arithmetic; put it beside your instance in your own bench or in the simulator of your choice; its `errors` counter is 0 when the instance conforms |
| `chk_top.sv` | your instance with the checker beside it, used by `run_harness.py --checker` |
| `coverage.yaml` | the coverage targets (bins over the inputs and the model's results, with minimum hit counts) that the stimulus must reach; `run_harness.py` fails if one is missed |
| `run_harness.py` | the standalone runner (Icarus Verilog + cocotb) |

## Running it against your instance

Needs `iverilog`, Python 3, `pip install cocotb==2.0.1 pyyaml`.

```
python3 run_harness.py --rtl my_fp_mul.sv --top my_module --params '{"EXP": 8, "MAN": 23, "SUBNORM": 1, "STAGES": 3}' --latency 3 --mode both --checker
```

- `--top` must have the ports listed in the specification under the same names, and the parameters you pass in `--params` (the harness needs the widths and signedness to build the model).
- `--latency` is your instance's latency in clocks. Giving a wrong latency fails the run: that is deliberate, it checks the number.
- `--mode exhaustive` is for small widths only (about 12 operand bits); `randomised` for any width; `both` runs both.
- `--checker` builds your instance next to `assertions.sv`; the run fails if the checker's error counter is not 0. To use the checker in your own bench instead, instantiate it with the same signals as in `chk_top.sv`.
- Exit status 0 means: every vector matched the model, the checker saw no mismatch, and every coverage target was met. `--build-dir` keeps the logs and `coverage.json`.

## Interface the harness assumes

- Protocol: plain registered-or-combinational ports, no handshake: operands are sampled every clock and one product leaves, with no valid, ready or backpressure. A caller that needs a valid bit delays its own valid by STAGES
- Throughput: one product per clock in every variant (initiation interval 1)
- Latency: per variant, in clocks: STAGES (0 to 3) for both dsp and lut
- Reset: none: no control state; the rank registers hold data only and y is meaningless for STAGES clocks after power-up
- Clock: one clock, rising edge, no clock-enable and no gating; clk is present but unused when STAGES is 0

Parameter names used by the variants of this library (your instance needs the ones the model uses; the others are ignored by the model):

- `EXP`: exponent bits (8 for binary32 and bfloat16, 5 for binary16)
- `MAN`: stored fraction bits (23 for binary32, 7 for bfloat16, 10 for binary16)
- `SUBNORM`: 1: subnormal numbers supported (IEEE 754); 0: flush to zero, smaller and faster
- `STAGES`: register ranks, 0 to 3: the latency in clocks (above 3 behaves as 3)

## What it does not check

Timing, power, area and clocking (those are Vivado's), behaviour for parameter values outside the ranges in the specification, X-propagation beyond the first compare, and anything about the surrounding design (handshakes, valid bits, your reset sequencing). A pass shows the instance computes the specified function with the stated latency at the parameters you ran; run it at each parameter set you instantiate.
