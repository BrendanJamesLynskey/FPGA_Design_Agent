# Integer adder and subtractor (arith/adder)

Generated by `python -m arith.tools.gen_spec_md` from [spec.yaml](spec.yaml); edit the YAML, not this file. Part of the arithmetic library of brief 139a ([../README.md](../README.md)).

A WIDTH-bit integer adder that is also a subtractor, with a carry (or borrow) in and out and a signed-overflow flag. Three implementations trade fabric area, delay and latency: one carry chain, carry-select blocks, and a pipeline of carry-chain chunks.

## Function

- sub = 0: s = (a + b + cin) mod 2**WIDTH and co = (a + b + cin) div 2**WIDTH
- sub = 1: s = (a - b - cin) mod 2**WIDTH and co = 1 when a >= b + cin (as unsigned numbers), else 0
- ovf = 1 when the true signed result (two's complement readings of a and b, minus or plus cin) is outside -2**(WIDTH-1) .. 2**(WIDTH-1)-1
- the hardware identity behind every variant: a - b - cin = a + ~b + ~cin on WIDTH bits, so one adder serves both operations (Lean: ArithAdder.sub_is_add_complement)

Signedness: one datapath for both readings: s and co are the same bits either way; ovf is the signed flag, co the unsigned one.

Exactness: exact (no error bound): every output bit equals the model's for every input.

Latency: clocks from the operands being presented to s, co and ovf being valid; 0 means combinational; throughput is one operation per clock in every variant.

## Ports

| Port | Direction | Width | Meaning |
|---|---|---|---|
| `clk` | in | 1 | clock; unused (and kept for a common port list) by the combinational variants |
| `a` | in | WIDTH | first operand, a bit pattern (unsigned value; two's-complement reading only for ovf) |
| `b` | in | WIDTH | second operand |
| `cin` | in | 1 | carry in when sub = 0; borrow in when sub = 1 |
| `sub` | in | 1 | 0 = add, 1 = subtract |
| `s` | out | WIDTH | a + b + cin or a - b - cin, modulo 2**WIDTH |
| `co` | out | 1 | carry out of the underlying adder; with sub = 1 it is 1 when there is NO borrow (a >= b + cin as unsigned numbers) |
| `ovf` | out | 1 | signed (two's complement) overflow of the operation |

### Intended primitive use

- `ripple`, Artix-7 (xc7a100t): ceil(WIDTH/4) CARRY4 in one chain; about WIDTH LUTs; 0 FF; 0 DSP
  - K26 (xck26): ceil(WIDTH/8) CARRY8 in one chain; about WIDTH LUTs; 0 FF; 0 DSP
- `carry_select`, Artix-7 (xc7a100t): 1 + 2*(NB-1) carry chains (NB = ceil(WIDTH/BLOCK), each ceil(BLOCK/4) CARRY4); about 2*WIDTH - BLOCK LUTs for sums plus NB-1 for the carries; 0 FF; 0 DSP
  - K26 (xck26): as a7 with CARRY8 cells (ceil(BLOCK/8) per chain)
- `pipelined`, Artix-7 (xc7a100t): STAGES carry chains of about WIDTH/STAGES bits (CARRY4 cells); about WIDTH*(STAGES-1) flip-flops each way (a triangle of skew registers on the operands and of de-skew registers on the sum), plus STAGES carry flip-flops; 0 DSP
  - K26 (xck26): as a7 with CARRY8 cells

## Interface contract

Written without knowing the design the block will sit in (brief 139a, owner decision 24): this is what a user can rely on and must provide.

- Protocol: plain registered-or-combinational ports, no handshake: operands are sampled every clock and one result per clock leaves, with no valid, ready or backpressure. A caller that needs a valid bit delays its own valid by the variant's latency
- Throughput: one operation per clock in every variant (initiation interval 1)
- Latency: per variant, in clocks: ripple 0, carry_select 0, pipelined STAGES (spec.yaml variants.<v>.latency); combinational variants are not registered, so the caller registers the outputs (or the inputs) to get a timing-clean path
- Reset: none: the datapath holds no control state; the pipelined variant has no reset and its outputs are meaningless for STAGES clocks after power-up or after the inputs were last changed from an unrelated stream
- Clock: one clock, rising edge, no clock-enable and no gating; clk is present but unused on the combinational variants
- Stalls: none: a stalled consumer must drop or buffer results itself; the pipeline cannot be frozen (no enable)

| Variant | Latency (clocks) | Throughput |
|---|---|---|
| `ripple` | `0` | 1 per clock |
| `carry_select` | `0` | 1 per clock |
| `pipelined` | `STAGES` | 1 per clock |

## Integration

- Port timing: combinational variants: a to s/co/ovf is one combinational path (a carry chain of WIDTH bits for ripple, about BLOCK bits plus a select chain for carry_select), so register both sides in the surrounding design and budget the path as one clock; pipelined: inputs and outputs are directly registered inside the block, so they can be driven from and sampled by ordinary registers with a full clock of slack
- Constraints to carry: no special constraints: no multicycle or false paths, one clock. For the combinational variants constrain the path from the source registers to the sink registers at one clock period; keep the carry chain in one column (do not break the adder across a hierarchy that a keep_hierarchy or a pblock splits). A wider adder than the fabric's carry-chain column height crosses columns and slows sharply: check the post-route path
- Verification after integration: rerun the packaged harness against your instance ([harness/README.md](harness/README.md)); it needs no other file of this repository.

## What a user could guess wrong

- co with sub = 1 is NOT a borrow flag: it is the carry out of a + ~b + ~cin, so it is 1 when no borrow occurs
- cin is a borrow in when sub = 1 (s = a - b - cin), not a carry in
- ovf is the signed flag; for unsigned arithmetic read co (add) or its inverse (sub)
- the pipelined variant has no reset and no valid: for STAGES clocks after power-up its outputs are not meaningful, and a new operation can enter every clock
- a combinational variant has a clk port it ignores
- WIDTH 1 is legal; its signed range is -1..0, so ovf is set for 0+0+1 and for -1+-1 (a + b + cin outside -1..0)
- STAGES must be between 1 and WIDTH and BLOCK at least 1; other values are not rejected by an assertion (they fail to elaborate or give the wrong widths)
