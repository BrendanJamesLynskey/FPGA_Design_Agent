arith_adder: specification to evidence

The human specifies the requirements and checks that the verification is thorough enough. The agent holds the knowledge to implement and to verify. You can open any of the implementation or the evidence, and you do not have to. Hardware on the board, with attached instruments, is a verification layer of its own: where a requirement depends on something outside the design (an optical link, a network card, a data source) it may be the only way to close it.

Requirements in full

ADD-F-MODEL: The bit-exact model is right

arith/adder/model.py gives, for every input, the result that spec.md defines. It agrees with an independent formulation (a bit-serial chain of full adders) on every input at small widths and with Python's integer arithmetic on random large-width inputs, and the conventions that a user could guess wrong (spec.md, last section) are pinned by examples.

  • simulation test: pass The model against independent formulations (exhaustive small, random large) and the pinned conventions: 4 test(s) passed in the recorded run evidence

ADD-F-EXACT: Every variant is bit-exact against the model

At every parameter point listed in spec.yaml (16 exhaustive points, 14 random ones, across 3 variants), each variant's outputs equal the model's in every clock: every input is driven at the small points; edge values, runs of ones, and random inputs at the large ones. The function is exact, so there is no error bound.

  • simulation test: pass Every variant against the model, every input, at the small points (Icarus + cocotb): 16 test(s) passed in the recorded run evidence
  • simulation test: pass Every variant against the model at the large points: edge values, carry runs and random inputs (Icarus + cocotb): 14 test(s) passed in the recorded run evidence

ADD-F-LAT: Latency is as specified and the bench would notice if it were not

Each variant's latency in clocks is the expression in spec.yaml (ripple: 0; carry_select: 0; pipelined: STAGES), and the bench, run with a latency two clocks off, fails for every variant, so the passing runs prove the latency rather than assume it.

  • simulation test: pass The bench passes at the stated latency and fails two clocks off, for every variant: 3 test(s) passed in the recorded run evidence

ADD-F-EQUIV: The variants are equivalent to a plain reference, by proof where the tools allow

SymbiYosys with the slang front end checks the variants against each other and a plain reference (a single `+` or `*`, or the specification written as RTL). The jobs in formal/jobs.yaml name the widths; a proof is by k-induction (for all inputs, any run length) at the widths listed there, a bounded check holds only to its stated depth. Widths beyond the listed ones are covered by simulation, not by proof.

  • formal: pass k-induction proofs of the variants against the reference (5 jobs; widths in formal/jobs.yaml): 5 test(s) passed in the recorded run evidence
  • formal: pass Each formal check refutes a planted fault (the check can fail): 2 test(s) passed in the recorded run evidence

ADD-F-BENCH: The bench catches seeded faults

Every one of the mutants in verif/mutants.yaml (one exact text change each, in the variant's RTL: an inverted condition, a wrong constant, a dropped connection, a lost reset) makes the cocotb bench fail; mutants that survive or do not build are reported, never hidden.

  • simulation test: pass The mutation run as a test: no mutant survives, none fails to build: 1 test(s) passed in the recorded run evidence
  • simulation measurement: pass Mutants killed of valid mutants (the record of the last full run): survived = []; invalid = []; valid = 16; score_pct = 100 evidence

ADD-F-HARNESS: The packaged verification harness is a standalone deliverable that works

arith/adder/harness holds the model, the cocotb bench, a SystemVerilog checker, coverage targets and a runner that needs nothing else from the repository. Run standalone against every variant (one small exhaustive point and one large random point each, with the checker beside the instance) it passes and the random runs meet every coverage target; run against a planted fault it fails, with and without the checker. Its generated files are the repository's own bench, so they cannot drift.

  • simulation test: pass The packaged harness run standalone on every variant (with the checker and the coverage targets) and on a planted fault: 8 test(s) passed in the recorded run evidence

ADD-F-PACKAGE: The RTL is lint-clean, and its files agree with the specification and with the Vivado build files

spec.yaml states an interface contract (protocol, throughput, latency, reset, clock, stalls) and integration guidance (port timing, constraints to carry). Every variant passes Verilator -Wall at every point of spec.yaml; its ports and default parameters are the ones spec.yaml states; its header states the intended primitive use before any Vivado run; spec.md is the rendering of spec.yaml; the out-of-context wrapper and the build.yaml for each variant (Artix-7 xc7a100t and K26 xck26, prepared in 139a and run in brief 160) are current and lint-clean at every point they list, so a Vivado run can start from the repository alone.

  • simulation test: pass spec.yaml against the RTL headers, spec.md against spec.yaml, Verilator -Wall at every point, wrappers and build.yaml current and lint-clean: 5 test(s) passed in the recorded run evidence

ADD-F-LEAN-CS: Carry-select composition adds, for every width

A carry-select adder (a low block, and a high block computed for carry in 0 and 1 and selected by the low block's carry out) returns the same sum and carry out as plain addition, for every block widths m and k and every pair of operands. The statement is the specification and is NOT approved by a human (verif/lean_approvals.yaml is empty), so the proof is shown but not counted as verification. The Lean text is a hand transcription of the RTL's structure; it models no timing or clocking.

  • Lean proof (all widths): statement not approved Carry-select composition adds: statement not approved; ArithAdder.cs_correct: kernel only; proof of the transcription, transcription not tested; recorded build (not re-run) evidence

ADD-F-LEAN-SUB: Subtraction is addition of the complements, for every width

For every width n, a + ~b + ~bin on n bits equals a - b - bin modulo 2^n, and its carry out is 1 exactly when there is no borrow: the identity every variant's subtract path rests on. The statement is the specification and is NOT approved by a human (verif/lean_approvals.yaml is empty), so the proof is shown but not counted as verification. The Lean text is a hand transcription of the RTL's structure; it models no timing or clocking.

  • Lean proof (all widths): statement not approved Subtraction is addition of the complements: statement not approved; ArithAdder.sub_is_add_complement: kernel only; proof of the transcription, transcription not tested; recorded build (not re-run) evidence

ADD-P-OOC: Every prepared point places and routes out of context on Artix-7 and K26

Each point of the build files of adder (build/<variant>/build.yaml; 20 in all, both parts) goes through Vivado 2026.1 out-of-context synthesis, placement and routing and leaves a recorded result (utilisation, WNS, WHS, Fmax, logic levels, vectorless power) in verif/results/vivado_ooc_<variant>_<part>.json. The measured values and each point's pre-stated expectation are in the Measured table of spec.md and in verif/results/vivado_surface.json; this requirement states only that the measurement exists for every point, because no Fmax or area bound has been agreed. Bound: prepared points with a routed out-of-context Vivado result at least 20 points; condition: Vivado 2026.1 out-of-context, one thread, the clocks of the build files, brief 160.

  • post-route timing: pass The routed Vivado results of every prepared point (the records of the last run): measured 20 points; bound at least 20 points evidence
