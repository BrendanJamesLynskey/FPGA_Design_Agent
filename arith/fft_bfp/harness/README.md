# Verification harness for fft_bfp (Block-floating-point FFT (one exponent per frame, W-bit output words, two architectures))

Generated by `python -m arith.tools.gen_harness_fft` (arith brief 161); the handwritten parts are `chk_top.sv` and `coverage.yaml`. This folder is a deliverable: rerun it against your own instance after you integrate or change the block. It needs nothing else from the repository.

## What is in it

| File | What |
|---|---|
| `model.py` and its support (`fft_ref.py`) | the bit-exact model of the specification ([../spec.md](../spec.md)), in Python integers |
| `bench.py`, `frames.py`, `fcover.py`, `fft_bfp_cocotb.py` | the cocotb bench: drives frames or streams (directed stimuli: impulses, tones, corner values; random ones; the stalls and gaps the contract permits), compares every output with the model bit for bit and checks the latency |
| `assertions.sv` | passive SystemVerilog checkers (simulation only): the frame structure of the output (N consecutive beats from sof, valid held and data/exponent stable while the sink is not ready, the exponent constant over a frame). Their error counters must stay 0 |
| `chk_top.sv` | your instance with those checkers beside it, used by `run_harness.py --checker` |
| `coverage.yaml` | the coverage targets (events the stimulus must produce, with minimum counts); `run_harness.py` fails a full run that misses one |
| `run_harness.py` | the standalone runner (Icarus Verilog + cocotb) |

## Running it against your instance

Needs `iverilog`, Python 3, `pip install cocotb==2.0.1 pyyaml`.

```
python3 run_harness.py --rtl my_fft_bfp.sv --top my_module --variant sdf --params '{"LOGN": 4, "W": 8, "TW": 10, "RND": 1, "ORDER": 0, "CMUL": 4, "TWSTAGES": 1, "MULSTAGES": 2}' --latency 41 --mode all --checker
```

- `--top` must have the ports listed in the specification under the same names, and every parameter of the specification (pass them all in `--params`; the model is built from them).
- `--latency` is your instance's latency in clocks as the specification defines it. Giving a wrong latency fails the run: that is deliberate, it checks the number. The latency of this block's variants (`sdf, burst`) is stated in `../spec.yaml` as a formula.
- `--mode` is one of `all` (default) or `directed`, `levels`, `randomised`, `stalled`, `stalled_hard`: the modes are the benches of the repository's own tests (stimuli, schedules and checks described in `fft_bfp_cocotb.py`).
- `--checker` builds your instance next to `assertions.sv`; the run fails if a checker counts a violation. To use the checkers in your own bench instead, instantiate them with the same signals as in `chk_top.sv`.
- Exit status 0 means: every output matched the model, the latency and the checkers were as specified, and (mode `all`) every coverage target was met. `--build-dir` keeps the logs and the coverage files.

## Interface the harness assumes

- Protocol: streaming frames as arith/fft: sdf has no back-pressure (in_valid high for N consecutive clocks per frame, the next frame after no gap or at least N/4 idle clocks, out_ready ignored, in_ready always 1); burst: in_sof only while in_ready is 1, out_ready stalls the output with every output signal held. The exponent out_exp is valid together with out_valid and is the same on all N words of a frame
- Throughput: sdf: one sample per clock continuously, a frame every N clocks (the frame store is two banks, one being written while the other is read). burst: one frame per N + LOGN * (N/2 + MULSTAGES + 3) + N clocks as arith/fft burst; the store adds no time
- Latency: sdf: N - 1 + LOGN + ((LOGN - 1) // 2) * (TWSTAGES + MULSTAGES + 1) + N + 2 (the core's bit-reversed latency, a frame to store, 2 clocks to read) for both orders. burst: N + LOGN * (N/2 + MULSTAGES + 3) + 1 + N + 2
- Reset: synchronous: clears the control state of the core and the store (bank flags, counters); the memories are not cleared. A frame in flight when rst is asserted is lost; no test covers a reset in the middle of a frame
- Clock: one clock, rising edge, no clock-enable
- Stalls: sdf: none (the sink must take every word when presented; in_valid must stay high for N clocks per frame); burst: in_ready low means busy, out_ready low stalls the output and, when both store banks are full, the core

## What the harness does not cover

- Timing, area and power: nothing here is a Vivado result. The harness checks function against the model, the interface rules and the stated latency, in simulation only.
- A reset in the middle of a frame or a block, and parameter combinations outside the points of `../spec.yaml` (the model supports them; the harness is run at the points you give it).
- The checkers are immediate assertions evaluated on the clock edge, not concurrent SVA properties (the open-source simulator does not run those).
