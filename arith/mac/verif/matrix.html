arith_mac: specification to evidence

The human specifies the requirements and checks that the verification is thorough enough. The agent holds the knowledge to implement and to verify. You can open any of the implementation or the evidence, and you do not have to. Hardware on the board, with attached instruments, is a verification layer of its own: where a requirement depends on something outside the design (an optical link, a network card, a data source) it may be the only way to close it.

Requirements in full

MAC-F-MODEL: The bit-exact model is right

arith/mac/model.py gives, for every input, the result that spec.md defines. It agrees with an independent formulation (a structure-free reference that applies the samples one at a time with Python integers) on every input at small widths and with Python's integer arithmetic on random large-width inputs, and the conventions that a user could guess wrong (spec.md, last section) are pinned by examples.

  • simulation test: pass The model against independent formulations (exhaustive small, random large) and the pinned conventions: 5 test(s) passed in the recorded run evidence

MAC-F-EXACT: Every variant is bit-exact against the model

At every parameter point listed in spec.yaml (16 exhaustive points, 12 random ones, across 3 variants), each variant's outputs equal the model's in every clock: every input is driven at the small points; edge values, runs of ones, and random inputs at the large ones. The function is exact, so there is no error bound.

  • simulation test: pass Every variant against the model, every input, at the small points (Icarus + cocotb): 16 test(s) passed in the recorded run evidence
  • simulation test: pass Every variant against the model at the large points: edge values, carry runs and random inputs (Icarus + cocotb): 12 test(s) passed in the recorded run evidence

MAC-F-LAT: Latency is as specified and the bench would notice if it were not

Each variant's latency in clocks is the expression in spec.yaml (dsp: NREG; dsp_cascade: LANES + 1; fabric: NREG), and the bench, run with a latency two clocks off, fails for every variant, so the passing runs prove the latency rather than assume it.

  • simulation test: pass The bench passes at the stated latency and fails two clocks off, for every variant: 3 test(s) passed in the recorded run evidence

MAC-F-EQUIV: The variants are equivalent to a plain reference, by proof where the tools allow

SymbiYosys with the slang front end checks the variants against each other and a plain reference (a single `+` or `*`, or the specification written as RTL). The jobs in formal/jobs.yaml name the widths; a proof is by k-induction (for all inputs, any run length) at the widths listed there, a bounded check holds only to its stated depth. Widths beyond the listed ones are covered by simulation, not by proof.

  • formal: pass k-induction proofs of the variants against the reference (4 jobs; widths in formal/jobs.yaml): 4 test(s) passed in the recorded run evidence
  • formal: bounded Bounded model checking from reset (1 job: a larger width than the proofs reach): 1 test(s) passed in the recorded run evidence
  • formal: pass Each formal check refutes a planted fault (the check can fail): 3 test(s) passed in the recorded run evidence

MAC-F-BENCH: The bench catches seeded faults

Every one of the mutants in verif/mutants.yaml (one exact text change each, in the variant's RTL: an inverted condition, a wrong constant, a dropped connection, a lost reset) makes the cocotb bench fail; mutants that survive or do not build are reported, never hidden.

  • simulation test: pass The mutation run as a test: no mutant survives, none fails to build: 1 test(s) passed in the recorded run evidence
  • simulation measurement: pass Mutants killed of valid mutants (the record of the last full run): survived = []; invalid = []; valid = 22; score_pct = 100 evidence

MAC-F-HARNESS: The packaged verification harness is a standalone deliverable that works

arith/mac/harness holds the model, the cocotb bench, a SystemVerilog checker, coverage targets and a runner that needs nothing else from the repository. Run standalone against every variant (one small exhaustive point and one large random point each, with the checker beside the instance) it passes and the random runs meet every coverage target; run against a planted fault it fails, with and without the checker. Its generated files are the repository's own bench, so they cannot drift.

  • simulation test: pass The packaged harness run standalone on every variant (with the checker and the coverage targets) and on a planted fault: 8 test(s) passed in the recorded run evidence

MAC-F-PACKAGE: The RTL is lint-clean, and its files agree with the specification and with the Vivado build files

spec.yaml states an interface contract (protocol, throughput, latency, reset, clock, stalls) and integration guidance (port timing, constraints to carry). Every variant passes Verilator -Wall at every point of spec.yaml; its ports and default parameters are the ones spec.yaml states; its header states the intended primitive use before any Vivado run; spec.md is the rendering of spec.yaml; the out-of-context wrapper and the build.yaml for each variant (Artix-7 xc7a100t and K26 xck26, prepared in 139a and run in brief 160) are current and lint-clean at every point they list, so a Vivado run can start from the repository alone.

  • simulation test: pass spec.yaml against the RTL headers, spec.md against spec.yaml, Verilator -Wall at every point, wrappers and build.yaml current and lint-clean: 5 test(s) passed in the recorded run evidence

MAC-F-LEAN-NOCLR: A clear-free run adds up modulo 2^ACCW, for every width

For every modulus M and run length, applying samples that never clear gives the initial accumulator plus the sum of the products, reduced modulo M: no saturation, no loss, however long the run. The statement is the specification and is NOT approved by a human (verif/lean_approvals.yaml is empty), so the proof is shown but not counted as verification. The Lean text is a hand transcription of the RTL's structure; it models no timing or clocking.

  • Lean proof (all widths): statement not approved A clear-free run adds up modulo 2^ACCW: statement not approved; ArithMac.run_noclr: kernel only; proof of the transcription, transcription not tested; recorded build (not re-run) evidence

MAC-F-LEAN-CLR: A clear makes the history irrelevant, for every width

Whatever the accumulator held, a sample with clr followed by clear-free samples gives that sample's product plus the others, reduced modulo M. The statement is the specification and is NOT approved by a human (verif/lean_approvals.yaml is empty), so the proof is shown but not counted as verification. The Lean text is a hand transcription of the RTL's structure; it models no timing or clocking.

  • Lean proof (all widths): statement not approved A clear makes the history irrelevant: statement not approved; ArithMac.run_after_clr: kernel only; proof of the transcription, transcription not tested; recorded build (not re-run) evidence

MAC-P-OOC: Every prepared point places and routes out of context on Artix-7 and K26

Each point of the build files of mac (build/<variant>/build.yaml; 20 in all, both parts) goes through Vivado 2026.1 out-of-context synthesis, placement and routing and leaves a recorded result (utilisation, WNS, WHS, Fmax, logic levels, vectorless power) in verif/results/vivado_ooc_<variant>_<part>.json. The measured values and each point's pre-stated expectation are in the Measured table of spec.md and in verif/results/vivado_surface.json; this requirement states only that the measurement exists for every point, because no Fmax or area bound has been agreed. Bound: prepared points with a routed out-of-context Vivado result at least 20 points; condition: Vivado 2026.1 out-of-context, one thread, the clocks of the build files, brief 160.

  • post-route timing: pass The routed Vivado results of every prepared point (the records of the last run): measured 20 points; bound at least 20 points evidence
