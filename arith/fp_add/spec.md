# Floating-point adder (IEEE-754-style binary formats) (arith/fp_add)

Generated by `python -m arith.tools.gen_spec_md` from [spec.yaml](spec.yaml); edit the YAML, not this file. Part of the arithmetic library of brief 139e ([../README.md](../README.md)).

y = a + b for a binary floating-point format of EXP exponent and MAN fraction bits (binary32 is 8/23, bfloat16 8/7, binary16 5/10; any EXP >= 2 and MAN >= 1 works), one correctly rounded result per clock (round to nearest, ties to even), with the special cases fixed and documented. Two structures trade the length of the combinational path against LUTs: a single datapath, and a near/far dual datapath with a shorter normalisation. Each takes STAGES register ranks (0 to 3) and a SUBNORM switch between full subnormal support and flush-to-zero.

## Function

- format: sign (1 bit), exponent (EXP bits, bias 2**(EXP-1) - 1), fraction (MAN bits); y has the same format. An exponent field of all ones is infinity (fraction 0) or NaN (fraction nonzero); a field of 0 is zero (fraction 0) or subnormal
- y is the exact sum a + b rounded ONCE to nearest, ties to even (so the result is the correctly rounded sum; there is no other rounding mode and no exception flag)
- NaN: any NaN input, and infinity + (-infinity), give the canonical quiet NaN (sign 0, exponent all ones, fraction msb 1, rest 0); NaN payloads and signs are not propagated
- infinity: infinity + a finite number is that infinity; infinity + infinity of the same sign is that infinity; a finite sum too large to round to a finite number is an infinity of the sign of the sum
- zeros: x + (-x) is +0 for finite nonzero x; (+0) + (-0) is +0; (-0) + (-0) is -0; (+0) + (+0) is +0; zero plus a nonzero number is that number
- SUBNORM = 1: subnormal inputs and outputs follow IEEE 754 (gradual underflow, the sum of two numbers of the format is exact whenever the exact value is a multiple of the subnormal step, which every sum is when it is small)
- SUBNORM = 0 (flush to zero): a subnormal input is read as a zero of its own sign (denormals-are-zero) and a result smaller in magnitude than the smallest normal number, after rounding with an unbounded exponent range, is replaced by a zero of the result's sign
- the model (fp_common/fp_ref.py) adds with exact rational arithmetic and rounds once; the RTL aligns, adds on SP + 3 bits (guard, round, sticky), normalises and rounds, and equals the model for every input (exhaustive at small formats, proved by SymbiYosys at tiny formats, random elsewhere)

Signedness: sign-magnitude as IEEE 754: the top bit of a, b and y is the sign; there is no two's complement reading.

Exactness: exact in the sense of IEEE 754: y is the correctly rounded value of the exact sum (round to nearest, ties to even), for every input including zeros, subnormals (SUBNORM = 1), infinities and NaNs; the error is at most half a unit in the last place (0.5 ulp) except where the result is flushed or overflows.

Latency: clocks from the operands being presented to y being valid; 0 means combinational; throughput is one sum per clock in every variant.

| Variant | Module | Latency (clocks) | Trade-off |

| `dual_path` | `fp_add_dual` ([rtl/fp_add_dual.sv](rtl/fp_add_dual.sv)) | `STAGES` | a near path (exponents differ by at most 1, or a subnormal operand: a one-bit alignment, an adder and a full leading-zero count) and a far path (a full-width aligner, an adder and a normalisation of at most two places) computed side by side and selected before rounding; no path has both a full-width aligner and a full-width normaliser, so the combinational path is shorter, for about one more adder and one more small shifter in LUTs |

### Intended primitive use

- `single_path`, Artix-7 (xc7a100t): 0 DSP, 0 BRAM; about 450 to 600 LUT6 and 60 CARRY4 at binary32 (two 27-bit barrel shifters of about 5 LUT levels each, one 28-bit adder); flip-flops only for the rank registers (about 100 per rank at STAGES 3)
  - K26 (xck26): 0 DSP, 0 BRAM; as a7 with CARRY8 cells
- `dual_path`, Artix-7 (xc7a100t): 0 DSP, 0 BRAM; about 1.3 to 1.6 times the LUTs of single_path at binary32 (a second adder and a three-way small shifter, plus the near path's 1-bit aligner and its own leading-zero counter and shifter); shorter longest path; flip-flops only for the rank registers (more bits per rank than single_path: both paths' operands are registered)
  - K26 (xck26): 0 DSP, 0 BRAM; as a7 with CARRY8 cells

## Interface contract

Written without knowing the design the block will sit in (brief 139e, owner decision 24): this is what a user can rely on and must provide.

- Protocol: plain registered-or-combinational ports, no handshake: operands are sampled every clock and one sum leaves, with no valid, ready or backpressure. A caller that needs a valid bit delays its own valid by STAGES
- Throughput: one sum per clock in every variant (initiation interval 1)
- Latency: per variant, in clocks: STAGES (0 to 3) for both single_path and dual_path
- Reset: none: no control state; the rank registers hold data only and y is meaningless for STAGES clocks after power-up
- Clock: one clock, rising edge, no clock-enable and no gating; clk is present but unused when STAGES is 0
- Stalls: none: the pipeline cannot be frozen (no enable)

|---|---|---|
| `single_path` | `STAGES` | 1 per clock |
| `dual_path` | `STAGES` | 1 per clock |

## Integration

- Port timing: STAGES 0 is one long combinational path from a and b to y (two barrel shifters and an adder in series: expect many nanoseconds at binary32); STAGES 1 registers only y, so the path from a and b is still the whole adder; STAGES 3 splits it into align, add and normalise-and-round, each about a third, with a register on y so the block sits between ordinary registers with a full clock on both sides only at STAGES 3 (the input side is the aligner, not a register)
- Constraints to carry: no multicycle or false paths, one clock. Keep the rank registers as written (do not retime across the aligner with keep or dont_touch changes if the latency must be exactly STAGES; Vivado does not retime unless asked). The shifters are wide multiplexers: floorplan the block in one region at binary32. The flush-to-zero build (SUBNORM 0) removes the denormalising shifter at the output
- Verification after integration: rerun the packaged harness against your instance ([harness/README.md](harness/README.md)); it needs no other file of this repository.

## What a user could guess wrong

- the result is correctly rounded to nearest, ties to even; there is no rounding-mode input, no sticky or exception flag output (overflow, underflow, inexact, invalid)
- every NaN result is the canonical quiet NaN (sign 0, fraction 0x400000 for binary32): the payload and sign of an input NaN are NOT propagated, and a signalling NaN is not distinguished
- with SUBNORM = 0 a subnormal INPUT is treated as zero: 1.0 + (a subnormal) = 1.0, and (subnormal) + (subnormal) = +0 or -0 by the zero rules. A result is flushed when it is below the smallest normal number after rounding with an unbounded exponent range; a sum that rounds up to exactly the smallest normal number is NOT flushed
- x + (-x) is +0, never -0 (round to nearest); only (-0) + (-0) gives -0
- there is no valid, ready or reset: for STAGES clocks after power-up y is not meaningful, and a change of EXP, MAN or SUBNORM is a different block, not a mode
- STAGES is the number of register ranks and the latency, not a retiming request. Above 3 it behaves as 3; values outside the ranges in the table above (EXP below 2, MAN below 1) are not rejected by an assertion
- the exponent bias is 2**(EXP-1) - 1 for every EXP; EXP = 8, MAN = 7 is bfloat16 (NOT binary16, which is EXP = 5, MAN = 10); half-precision formats other than these two are not checked against any external library

## Lean, and what is research

Core Lean (4.36, no Mathlib) has no IEEE-754 library (Flocq is a Coq library). The rounding and special-case rules are stated in "Function" above and written as a program in fp_common/fp_ref.py (exact rational arithmetic, one rounding); they are checked against NumPy's float32 and float16, against an enumeration of every value of a tiny format, by simulation of every variant, and by SymbiYosys proofs against a wide-integer specification at tiny formats. None of that is a Lean proof. Lean (formal/lean/Arith/Float.lean) states only three small integer facts that the RTL relies on: that the rounding increment added to the packed {exponent, fraction} pattern carries into the exponent, that left-normalising by the leading-zero count puts the leading one at the top, and that the guard-and-sticky rule is round-to-nearest with ties to even. They are proved for all widths; the statements are NOT approved (verif/lean_approvals.yaml is empty), so the matrix shows "statement not approved". Marked research and not attempted: that fp_ref.py's rounding is IEEE roundTiesToEven for every format and exponent range (it needs a real-number or rational model of the format, as Flocq gives in Coq), and the adder's alignment-with-sticky argument (a sticky bit OR-ed into the last place of the aligned operand gives the correct rounding because three bits are kept below the significand and the larger operand's low bits are zero). Those are covered by simulation and by the proofs at the tiny formats only.
