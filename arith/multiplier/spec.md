# Integer multiplier, full-width product (arith/multiplier)

Generated by `python -m arith.tools.gen_spec_md` from [spec.yaml](spec.yaml); edit the YAML, not this file. Part of the arithmetic library of brief 139a ([../README.md](../README.md)).

A WA x WB integer multiplier returning the exact WA + WB bit product, signed or unsigned. Three implementations trade DSP blocks against LUTs and carry chains: a DSP-mapped multiply with 0 to 3 pipeline registers, a LUT array of shifted partial products, and a radix-4 Booth array with half as many rows.

## Function

- SIGNED = 0: p = a * b, both read as unsigned numbers (a below 2**WA, b below 2**WB)
- SIGNED = 1: p = a * b with a and b read as two's complement numbers, p as a (WA + WB)-bit two's complement number
- p is never truncated: the full product of any two inputs fits in WA + WB bits
- Booth recoding: b is cut into radix-4 digits d_i = -2 b[2i+1] + b[2i] + b[2i-1]; the digit sum equals b's value for every width (Lean: ArithBooth.booth_correct)

Signedness: SIGNED chooses the reading of a, b and p; the same RTL file serves both.

Exactness: exact: p equals the integer product for every input; the full WA + WB bit result is returned, so nothing overflows (the one signed corner, -2**(WA-1) times -2**(WB-1), is 2**(WA+WB-2) and fits).

Latency: clocks from the operands being presented to p being valid; 0 means combinational; throughput is one product per clock in every variant.

## Variants

Each variant is one SystemVerilog file under `rtl/`, with the same ports. Parameters of the variant beyond the ones above are in its header. The primitive use is what the code is written to infer; it was stated BEFORE any Vivado run and is not a measurement.

| Variant | Module | Latency (clocks) | Trade-off |
|---|---|---|---|
| `dsp` | `mult_dsp` ([rtl/mult_dsp.sv](rtl/mult_dsp.sv)) | `STAGES` | DSP blocks and no LUTs; the fastest and the smallest in fabric, at the price of scarce DSPs; STAGES 3 uses the DSP's own registers |
| `lut_array` | `mult_lut_array` ([rtl/mult_lut_array.sv](rtl/mult_lut_array.sv)) | `REG` | no DSP; about one LUT per partial-product bit and WB - 1 adders in series, so the longest combinational path and the most LUTs of the three |
| `booth_r4` | `mult_booth_r4` ([rtl/mult_booth_r4.sv](rtl/mult_booth_r4.sv)) | `REG` | no DSP; about half the adder rows of lut_array (shorter carry path) for a select-and-negate stage per row; the usual hardware-multiplier area/delay trade |

### Intended primitive use

- `dsp`, Artix-7 (xc7a100t): DSP48E1: 1 for WA <= 25 and WB <= 18 signed (24 and 17 unsigned); about ceil((WA+1)/25)*ceil((WB+1)/18) tiled; LUTs and FFs only for the tiling adders and any register not absorbed
  - K26 (xck26): DSP48E2 (27 x 18 signed): 1 for WA <= 27 and WB <= 18 signed; ceil((WA+1)/27)*ceil((WB+1)/18) tiled
- `lut_array`, Artix-7 (xc7a100t): 0 DSP; about WA*WB/2 to WA*WB LUTs; WB - 1 carry chains of up to WA+WB bits (CARRY4); REG FFs of WA+WB
  - K26 (xck26): 0 DSP; as a7 with CARRY8 cells
- `booth_r4`, Artix-7 (xc7a100t): 0 DSP; about NP - 1 carry chains of up to WA+WB bits with NP = ceil((WB + 1 - SIGNED)/2); about one LUT per partial-product bit for the selector
  - K26 (xck26): 0 DSP; as a7 with CARRY8 cells

## Interface contract

Written without knowing the design the block will sit in (brief 139a, owner decision 24): this is what a user can rely on and must provide.

- Protocol: plain registered-or-combinational ports, no handshake: operands are sampled every clock and one product per clock leaves, with no valid, ready or backpressure. A caller that needs a valid bit delays its own valid by the variant's latency
- Throughput: one product per clock in every variant (initiation interval 1)
- Latency: per variant, in clocks: dsp STAGES (0 to 3), lut_array REG (0 or 1), booth_r4 REG (0 or 1)
- Reset: none: no control state; registered variants hold data only and their outputs are meaningless for latency clocks after power-up
- Clock: one clock, rising edge, no clock-enable and no gating; clk is present but unused when the latency is 0
- Stalls: none: the pipeline cannot be frozen (no enable); DSP registers are inferred without a clock-enable

| Variant | Latency (clocks) | Throughput |
|---|---|---|
| `dsp` | `STAGES` | 1 per clock |
| `lut_array` | `REG` | 1 per clock |
| `booth_r4` | `REG` | 1 per clock |

## Integration

- Port timing: dsp with STAGES 3: operands are registered inside the block (AREG/BREG) and the product leaves a register (PREG), so the block can sit between ordinary registers with a full clock of slack on both sides; STAGES 0 to 2 leave a combinational path to or from the DSP that the caller must budget (about the DSP delay: it dominates). lut_array and booth_r4 with REG 0 are combinational from a/b to p (a long chain of adders: register both sides and expect a multi-ns path); with REG 1 the output is registered but the input path to it is still the whole array
- Constraints to carry: no multicycle or false paths, one clock. DSP variants: use the DSP block's registers (STAGES 3) for the highest clock; placing the surrounding registers next to the DSP column helps. Keep the three DSP register stages un-merged (no keep or retiming that moves them). LUT variants: nothing to carry beyond the clock; their cost is the carry-chain columns, so a floorplan that keeps the array in one region helps timing
- Verification after integration: rerun the packaged harness against your instance ([harness/README.md](harness/README.md)); it needs no other file of this repository.

## What a user could guess wrong

- p is the full WA + WB bit product, not truncated to the wider operand's width
- with SIGNED = 1 both operands are signed: a signed times unsigned product needs one more operand bit (sign-extend the unsigned one by a zero) and is not a parameter
- an unsigned operand costs one extra multiplier bit on a DSP (the DSP multiplier is signed), so a 17 x 17 unsigned product needs the same DSP as 18 x 18 signed
- the pipelined configurations have no reset and no valid: for STAGES clocks after power-up the output is not meaningful
- STAGES (dsp) and REG (lut_array, booth_r4) are register stages in the variant, not retiming requests: Vivado does not move them unless retiming is enabled
- STAGES above 3 behaves as 3 and REG other than 0 behaves as 1; SIGNED other than 0 or 1 behaves as 1; none of this is rejected by an assertion
