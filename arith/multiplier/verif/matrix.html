Requirements in full

MUL-F-MODEL: The bit-exact model is right

arith/multiplier/model.py gives, for every input, the result that spec.md defines. It agrees with an independent formulation (a shift-and-add formulation (and, for the Booth recoding, the digit-sum identity)) on every input at small widths and with Python's integer arithmetic on random large-width inputs, and the conventions that a user could guess wrong (spec.md, last section) are pinned by examples.

  • simulation test: pass The model against independent formulations (exhaustive small, random large) and the pinned conventions: 5 test(s) passed in the recorded run evidence

MUL-F-EXACT: Every variant is bit-exact against the model

At every parameter point listed in spec.yaml (24 exhaustive points, 14 random ones, across 3 variants), each variant's outputs equal the model's in every clock: every input is driven at the small points; edge values, runs of ones, and random inputs at the large ones. The function is exact, so there is no error bound.

  • simulation test: pass Every variant against the model, every input, at the small points (Icarus + cocotb): 24 test(s) passed in the recorded run evidence
  • simulation test: pass Every variant against the model at the large points: edge values, carry runs and random inputs (Icarus + cocotb): 14 test(s) passed in the recorded run evidence

MUL-F-LAT: Latency is as specified and the bench would notice if it were not

Each variant's latency in clocks is the expression in spec.yaml (dsp: STAGES; lut_array: REG; booth_r4: REG), and the bench, run with a latency two clocks off, fails for every variant, so the passing runs prove the latency rather than assume it.

  • simulation test: pass The bench passes at the stated latency and fails two clocks off, for every variant: 3 test(s) passed in the recorded run evidence

MUL-F-EQUIV: The variants are equivalent to a plain reference, by proof where the tools allow

SymbiYosys with the slang front end checks the variants against each other and a plain reference (a single `+` or `*`, or the specification written as RTL). The jobs in formal/jobs.yaml name the widths; a proof is by k-induction (for all inputs, any run length) at the widths listed there, a bounded check holds only to its stated depth. Widths beyond the listed ones are covered by simulation, not by proof.

  • formal: pass k-induction proofs of the variants against the reference (4 jobs; widths in formal/jobs.yaml): 4 test(s) passed in the recorded run evidence
  • formal: pass Each formal check refutes a planted fault (the check can fail): 2 test(s) passed in the recorded run evidence

MUL-F-BENCH: The bench catches seeded faults

Every one of the mutants in verif/mutants.yaml (one exact text change each, in the variant's RTL: an inverted condition, a wrong constant, a dropped connection, a lost reset) makes the cocotb bench fail; mutants that survive or do not build are reported, never hidden.

  • simulation test: pass The mutation run as a test: no mutant survives, none fails to build: 1 test(s) passed in the recorded run evidence
  • simulation measurement: pass Mutants killed of valid mutants (the record of the last full run): survived = []; invalid = []; valid = 17; score_pct = 100 evidence

MUL-F-HARNESS: The packaged verification harness is a standalone deliverable that works

arith/multiplier/harness holds the model, the cocotb bench, a SystemVerilog checker, coverage targets and a runner that needs nothing else from the repository. Run standalone against every variant (one small exhaustive point and one large random point each, with the checker beside the instance) it passes and the random runs meet every coverage target; run against a planted fault it fails, with and without the checker. Its generated files are the repository's own bench, so they cannot drift.

  • simulation test: pass The packaged harness run standalone on every variant (with the checker and the coverage targets) and on a planted fault: 8 test(s) passed in the recorded run evidence

MUL-F-PACKAGE: The RTL is lint-clean, and its files agree with the specification and with the Vivado build files

spec.yaml states an interface contract (protocol, throughput, latency, reset, clock, stalls) and integration guidance (port timing, constraints to carry). Every variant passes Verilator -Wall at every point of spec.yaml; its ports and default parameters are the ones spec.yaml states; its header states the intended primitive use before any Vivado run; spec.md is the rendering of spec.yaml; the out-of-context wrapper and the build.yaml for each variant (Artix-7 xc7a100t and K26 xck26, prepared and not run) are current and lint-clean at every point they list, so a Vivado run can start from the repository alone.

  • simulation test: pass spec.yaml against the RTL headers, spec.md against spec.yaml, Verilator -Wall at every point, wrappers and build.yaml current and lint-clean: 5 test(s) passed in the recorded run evidence

MUL-F-LEAN-BOOTH: Radix-4 Booth digits sum to the multiplier's value, for every width

For every multiplier width, the radix-4 Booth digits d_i = -2 b[2i+1] + b[2i] + b[2i-1] of an even-length bit pattern sum, weighted by 4^i, to its two's-complement value. The statement is the specification and is NOT approved by a human (verif/lean_approvals.yaml is empty), so the proof is shown but not counted as verification. The Lean text is a hand transcription of the RTL's structure; it models no timing or clocking.

  • Lean proof (all widths): statement not approved Radix-4 Booth digits sum to the multiplier's value: statement not approved; ArithBooth.booth_correct: kernel only; proof of the transcription, transcription not tested; recorded build (not re-run) evidence

MUL-F-LEAN-BOOTH-UNS: An unsigned multiplier extended by a zero bit has non-negative digits summing to its value, for every width

For every pattern whose top bit is 0 (an unsigned multiplier given the RTL's extra zero bit), the Booth digit sum equals the unsigned value. The statement is the specification and is NOT approved by a human (verif/lean_approvals.yaml is empty), so the proof is shown but not counted as verification. The Lean text is a hand transcription of the RTL's structure; it models no timing or clocking.
