# Verification harness for fft_mdc2 (2-parallel streaming FFT (two samples per clock, N = 16 to 4096))

Generated by `python -m arith.tools.gen_harness_fft` (arith brief 161); the handwritten parts are `chk_top.sv` and `coverage.yaml`. This folder is a deliverable: rerun it against your own instance after you integrate or change the block. It needs nothing else from the repository.

## What is in it

| File | What |
|---|---|
| `model.py` and its support (`fft_ref.py`) | the bit-exact model of the specification ([../spec.md](../spec.md)), in Python integers |
| `bench.py`, `frames.py`, `fcover.py`, `fft_mdc2_cocotb.py` | the cocotb bench: drives frames or streams (directed stimuli: impulses, tones, corner values; random ones; the stalls and gaps the contract permits), compares every output with the model bit for bit and checks the latency |
| `assertions.sv` | passive SystemVerilog checkers (simulation only): the frame structure of the output (N/2 consecutive beats from sof, no unknowns). Their error counters must stay 0 |
| `chk_top.sv` | your instance with those checkers beside it, used by `run_harness.py --checker` |
| `coverage.yaml` | the coverage targets (events the stimulus must produce, with minimum counts); `run_harness.py` fails a full run that misses one |
| `run_harness.py` | the standalone runner (Icarus Verilog + cocotb) |

## Running it against your instance

Needs `iverilog`, Python 3, `pip install cocotb==2.0.1 pyyaml`.

```
python3 run_harness.py --rtl my_fft_mdc2.sv --top my_module --variant par2 --params '{"LOGN": 5, "W": 8, "TW": 10, "SCALE": 0, "RND": 1, "ORDER": 0, "CMUL": 4, "TWSTAGES": 1, "MULSTAGES": 2}' --latency 45 --mode all --checker
```

- `--top` must have the ports listed in the specification under the same names, and every parameter of the specification (pass them all in `--params`; the model is built from them).
- `--latency` is your instance's latency in clocks as the specification defines it. Giving a wrong latency fails the run: that is deliberate, it checks the number. The latency of this block's variants (`par2`) is stated in `../spec.yaml` as a formula.
- `--mode` is one of `all` (default) or `directed`, `randomised`, `gaps`: the modes are the benches of the repository's own tests (stimuli, schedules and checks described in `fft_mdc2_cocotb.py`).
- `--checker` builds your instance next to `assertions.sv`; the run fails if a checker counts a violation. To use the checkers in your own bench instead, instantiate them with the same signals as in `chk_top.sv`.
- Exit status 0 means: every output matched the model, the latency and the checkers were as specified, and (mode `all`) every coverage target was met. `--build-dir` keeps the logs and the coverage files.

## Interface the harness assumes

- Protocol: streaming frames of N/2 pairs, no back-pressure: in_valid high for N/2 consecutive clocks per frame (in_sof on the first), the next frame after no gap or at least N/8 idle clocks, in_ready always 1, the consumer takes every output pair in the clock it is presented
- Throughput: two samples per clock continuously: a frame every N/2 clocks (N/2 clocks of input, N/2 of output)
- Latency: N/2 - 1 + (LOGN - 1) + ((LOGN - 2) // 2) * (TWSTAGES + MULSTAGES + 1) + TWSTAGES + MULSTAGES + 2, plus N/2 + 1 for natural order
- Reset: synchronous: clears the control state of both sub-pipelines and of the combining stage (counters, frame markers, valid flags, the direction-flag line); data memories and delay lines are not cleared. A frame in flight when rst is asserted is lost; no test covers a reset in the middle of a frame
- Clock: one clock, rising edge, no clock-enable
- Stalls: none: once started a frame cannot be paused (in_valid must stay high for N/2 clocks) and the output cannot be stalled

## What the harness does not cover

- Timing, area and power: nothing here is a Vivado result. The harness checks function against the model, the interface rules and the stated latency, in simulation only.
- A reset in the middle of a frame or a block, and parameter combinations outside the points of `../spec.yaml` (the model supports them; the harness is run at the points you give it).
- The checkers are immediate assertions evaluated on the clock edge, not concurrent SVA properties (the open-source simulator does not run those).
