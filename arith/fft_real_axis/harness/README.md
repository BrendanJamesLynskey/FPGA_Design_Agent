# Verification harness for fft_real_axis (AXI4-Stream real-input FFT (wrapper of fft_real, N REAL samples, N/2 + 1 bins))

Generated by `python -m arith.tools.gen_harness_fft` (arith brief 161); the handwritten parts are `chk_top.sv` and `coverage.yaml`. This folder is a deliverable: rerun it against your own instance after you integrate or change the block. It needs nothing else from the repository.

## What is in it

| File | What |
|---|---|
| `model.py` and its support (`fft_ref.py`) | the bit-exact model of the specification ([../spec.md](../spec.md)), in Python integers |
| `bench.py`, `frames.py`, `fcover.py`, `fft_real_axis_cocotb.py` | the cocotb bench: drives frames or streams (directed stimuli: impulses, tones, corner values; random ones; the stalls and gaps the contract permits), compares every output with the model bit for bit and checks the latency |
| `assertions.sv` | passive SystemVerilog checkers (simulation only): the AXI4-Stream handshake rules on both streams, tlast positions, the source's no-pause obligation and the sink's no-stall promise. Their error counters must stay 0 |
| `chk_top.sv` | your instance with those checkers beside it, used by `run_harness.py --checker` |
| `coverage.yaml` | the coverage targets (events the stimulus must produce, with minimum counts); `run_harness.py` fails a full run that misses one |
| `run_harness.py` | the standalone runner (Icarus Verilog + cocotb) |

## Running it against your instance

Needs `iverilog`, Python 3, `pip install cocotb==2.0.1 pyyaml`.

```
python3 run_harness.py --rtl my_fft_real_axis.sv --top my_module --variant post --params '{"LOGN": 5, "W": 16, "TW": 16, "SCALE": 1, "RND": 1, "CMUL": 4, "TWSTAGES": 1, "MULSTAGES": 2}' --latency 44 --mode all --checker
```

- `--top` must have the ports listed in the specification under the same names, and every parameter of the specification (pass them all in `--params`; the model is built from them).
- `--latency` is your instance's latency in clocks as the specification defines it. Giving a wrong latency fails the run: that is deliberate, it checks the number. The latency of this block's variants (`post`) is stated in `../spec.yaml` as a formula.
- `--mode` is one of `all` (default) or `directed`, `randomised`, `checker`: the modes are the benches of the repository's own tests (stimuli, schedules and checks described in `fft_real_axis_cocotb.py`).
- `--checker` builds your instance next to `assertions.sv`; the run fails if a checker counts a violation. To use the checkers in your own bench instead, instantiate them with the same signals as in `chk_top.sv`.
- Exit status 0 means: every output matched the model, the latency and the checkers were as specified, and (mode `all`) every coverage target was met. `--build-dir` keeps the logs and the coverage files.

## Interface the harness assumes

- Protocol: AMBA AXI4-Stream on both interfaces. Slave: frames of N/2 beats, tlast on the last, tvalid held high through a frame; the wrapper provides back-pressure only between frames (N/8 clocks of tready low after each frame). Master: frames of N/2 + 1 beats, tlast on the last, no back-pressure (the sink's tready must be 1). No AXI4-Lite
- Throughput: 2 real samples per clock inside a frame; N real samples per N/2 + N/8 clocks at the fastest legal frame spacing (the output frame takes N/2 + 1 clocks, so output frames never overlap)
- Latency: (N/2) - 1 + (LOGN - 1) + ((LOGN - 2) // 2) * (TWSTAGES + MULSTAGES + 1) + N/2 + MULSTAGES + 3, as the wrapped core
- Reset: aresetn low for at least one clock clears the control state of the wrapper (start flag, gap counter, output beat counter) and of the core (the data memories are not cleared); a frame in flight is lost; the first frame after reset starts with its first beat, and there is no gap after reset
- Clock: one clock, rising edge, no clock enable
- Stalls: the input is back-pressured between frames only; neither stream can be stalled inside a frame or at the output

## What the harness does not cover

- Timing, area and power: nothing here is a Vivado result. The harness checks function against the model, the interface rules and the stated latency, in simulation only.
- A reset in the middle of a frame or a block, and parameter combinations outside the points of `../spec.yaml` (the model supports them; the harness is run at the points you give it).
- The checkers are immediate assertions evaluated on the clock edge, not concurrent SVA properties (the open-source simulator does not run those).
