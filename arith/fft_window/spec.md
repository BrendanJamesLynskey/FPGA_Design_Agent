# Window multiplier (one coefficient for both parts of a complex sample) (arith/fft_window)

Generated by `python -m arith.tools.gen_spec_md` from [spec.yaml](spec.yaml); edit the YAML, not this file. Part of the frequency-domain suite of brief 148 ([../README.md](../README.md)).

yr = round(xr * w / 2**WW) and yi = round(xi * w / 2**WW): a complex sample (WD-bit signed parts) times a real window coefficient w, a WW-bit UNSIGNED number of value w / 2**WW (so the largest coefficient is 1 - 2**-WW; exactly 1.0 cannot be represented, a stated convention). Rounding half up or truncation (RND). The result has the width of the input and cannot overflow. One sample per clock. The coefficient comes from the caller (arith/fft_common/fft_ref.py has rect, Hann, Hamming and Blackman coefficient generators).

## Function

- xr and xi are WD-bit two's complement; w is a WW-bit unsigned number; yr and yi are WD-bit two's complement
- RND = 1: y = floor((x * w + 2**(WW-1)) / 2**WW), round half up (toward plus infinity at a tie); RND = 0: y = floor(x * w / 2**WW), truncation toward minus infinity
- because w < 2**WW the magnitude of y never exceeds that of x (|y| <= |x|), so y always fits WD bits
- the same coefficient multiplies the real and the imaginary part

Signedness: samples signed two's complement; the coefficient unsigned.

Exactness: bit-exact against the model, which rounds once: the error against the real product is at most 0.5 unit in the last place (RND = 1) or less than 1 (RND = 0).

Latency: clocks from the inputs being presented to yr and yi being valid; 0 means combinational; one sample per clock.

## Interface contract

Written without knowing the design the block will sit in (brief 148, owner decision 24): this is what a user can rely on and must provide.

- Protocol: plain ports, no handshake: a sample and its coefficient are sampled every clock; the caller delays its own valid by STAGES and presents the coefficient with its sample (a counter-addressed ROM of the caller, one clock ahead if the ROM is synchronous)
- Throughput: one sample per clock (initiation interval 1)
- Latency: STAGES (0 to 3)
- Reset: none: no control state; data only
- Clock: one clock, rising edge, no clock-enable
- Stalls: none

## Integration

- Port timing: STAGES 3 lets the DSP absorb the operand, product and output registers; at STAGES 0 the multiplier and the rounding adder are in series with the caller's logic
- Constraints to carry: one clock; keep the stages as written. The coefficient generator is outside this block: a window table sized N x WW bits per window shape, or one shared table with a run-time shape select
- Verification after integration: this function has no packaged harness (brief 148 left it out; see the report): rerun its bench (tests/) against your instance, which needs the repository's arith/tools and fft_common helpers.

## What a user could guess wrong

- the coefficient is UNSIGNED with scale 2**WW: 1.0 is not representable, the largest coefficient is 1 - 2**-WW, so a rectangular window of 'all ones' attenuates by 2**-WW; a window that must reach 1.0 uses WW + 1 bits with the top bit meaning exactly 1.0, which this block does not do
- RND = 1 rounds half up, not half to even, so a long run of exact ties is biased upward by half a unit; RND = 0 truncates toward minus infinity and is biased downward by half a unit on average
- the same coefficient is applied to the real and the imaginary part: a complex window (a different coefficient per part) is not this block
- the window coefficients themselves are the caller's: fft_common/fft_ref.window_coeffs gives periodic (DFT-even) Hann, Hamming and Blackman tables rounded to nearest and clipped to 2**WW - 1; a symmetric window of the same name has slightly different values
- STAGES is the number of register ranks and the latency, not a retiming request. Above 3 it behaves as 3
- no valid, ready or reset: for STAGES clocks after power-up the outputs are not meaningful
